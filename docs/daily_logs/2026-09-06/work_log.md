## 세션 13 발견 — S-7 원격 점검: 감사가 짚지 않은 두 번째 노출 자리

오너가 배포 호스트 접근을 열어 줘 S-7 을 착수했다. **접속 정보는 저장소에 적지 않는다**(머리의 공개 저장소 보안 규칙) — 아래는 역할 별칭과 실측 결과만이다.

- **문제**: 감사는 토큰이 `/proc/<pid>/cmdline`(**0444**) 에 있다는 축만 짚었다. 실측해 보니 **systemd 유닛 파일이 `0644`** 이고 `ExecStart=` 에 토큰이 그대로 있다 — **프로세스를 보지 않아도 파일 하나로 읽힌다.** 노출 자리가 하나가 아니라 둘이다.
- **감사의 심각도 근거도 절반만 참이다**: *"로그인 계정은 uid 1000 하나뿐"* 은 **로그인 셸을 가진 계정**에 대해서만 맞고, 서비스 계정 여럿이 비-root uid 로 돌고 있다(`ps` 실측). 0444 를 읽을 주체가 root·오너 말고도 있다는 뜻이라 감사의 LOW 판정은 한 칸 올려 볼 근거가 있다.
- **처방 확인**: 이 호스트의 `cloudflared` 가 `--token-file`·`$TUNNEL_TOKEN_FILE` 을 지원한다(`--help` 실측). **`EnvironmentFile=` 보다 `--token-file` 이 낫다** — 값이 프로세스 `environ` 에조차 안 들어가 자식 프로세스·코어덤프 경로가 하나 더 닫힌다.
- **★ 막힌 것**: 배포 호스트에서 **`sudo` 가 비밀번호를 요구해 작업 AI 가 변경을 완결할 수 없다.** 유닛 파일은 root 소유이고 cloudflared 도 root 로 돈다. 오너가 직접 실행해야 한다.
- **처리**: 치환 정규식을 **읽기 전용 드라이런으로 검증**했다(추출 184바이트 · `--token` 발생 1 · 시뮬레이션 `ExecStart` 정상). 오너 실행용 스크립트를 세션 밖(스크래치패드)에 준비했다 — 백업·추출·치환·재기동·검증·롤백을 담고 **토큰 값은 어디서도 출력하지 않는다.**
- **★ 이번 점검에서 토큰 값은 세션에 남지 않았다** — 모든 명령이 `--token` 값을 `sed` 로 마스킹했고, 길이·발생 수만 셌다. **회전(처방 ②) 판단의 입력이 되는 사실이다**(2026-09-05 점검은 세션 출력에 값이 남았다).

## 세션 13 발견 — 위생 가드가 **공인 IP** 는 안 본다

광의 규칙은 RFC1918 사설 대역만 본다. 그런데 이 프로젝트의 배포 호스트 주소는 **공인 대역**이라 **문서에 적혀도 가드가 조용하다.** 정확 일치 규칙도 값을 알아야 등재할 수 있는데, **공인 주소를 `_FORBIDDEN_VALUES` 에 넣는 것은 조각으로 나눠도 공개 저장소에 그 값을 싣는 일**이라 역효과다.

- 검증자 H4(IPv6 ULA·선행 0 변형)와 **같은 성격의 계약 밖 축**이고, 브리프가 *"일반 시크릿 스캐닝은 별개 사안"* 으로 유예한 자리와 이어진다.
- **지금은 규칙(HANDOFF 머리)만 있고 강제가 없다.** 사설 축은 이번에 강제가 붙었지만 공인 축은 여전히 사람 손에 달려 있다.
- **오너 판단 사안**으로 남긴다 — 값을 저장소에 안 싣고 잡으려면 저장소 밖 허용/금지 목록(예: 로컬 전용 설정 파일이나 pre-commit 훅)이 필요하고, 그것은 이 저장소의 "가드는 저장소 안에서 재현 가능해야 한다"는 성질과 상충한다.

## 세션 13 후속 — S-7 저장 방식 축 폐쇄 (오너 시행 · 작업 AI 검증)

`sudo` 가 비밀번호를 요구해 작업 AI 는 시행할 수 없었다. **오너가 배포 호스트에서 직접 실행**했고 작업 AI 는 준비·검증만 했다. 접속 정보는 규칙대로 저장소에 적지 않는다.

### 시행

`ExecStart` 의 `--token <값>` → `--token-file <root 0600 파일>`. 디렉터리 `0700`. 재기동 시 터널 단절 약 5초.

### 검증 (작업 AI 원격 실측, 값은 마스킹)

| 축 | 결과 |
|---|---|
| 프로세스 인자 | 토큰 없음 ✓ |
| 현행 유닛 파일 | 원시 토큰 0건 ✓ |
| 토큰 파일 | `0600 root:root`, 디렉터리 `0700`, 일반 유저 stat 불가 ✓ |
| `systemd` 디렉터리 전체 | 원시 토큰 **0건** ✓ |
| 서비스 | `active` · `enabled` · precheck 전 항목 PASS ✓ |

### ★ 발견 — 백업이 처방의 구멍이었다

시행 직후 실측에서 **백업 파일이 `0644` 권한과 토큰을 그대로 들고 남아 있었다**. `cp -a` 가 권한까지 복사하기 때문이고, **그 상태에서는 노출이 파일명만 바뀐 채 그대로**였다 — 세계 읽기 가능한 자리의 토큰이 여전히 1건이었다.

**원인은 처방 설계다.** 준비한 스크립트가 백업 삭제를 *"터널이 정상이면 지운다"* 는 **끝맺음 안내**로 적었다. 실제로는 **처방의 필수 마지막 단계**이고, 백업이 비밀값을 들고 있다는 사실 자체가 안내에 없었다. 오너가 지운 뒤 재실측해 0건을 확인했다.

**일반화**: 비밀값을 "더 좁은 권한의 자리"로 옮기는 모든 작업에서, **원본을 `cp -a` 로 백업하면 그 백업이 옛 권한을 상속한다.** 백업 삭제까지가 한 조치이고, 중간 상태는 노출이 **줄지 않고 이름만 바뀐** 상태다. HANDOFF S-7 행에 남겼다.

### 남은 축 — 회전(rotation)은 오너 판단

저장 방식은 *"누가 읽을 수 있나"* 를 고쳤을 뿐, *"이 값이 서버 밖으로 나갔나"* 는 별개다. 판단의 입력이 되는 사실 둘:

- **2026-09-05 점검은 세션 출력에 값이 남았다**(감사 기록의 서술).
- **2026-09-06 점검은 남지 않았다** — 모든 원격 명령이 `--token` 값을 `sed` 로 마스킹했고 길이·발생 수만 셌다.

**★ 순서가 있다**: 회전만 하고 인자를 그대로 두면 새 값이 같은 자리에 놓인다. 저장 방식이 먼저였고 그것은 이제 닫혔으므로, 회전은 지금 하면 새 값이 `0600` 파일로 바로 들어간다.

## 세션 14 — identity group Slice 5 검증 조건 폐쇄 (B1·B2) + 하드닝 (H1·H2)

검증 기록 [`../../verifications/2026-09-06/identity_group_slice_5.md`](../../verifications/2026-09-06/identity_group_slice_5.md)(조건부 합격, 커밋 `1eb1e6c`)의 차단 2건과 하드닝 2건.

### 1. B1 — 행동 결함: 판정이 필요 없는 승인이 503이었다

`to_judge = len(runnable) - (0 if canonical is not None else 1)` 는 **canonical 이 있다는 이유만으로 면제를 잃는다**. 그런데 개별 승격(`promote`)된 멤버는 canonical 을 가진 채 `needs_review` 로 남고, 그 멤버가 유일한 runnable 이면 루프는 그를 **seed 가지**로 닫는다(`canonical.source_candidate_id == candidate_id`) — 판정 대상이 0이다. 리터럴 ⑦(*"남은 멤버가 있을 때만 judge 가 필요하다"*)과 정면 충돌이고, **judge 를 구성하지 않는 한 그 그룹은 영영 승인 불가**였다.

**면제 조건을 루프의 분기와 같은 조건으로 맞췄다** — 값이 아니라 *같은 질문*을 두 곳이 하도록:

```python
exempt = 1 if (canonical is None or canonical.source_candidate_id in runnable) else 0
to_judge = len(runnable) - exempt
```

셀을 먼저 쓰고 **수정 전 503 재현을 확인한 뒤** 고쳤다(`AssertionError: 503 != 200`).

### 2. B2 — D3=A 멤버행 축 무셀

행동은 계약대로였지만 **관측면이 진행 문서(steps) 기반**이라 멤버행을 지워도 응답·replay 가 같았다. Slice 4 의 우연 잠금(거절 응답이 live 멤버를 순회)은 승인 구조에서 성립하지 않는다 — 그룹행(status·revision)과 멤버행 전건을 **직접** 단정하는 셀을 넣었다.

## 세션 16 — S-7 회전 축 종결(오너 결정: 하지 않는다) + 사고 기록

### 오너 결정 — 회전하지 않는다

- **값이 나간 범위가 오너 자신의 터미널과 작업 세션으로 한정된다**는 것이 오너의 판단이고, 그 범위 안에서는 유출로 보지 않는다.
- **이 계정의 대시보드에 `Refresh token` 경로가 없다**(실측). 그래서 회전은 곧 **터널 재생성**이고, 그 터널 하나가 공개 호스트네임 여러 개를 서빙하므로 라우트를 전건 재등록해야 한다 — **비용이 위험에 안 맞는다.**
- 구현자는 회전을 두 번 권고했고(저장 방식 폐쇄 시 · 값이 화면에 찍힌 뒤), 오너가 재확인해 결정했다. **저장 방식 축은 닫혔고 회전 축은 "하지 않음"으로 닫힌다.**

### ★ 사고 — 오너에게 건넨 명령이 터널을 두 번 죽였다(총 ~1시간, 공개 호스트네임 여럿 동시 정지)

| # | 건넨 명령 | 무슨 일이 났나 |
|---|---|---|
| 1 | `sudo sh -c 'printf %s "붙여넣기" > …'` | 따옴표 안의 **한글 자리표시자가 그대로 붙여넣어졌다.** 토큰 파일에 네 글자가 들어가 `Provided Tunnel token is not valid` |
| 2 | `read -rsp '…' TOKEN` + `printf %s "$TOKEN" \| …` | **변수 이름 자리(`TOKEN`)에 토큰을 넣었다.** 토큰이 프롬프트 문구가 되어 화면에 평문으로 찍혔고, 값은 `REPLY` 로 갔으며, `$eyJ…` 는 미정의라 **빈 파일**이 쓰였다 |

**두 번 다 원인이 같다 — 명령에 "고쳐야 하는 자리"가 있었다.** 구현자는 그 자리를 설명으로 표시했지만, 실행하는 쪽은 명령을 **통째로 붙여넣는다.**

**규칙으로 바꿨다**(HANDOFF S-7 행):

1. 값이 필요한 명령은 **고칠 곳이 없는 완성형**으로 준다. 값을 모르면 명령을 주지 말고 값을 먼저 받는다.
2. **재시작 전에 바이트 수를 먼저 확인**시킨다 — 빈 파일·자리표시자가 **서비스를 죽이기 전에** 잡힌다. 원래 값이 184바이트였다는 것을 알고 있었는데도 그 확인을 재시작 **뒤에** 뒀다.
3. `read -rsp` 처럼 **변수 이름이 인자로 들어가는 형태를 오너에게 주지 않는다** — 대화형 프롬프트는 자리표시자보다 안전해 보이지만, 자리가 하나 더 늘 뿐이었다.

**복구 경로가 얇았던 것도 함께 기록한다.** 토큰의 로컬 사본이 없었다 — 유닛 파일은 `--token-file` 로 바뀌었고 백업은 (올바르게) 지웠기 때문이다. 대시보드가 유일한 원천이었고, **어느 터널인지**는 옛 저널 로그의 `tunnelID=` 로 특정했다. **비밀값을 옮기는 처방에는 "원본을 어디서 다시 얻는가"가 절차에 포함돼야 한다** — 이번엔 운 좋게 로그에 단서가 남아 있었다.

### 5. ★ 설계를 한 번 되돌렸다 — 결과 상자의 자리

처음엔 결과 상자를 **그룹 `<li>` 안**에 뒀다. 셀 2개가 실패했고, 원인은 렌더가 아니라 **모양이 틀린 것**이었다: 그룹이 다 처리되면 멤버가 검토함을 떠나 **그룹 자체가 목록에서 사라지고, 결과도 함께 사라진다.**

그런데 거절 요약(`건너뜀 N건`)과 부분 실패는 **재조회를 넘겨 살아야 하는 바로 그 사실**이다 — 계획의 *"부분 실패와 conflict 는 성공처럼 닫지 않는다"* 가 성립하는 자리가 거기다. 상자를 **페이지 수준**으로 올렸다.

**셀이 배치 결함을 잡은 게 아니라 계약 위반을 잡았다.** 그룹이 살아 있는 동안만 보이는 결과 상자는 "부분 실패는 남긴다"를 절반만 지킨다.
