## Decisions

**D-2026-08-16-a. B2 는 선택지가 아니라 오너의 일반 규칙으로 닫혔다.**

- *오너 문언*: *"1. env에 외부 API가 있으면 그거 사용, 2. 그게 없다면 내부 LLM 모델 다운로드
  시도, 3. 모델 다운로드가 에러나 혹은 시도되지 못했다면 당연히 빌드 실패."*
- *★ 오너 질문이 짚은 것*: *"LLM 서버가 없다는 건 빌드할 때 선택하지 못했다는 것?"* — **반은
  맞다.** in-stack LLM 여부는 빌드 옵션이 아니라 **어떤 override 를 얹느냐**로 갈리고, 모델은
  빌드가 아니라 **첫 기동 때** 받는다(`llama` 는 pull 이미지이고 `-hf` 가 런타임 다운로드다).
  그래서 3번의 실패 지점은 `build` 가 아니라 **기동**이다. 이 구분을 HANDOFF 기동 표에 넣었다.
- *실측 — 규칙 ①②③은 알파에서 이미 돌고 있었다*: `llama.yml` 이 `${LLAMA_BASE_URL:-http://llama:9080}`
  라 ① env 우선 · ② 없으면 in-stack llama 가 받고 · ③ 못 받으면 healthcheck 실패 → gateway 가
  `depends_on: service_healthy` 에 걸려 안 뜬다. **그러므로 새로 정할 것이 없었다.**
- *결함이 있던 자리는 배포 override 하나*: 그 구성에는 llama 서비스가 **없어서 ②가 구조적으로
  불가능**한데 base 의 콜론 폴백이 살아 있어, ③ 대신 **자기 서버의 9080**(아무것도 없는 자리)을
  조용히 가리켰다. 스택은 healthy 로 뜨고 **생성만 전부 실패**한다.
- *결정*: 규칙을 그대로 적용해 **(a) 시행** — external override 의 gateway 에서만 `:?` 로 덮는다.
  base·llama override 는 **개발 머신의 폴백이 옳으므로** 안 건드린다. 즉 **같은 변수가 파일마다
  다른 계약**을 갖는다.
- *실측(전후)*:

  | 확인 | 결과 |
  |---|---|
  | 배포 override · 주소 없음 | **rc=1** + 한국어 사유(`required variable LLAMA_BASE_URL is missing a value: 외부 LLM API 주소가 필요하다 …`) |
  | 배포 override · 넷 다 지정 | **rc=0** |
  | 배포 override · 호스트 llama 명시 | `LLAMA_BASE_URL: http://host.docker.internal:9080` — **여전히 쓸 수 있다** |
  | base 단독 · llama override | 둘 다 **rc=0**, 알파 주소 `http://llama:9080` 무변 |

- *★ 세 번째 행이 감사 F2 의 실측 확인이다* — 어제 브리핑이 (a)의 단점을 *"배포 서버가 호스트
  llama 를 쓰는 선택지를 배제한다"* 고 적었는데 **틀렸다.** `${VAR:?}` 는 값이 있으면 그 값을
  그대로 쓰므로, 사라지는 것은 선택지가 아니라 **미설정 시의 암묵적 폴백**뿐이다. 즉 (a)의 실제
  비용은 **`.env` 에 한 줄**이다. **비용을 과대하게 적으면 오너가 잘못된 저울로 고른다.**
- *열어 둔 문*: 가드가 잠그는 방식이 "이 두 파일" 이라 **세 번째 compose 파일에는 안 따라간다**
  (원 제안이던 `_COLON_REQUIRED` 목록 일반화는 미착수). 새 override 를 더하는 사람의 자리다.
