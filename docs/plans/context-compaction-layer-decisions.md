## 결정 필요

**정본이 쌓일 때, 검색 상한 안에 "원자에 없는 지식"을 넣을 방법이 없다. 압축 층을 어떤 형태로 세울 것인가.**

중복 제거(ⓒ)를 완벽히 해도 남는 문제다. 한 인물의 궤적이 사건 40건에 흩어져 있으면 관련도 랭킹이 아무리 정확해도 상한 8은 그중 8건만 준다 — 나머지 32건이 말하는 *"이 인물이 지금 어떤 사람인가"* 는 **어느 원자에도 들어 있지 않다.** 랭킹으로 못 푸는 **층의 문제**이므로, 검색 개선과는 다른 결정이다.

## 현재 확정된 경계 (결정이 아니라 사실)

1. **압축 층은 원설계에 있었고 구현에서 빠졌다.** Agentic Search 모듈 표에 `ContextCompressor | token budget에 맞게 압축` 이 있고([`../agentic_search_flow.md:315`](../agentic_search_flow.md#L315)), 역할 목록도 *"context budget에 맞춰 압축한다"* 를 적는다([`../abstract.md:435`](../abstract.md#L435)). **구현에는 없다** — [`_apply_budget`](../../services/application/app/context_search/service.py)이 하는 것은 압축이 아니라 **절단**이다(예산을 넘는 항목을 버리고 `budget_excluded` 에 사유만 남긴다).
2. **Macro/Micro 층이 이름만 남았다.** 원설계의 `macro_context` 는 **요약 층**이다(`characters`·`locations`·`open_foreshadowings`·`timeline_constraints`·`pov_constraints`·`voice_profile`, [`../abstract.md:702-733`](../abstract.md#L702-L733)). 현재 코드는 `MACRO_NEEDS = (CURRENT_SCENE, RECENT_SCENES)` — macro 가 요약이 아니라 **위치**다. 그래서 canonical·candidate memory 는 전부 `micro_evidence` 로 들어가 **원자 단위로 상한을 두고 경쟁**한다.
3. **드릴다운 구조는 원설계에 있다.** `micro_evidence` 항목이 `source_ref` + `quote` 와 함께 `"supports": "foreshadow_black_sun_knife"` 로 **macro 항목을 가리킨다** — 요약이 진입점, 원문이 근거다.
4. **canonical 기반 need(`character_state` 등)는 Phase 4 가 명시적으로 유보했다.** `constraints`/`do_not_use` 도 *"채우는 출처 미정"* 으로 여전히 빈 tuple 이다.
5. **★ 원설계의 압축 단위는 엔티티별이고, 챕터는 압축 단위가 아니라 유효 시점·검색 범위 필터다** — `"valid_from": "chapter_04"`([`../abstract.md:1313`](../abstract.md#L1313)) · *"아린은 chapter_08 이전에는 레온의 배신을 알지 못한다"*([`../abstract.md:1328`](../abstract.md#L1328)) · *"chapter/scene 범위 검색"*. **D2 는 이 지점에서 원설계와 갈라진다**(사유는 D2 에 적는다). 다음 사람이 문서와 구현의 불일치를 결함으로 오해하지 않도록 여기 남긴다.
6. **Context Gate 는 모든 item 을 SOT 에서 재검증한다.** 그런데 요약은 **여러 정본의 함수**라 단일 pointer 로 재검증이 안 된다 — 어느 안을 골라도 D4 를 풀어야 하는 이유다.
7. **장은 metadata-only 다**(chapter-scene D=A). 그 결정이 거절한 것은 *"장 서문·요약을 **본문처럼 직접 쓰는** 흐름"* 이다. **재생성 가능한 파생 압축본은 산문 정본이 아니므로 그 결정과 충돌하지 않는다** — 다만 이름이 겹치면 다음 사람이 혼동하므로 압축본은 `chapter_synopsis`(작가가 쓰는 것) 가 아닌 별도 이름을 쓴다.
8. **실측(2026-09-09): `ai_writing_system.memories` 0건.** 분석 파이프라인이 실데이터로 아직 한 번도 안 돌았다. 요약 품질을 잴 데이터가 없다는 것이 D1 의 "트리거" 근거다.

## ✅ D1 — 압축본의 지위 · 시점 (오너 확정 2026-09-09: **파생 층 + 트리거**)

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **파생 층 + 트리거** ✅ | 재생성 가능한 파생으로 설계하고, 구현은 트리거가 올 때 연다 | 요약이 틀려도 재생성으로 고친다 · *"Mongo 가 정본, 파생 인덱스는 단방향"* 원칙과 정합 · 데이터 0건에서 품질 상수를 추측하지 않는다 | 도그푸드 초기에는 층이 없는 채로 돈다 |
| 파생 층 + 지금 구현 | 같은 설계를 이번에 바로 구현한다 | 도그푸드 시작과 동시에 효력 | 요약 품질을 잴 데이터가 0건 — 프롬프트·임계·길이가 전부 추측이 되고 실데이터로 다시 고칠 공산이 크다 |
| 정본 승격 | 요약도 승인 대상 canonical memory 의 한 종류로 만든다 | 사람이 검토해 품질 보장 · 근거 추적 일관 | **LLM 요약 오류가 정본에 영구히 박힌다** · 원자가 바뀔 때마다 요약 정본이 낡아 supersede 폭포가 생긴다 · 승인 부담 |
| 압축 안 함 | 랭킹·상한·예산 조정으로 버틴다 | 구현 0 | *"원자에 없는 지식"* 은 영원히 못 만든다 — 이 브리프의 문제가 그대로 남는다 |

**확정 근거**: 요약은 LLM 산출이라 틀릴 수 있다. 파생이면 재생성으로 고쳐지고 정본이면 오염이 영구화된다. 그리고 지금 데이터가 0건이라 품질 상수를 정직하게 고를 수 없다 — 이는 2B.6 D4=A·auto-promotion D2=B 가 이미 두 번 내린 판단(*"추측값으로 canon 을 만들지 않는다"*)과 같은 형태다.

## ✅ D2 — 압축 단위 (오너 확정 2026-09-09: **챕터 기준 1차 압축 + 드릴다운**)

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 엔티티별 (원설계) | 인물·장소·떡밥마다 프로필 요약을 만든다 | *"이 인물은 지금 어떤 사람인가"* 를 **한 항목**이 답한다 · 개수가 엔티티 수(수십)로 묶여 작다 | **원고가 한 줄 늘 때마다 낡는다** — 해당 인물이 나온 장면을 쓸 때마다 stale · 파생 캐시가 거의 항상 갱신 대기 · 시점을 평평하게 만든다(ch2 의 참이 ch9 엔 거짓) |
| **챕터별** ✅ | 각 memory type 마다 챕터 단위 압축본을 만들고, 검색은 압축본을 먼저 보고 필요할 때 원자로 드릴다운 | **장이 닫히면 거의 안 바뀐다** — 원고가 append-only 라 과거 장이 안정적이고, 파생의 **재생성 비용이 압도적으로 싸다** · 시간축·POV 제약과 정합 · 작가의 작업 리듬과 맞음 | **주체축을 압축하지 못한다** — 한 인물을 알려면 여러 장 요약을 읽어야 한다 · **장 수가 원고와 함께 선형으로 는다**(장 요약만으로 예산을 넘는 지점이 온다) |
| 둘 다 지금 | 챕터 + 엔티티 두 층을 함께 만든다 | 두 축을 모두 덮는다 | 데이터 0건에서 층을 둘 만든다 — §2 단순성 위반 |

**확정 근거**: D1 이 파생으로 정해진 이상 **재생성 빈도가 곧 비용**이고, 그 축에서 챕터가 엔티티를 압도한다. 엔티티 프로필은 매 장면마다 낡지만 챕터 요약은 장이 닫히면 안정적이다. 이 논거는 원설계 문서에 없다 — 원설계는 압축본을 파생으로 규정한 적이 없기 때문이다.

**남는 구멍과 그 처리**: 챕터별은 주체축을 못 덮는다(위 표의 단점). **엔티티 태그로 잇는다** — 각 챕터 압축본이 자기가 언급한 엔티티를 태그로 들고 있으면, "아린" 질의 → 아린이 태그된 장 요약들 → 드릴다운으로 원자, 가 성립한다. 주체축 롤업(2차 압축)은 D5 의 트리거로 미룬다. **3단을 지금 만들지 않으면서 문도 닫지 않는다.**

## ✅ D3 — 압축본을 언제 만드는가 (오너 **B** 채택 · **시점 정정 확정** 2026-09-09)

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 장이 닫힐 때 | 챕터의 마지막 Scene 이 최종 저장되면 그 장의 압축본을 만든다 | 트리거가 구조적이고 1회로 끝난다 · D2 의 "장은 안정적" 전제와 정확히 맞는다 | "장이 닫혔다"는 상태가 아직 없다(Scene 최종화는 있으나 장 최종화는 없다) — 새 상태를 열어야 한다 |
| B. 분석 완료마다 | 분석 job 이 끝나면 그 snapshot 이 속한 장의 압축본을 재생성한다 | 기존 트리거(final-save D4=A)를 재사용 — 새 상태가 필요 없다 | 장 안의 장면을 고칠 때마다 재생성 — 장이 닫히기 전엔 낭비가 크다 |
| C. 임계 초과 시 lazy | 검색이 "원자가 상한을 넘겼다"를 만난 뒤에야 만든다 | 필요한 장만 압축한다 — 비용 최소 | 첫 요청이 느려진다(검색 경로에 LLM 호출이 들어온다) · 검색 지연 계약을 건드린다 |
| D. 검색 시점 매번 | 요청마다 그 자리에서 압축한다 | 항상 최신 | 매 요청 LLM 호출 — 비용·지연 모두 최악이고 캐시의 이점을 버린다 |

**오너 확정 — B.** 근거: A 를 쓰려면 *"장이 닫혔다"* 를 시스템이 알아야 하는데 그것은 **장 개수를 미리 지정하게 만들고**, 장을 고쳤을 때의 **재분석 버튼까지 함께 열어야 한다**. 압축본 하나의 컨텍스트가 크지 않다는 전제라면 모아서 한 번에 하는 것보다 **그때그때 갱신**이 맞고, 바뀐 것이 없으면 건너뛰면 된다.

**★ 그런데 "분석 완료"는 정본을 만들지 않는다 — 트리거를 한 칸 옮겨야 한다.** 분석이 만드는 것은 `needs_review` **후보**이고 canonical memory 는 승인(promote/apply)에서 생긴다. auto-promotion 은 **기본 off** 이며(`memory/service.py` `evaluate_auto_promotion` — *"Off by default (None)"*) **이 머신에도 `MEMORY_AUTO_PROMOTION_THRESHOLD` 가 미설정**이다(실측 2026-09-09). 그래서 B 를 글자 그대로 구현하면 ① 분석 완료 시점에는 **아직 아무것도 안 바뀐 채로 재생성**하고 ② **정본이 실제로 느는 승인 시점에는 아무 일도 안 일어난다.**

**정정 확정(오너 2026-09-09) — 트리거는 "정본이 바뀔 때"(승인/apply 완료)다.** 오너 의도(*"모아서 하지 말고 그때그때, 중복이면 패스"*)는 그대로 보존되고 오히려 정확해진다. *"분석 완료마다"* 는 이 정정으로 **대체된다** — 구현이 분석 완료를 트리거로 삼으면 안 된다.

**그리고 그 결과 D3 은 D4 에 흡수된다 — 이것이 이 결정의 최종 형태다.** D4=A 는 압축본이 source memory version 집합을 들고 하나라도 superseded 면 stale 로 본다 — 정본이 바뀌면 집합이 어긋나 stale → 재생성, 안 바뀌면 stale 이 아니라 그냥 넘어간다(= *"중복이면 패스"* 가 공짜로 나온다). **별도 트리거를 둘 필요가 없고 D4 의 stale 판정이 곧 D3 이다.** 구현 시 이 형태를 취한다.

## ✅ D4 — 압축본의 stale 규칙 (오너 **A** 채택 2026-09-09)

Gate 는 item 을 SOT 에서 재검증하는데(경계 6) 요약은 여러 정본의 함수라 단일 pointer 로는 재검증이 안 된다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. source version 집합 | 압축본이 자기를 만든 memory id 와 **그 version** 집합을 들고, 하나라도 superseded 면 stale | 정확하다 · 기존 `MemoryStatus.SUPERSEDED` 를 그대로 쓴다 | 집합이 커지면 검증 비용이 는다 · 재생성이 잦아질 수 있다 |
| B. 장 단위 content_hash | 그 장의 snapshot content_hash 가 바뀌면 stale | 싸다 · source block 쪽 stale 규칙과 같은 모양 | 원고가 안 바뀌어도 **정본이 바뀌면**(승인·수정) 못 잡는다 |
| C. TTL·무검증 | 오래되면 버리고 재생성, 정합성은 안 본다 | 가장 싸다 | 낡은 요약이 근거로 실린다 — Gate 의 존재 이유를 부정한다 |

**오너 확정 — A.** 압축본은 **정본의 함수**이므로 정본의 변화를 봐야 한다. B 는 원고 축만 보므로 *"정본이 바뀌었는데 요약이 그대로"* 를 놓친다. 비용이 문제가 되면 집합을 통째로 비교하는 대신 **최대 version 값 하나**로 좁히는 최적화가 가능하지만 그건 실측 뒤에 정한다. **D3 의 정정에 따라 이 판정이 재생성 트리거를 겸한다.**

## ✅ D5 — 엔티티 태그와 주체축 롤업 (오너 **A 선 · B 후속 고려** 2026-09-09)

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 태그만, 롤업은 트리거 유예 | 챕터 압축본이 엔티티 태그를 들고, 주체축 롤업은 나중에 | 지금 만드는 것이 최소 · 주체축 질의가 그럭저럭 성립한다 | 장이 많아지면 태그된 장 요약도 예산을 넘는다 |
| B. 태그 + 롤업 동시 | 챕터 압축본 위에 엔티티 롤업 층을 함께 만든다 | 주체축이 한 항목으로 닫힌다 | 데이터 0건에서 층 둘 — D2 에서 이미 기각한 형태 |
| C. 태그도 안 단다 | 챕터 압축본만 만든다 | 가장 작다 | 주체축 질의가 **아무 경로도 없다** — 이 브리프의 원 문제가 절반 남는다 |

**오너 확정 — A 를 먼저 하고 B 를 후속 고려로 연다.** 태그는 압축본을 만들 때 거의 공짜로 나온다(요약 대상 memory 들의 scope 를 모으면 된다). 오너가 B 를 닫지 않은 이유: **주체축을 한 항목으로 닫아 두는 편이 나중 관리에 낫다**는 판단이다. 롤업 트리거: **한 엔티티에 태그된 챕터 압축본이 예산 안에 안 들어가기 시작할 때.**

## ✅ D6 — 구현 트리거 (오너 **상한 기준 · 16건** 2026-09-09)

트리거 없는 유예는 망각이다(선례: K-3 ⓐ 가 트리거 문장으로 살아남았다).

**오너 확정 — 한 프로젝트의 canonical memory 총계가 16건을 넘는 순간.** 근거: 이 기획에서는 항목이 랭킹에 뜨더라도 **드릴해서 들어가야** 하므로, 검색 상한(현재 need 당 8)을 넘기 시작하면 이미 압축 층이 할 일이 있다. 16 은 그 상한의 **2배** — 랭킹이 무엇을 고르든 절반 이상이 잘리기 시작하는 지점이다.

**단위를 못박는다: 프로젝트의 canonical memory 총계**(타입당도, 장당도 아니다). 세 해석이 크게 다르므로 값만 적으면 다음 사람이 다르게 읽는다.

**이 값이면 도그푸드 시작 직후 거의 즉시 발화한다** — 실측 2026-09-09 기준 정본 0건이지만 `source_blocks` 는 이미 640건이고, 장면 하나가 후보 여럿을 낳는다. D1 의 *"트리거가 올 때"* 는 따라서 사실상 **"첫 실데이터가 생기자마자"** 를 뜻한다. 모순이 아니라 의도다 — 데이터 0건인 지금은 품질 상수를 못 고르므로 안 만들고, 잴 것이 생기는 즉시 연다.

보조 트리거(먼저 오면 그것이 이긴다): **오너가 "AI 가 앞 내용을 잊었다"를 실제로 만나는 순간.** 이 시스템의 존재 이유가 그것이다.

## ✅ D7 — `constraints`/`do_not_use` 를 같은 슬라이스에 넣는가 (오너 **포함** 2026-09-09)

원설계의 `do_not_use`(*"아린은 아직 레온의 배신을 모른다"* · *"검은 태양단의 정체는 아직 공개하지 않는다"*)는
**요약이 아니라 제약**이다. Phase 4 가 *"채우는 출처 미정"* 으로 남겨 `constraints`/`do_not_use` 는 지금도 항상
빈 tuple 인데, **챕터 압축본이 그것을 아는 첫 번째 자리**다(장 유효 시점 정보를 이미 들고 있다).

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **포함** ✅ | 압축 층 슬라이스가 `do_not_use` 까지 채운다 | *"초반에 정한 규칙을 끝까지 지킨다"* 가 이 층의 목적에 이미 들어 있다 — 나눠 열면 **압축본이 아는 것을 쓰지 못하는 기간**이 생긴다 · Phase 4 가 남긴 빈 칸이 닫힌다 | 슬라이스가 커진다 · 경계를 그어야 한다(아래) |
| 분리 | 압축 층을 먼저 열고 제약은 뒤에 | 각 슬라이스가 작다 | 같은 데이터를 두 번 훑는다 · 압축본이 제약을 알면서 안 쓰는 상태가 남는다 |

**확정 근거(오너)**: 압축 층이 노리는 것이 *"길어져도 초반 규칙·지시사항을 끝까지 준수"* 인데, 그 절반인 제약을
빼면 층을 만들고도 목적을 반만 이룬다.

### ✅ D7 경계 — **(a) 아는 범위 안에서, 세 축**(오너 2026-09-09)

**(a) 를 채택한다** — 원설계의 `pov_constraints`·`timeline_constraints` 라는 **별도 기계를 들여오지 않는다.** 대신
`do_not_use` 를 **세 축**으로 만들고, 셋 다 이 저장소의 같은 파이프라인(분석 추출 → 사람 승인 → 정본 → 압축)에서
나오게 한다.

| 축 | 무엇 | 산출 | 읽기 |
|---|---|---|---|
| **시점** | 지금 위치까지 무슨 일이 있었나 | 챕터 압축본 | 현재 위치까지의 장 |
| **공개 의도** | *"검은 태양단의 정체는 아직 공개하지 않는다"* | `open_question` 정본 | 같음 |
| **인물 지식** | *"아린은 아직 레온의 배신을 모른다"* | `character_observation` 정본 | **버전 체인**을 걸어 그 장 시점의 버전 |

**★ "아는 범위" 는 *최신까지* 가 아니라 *현재 집필 위치까지* 다.** `do_not_use` 에서 최신은 오히려 독이다 — 9장에서
아린이 배신을 알게 됐는데 5장을 쓰면서 그 최신을 실으면, 압축 층이 막으라고 만든 누설을 압축 층이 일으킨다.
**D2(챕터 단위)가 이것을 공짜로 푼다** — 챕터 경계가 곧 시점이라, 현재 위치까지의 압축본만 읽으면 그 범위의
"최신" 이 자동으로 그 시점의 정답이 된다. 재료도 서 있다: 요청에 `current_position` 이 오고 `Draft.chapter_id` 가
있다(지금 검색은 위치로 거르지 않는다 — 그 필터가 이 슬라이스의 일부다). **D2 를 고를 때 이 배당은 못 봤다** —
그때 근거는 재생성 비용이었다.

**★ 인물 지식 축은 저장 제약이 하나 더 있다.** 인물 scope key 가 **정규화 이름**이라(`memory/scope.py` `derive_scope`)
**인물 하나 = 정본 하나**이고 모든 관찰이 한 엔트리로 모여 `update` 로 덮인다. 그래서 *"5장의 아린"* 과
*"9장의 아린"* 이 정본에 동시에 존재할 수 없다. 더 나쁜 것은 `_versioned_upsert` 가 새 버전에
`analysis_job_id = candidate.job_id` 를 박으므로 **인물 정본이 갱신될 때마다 최신 장으로 이사한다** — 인물 메모리의
장 귀속은 엔트리 단위로는 불안정하다.

**그런데 데이터는 이미 있다.** 저장이 append-only 라 이전 버전이 `SUPERSEDED` 로 보존되고, **각 버전이 자기
`analysis_job_id` 를 들고 있어** `job → snapshot_id → SourceSnapshot.draft_id → Draft.chapter_id` 로 장이 유도된다
(2026-09-09 실측 확인). 즉 **버전 체인이 곧 장별 인물 상태 이력**이고 버전 N 이 "그 장 시점의 아린" 이다.

따라서 이 축이 요구하는 것은 하나뿐이다 — **압축 층이 canonical 만 보지 않고 버전 체인을 걷는 읽기 경로.**
그것은 **압축 층만 필요하므로** 기존 canonical-only 계약(일반 검색은 최신만 본다)을 건드리지 않는다.

**비용을 정직하게 적는다**: 앞의 두 축은 *"장 귀속 규칙만 풀면 끝"* 인데 **인물 지식 축은 버전 체인 읽기 경로가
추가로 필요하다.** 슬라이스가 그만큼 커진다.

**부수 소득 — 장 귀속 숙제의 답이 반쯤 나왔다**: 인물 메모리의 장 귀속은 **엔트리가 아니라 버전 단위**여야 한다
(아래 "후속 고려" 의 (a)/(b)/(c) 중 사실상 (c) 에 가까운 답이며, 새 필드 없이 기존 버전 이력으로 성립한다).

## 후속 고려 (문을 열어 둘 것)

- **`MACRO_NEEDS` 는 확장 지점이다.** 압축본은 macro 로 실리고 원자는 micro 로 남아야 원설계의 드릴다운이 성립한다 — 지금처럼 모든 memory 가 micro 로 가면 압축본이 원자와 같은 8칸을 두고 경쟁한다.
- **`constraints`/`do_not_use` 는 이 층의 슬라이스에 포함된다 — D7 로 확정됐다**(아래).
- **ⓒ 배선(후보 정체성 그룹)과 충돌하지 않는다.** ⓒ 는 승인 **전** 후보 축이고 압축은 승인 **후** 정본 축이다. 다만 ⓒ 가 중복을 줄이면 압축 대상 원자도 줄어 트리거가 늦춰진다.
- **★ 정본은 자기가 어느 장 소속인지 모른다 — D2 의 숨은 전제다.** `MemoryEntry` 에 chapter 축이 없다(필드: id·project_id·memory_type·status·provenance·confidence·source_ref_ids·payload·version·analysis_job_id·source_candidate_id·promotion_mode·applied_threshold·scope·supersedes). 유도는 된다 — `Draft.chapter_id` 가 있으므로([`../../services/application/app/core_sot/models.py:85`](../../services/application/app/core_sot/models.py#L85)) `memory → analysis_job_id → snapshot_id → draft → chapter_id` 경로가 선다. 두 가지가 걸린다: ① **4단 조인**이고 ② `add_evidence` 가 여러 장의 `source_ref` 를 union 하면 **한 정본이 여러 장에 걸쳐** 장 경계가 흐려진다. 구현 전에 귀속 규칙을 정해야 한다 — 대략 (a) 최초 관측 장에 귀속 (b) 걸친 모든 장에 중복 등장 (c) memory 에 chapter 스냅샷 필드를 더한다. **지금 정하지 않는다.**
