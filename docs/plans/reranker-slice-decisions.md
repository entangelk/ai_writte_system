# Decision brief — 뉴럴 리랭커 슬라이스

> 작성 2026-08-14. **오너 결정 대기.** 부모 결정은 [`external-api-expansion-decisions.md`](external-api-expansion-decisions.md) D1·D5(2026-07-27)이고, 이 문서는 **그 결정을 뒤집지 않는다** — D5 가 정하지 않고 남긴 **순서·삽입 방식·완료 기준**을 정한다.

## 결정 필요

**리랭커 슬라이스를 지금 여는가. 연다면 self-host(B)와 외부 seam(C) 중 무엇을 먼저 만들고, 파이프라인 어디에 어떤 모양으로 끼우며, 무엇을 보고 "좋아졌다"고 판정하는가.**

D5 는 *"B + C 를 별도 슬라이스로"* 까지 정했다. 정하지 않은 것이 넷이고, 그 넷이 지금 구현을 막는다.

---

## 배경 — 지금 무엇이 있고 무엇이 없는가 (2026-08-14 코드 실측)

**없는 것: 리랭커 전부.** `services/` · `scripts/` · `tests/` · `frontend/src/` 전수에서 `rerank` · `re-rank` · `cross-encoder` · `bge-reranker` **0건**이다. 어댑터가 없는 것이 아니라 **기능 자체가 0줄**이다.

**있는 것: RRF 융합.** 지금 "리랭킹"이라 부르는 것은 [`context_search/service.py:277`](../../services/application/app/context_search/service.py#L277) 의 `DEFAULT_RRF_K = 60` 이며, 벡터·lexical 두 랭킹을 `1/(k + rank)` 로 합쳐 재정렬한다. **신경망 재채점이 아니다** — 두 순위의 합의를 보는 것이지 질의-문서 쌍을 다시 읽는 것이 아니다.

**융합이 일어나는 자리는 정확히 둘이다.**

| 클래스 | 정의 | 융합 반환 | 무엇을 랭킹하나 |
|---|---|---|---|
| `HybridCanonicalMemoryRetriever` | [:280](../../services/application/app/context_search/service.py#L280) | [:323](../../services/application/app/context_search/service.py#L323) | 정본 memory |
| `HybridCandidateMemoryRetriever` | [:496](../../services/application/app/context_search/service.py#L496) | [:538](../../services/application/app/context_search/service.py#L538) | 검토 대기 candidate |

둘 다 seam 이 **동일**하다 — `retrieve(*, project_id: str, query: str, limit: int)`. 그리고 그 모양은 이미 Protocol 로 선언돼 있다(`CanonicalMemoryRetriever` [:131](../../services/application/app/context_search/service.py#L131) · `CandidateMemoryRetriever` [:329](../../services/application/app/context_search/service.py#L329)). 조립은 [`main.py:1009`](../../services/application/app/main.py#L1009)·[`:1069`](../../services/application/app/main.py#L1069) 두 곳이다.

**이 대칭이 이 슬라이스의 가장 큰 자산이다** — 붙일 자리가 둘이고 둘의 계약이 같다.

## 이미 확정된 것 (다시 정하지 않는다)

- **D5 = B + C.** 로컬 기본은 self-host `dragonkue/bge-reranker-v2-m3-ko`, 동시에 외부 리랭커 API 도 붙을 수 있게 `RerankProvider` seam 을 뚫는다. 오너: *"로컬에는 이거 쓰고, 외부꺼도 쓸 수 있게 뚫어놓기."*
- **D1 = 별도 슬라이스**, 순서는 *"LLM 슬라이스 → 임베딩 슬라이스 → 리랭커 슬라이스"*.
- **삽입 지점 = RRF 결과 뒤, `retrieve()` seam 다음**(D5 본문).
- **D2 = generic OpenAI 호환 우선** · **D3 = env 기반 키.**

## ★ 2026-08-14 에 새로 생긴 긴장

배포 서버 방향(D-10.5-d/g)이 *"모델 다운로드 0 · 외부 API 전용"* 으로 정해졌고, 오늘 [`docker-compose.external.yml`](../../docker-compose.external.yml) 이 그것을 시행했다. 그런데 **D5 의 로컬 기본(B, self-host)은 torch 로 모델을 받는 서비스를 하나 더 만드는 일**이다 — 오늘 `embedding` 을 profile 뒤로 보낸 바로 그 종류다.

**모순은 아니다**(로컬과 배포는 원래 다른 구성이다). 다만 **순서가 실제로 의미를 갖게 됐다** — 무엇을 먼저 만드느냐에 따라 배포 서버가 완성되는 시점이 달라진다. D5 를 정할 때(2026-07-27)는 배포 서버 방향이 없었다.

## 결정 1 — 지금 여는가, 임베딩 어댑터가 먼저인가

D1 이 기록한 순서는 **LLM → 임베딩 → 리랭커**다. 현재 진척은 이렇다.

| 축 | 상태 |
|---|---|
| LLM | **어댑터 있음** — gateway 가 OpenAI 호환 `/v1/chat/completions` 를 부른다. 외부 API 그대로 붙는다 |
| 임베딩 | **어댑터 없음** — `RemoteEmbeddingProvider` 가 아는 계약은 우리 서비스의 자체 형식(`POST /embed {"text": …}`)이라 OpenAI 형식(`/v1/embeddings`)에 못 붙는다 |
| 리랭커 | **기능 자체가 0줄** |

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 임베딩 어댑터 먼저(기록된 순서 유지)** | 리랭커는 그다음 | **배포 서버가 먼저 완성된다**(지금 임베딩이 유일하게 막고 있다) · D1 순서 그대로 · 슬라이스가 작다 | RAG 정교화가 한 슬라이스 더 미뤄진다 |
| B. 리랭커 먼저 | 임베딩 어댑터는 그다음 | 검색 품질을 먼저 본다 · 오너 관심이 지금 여기 있다 | 배포 서버는 여전히 못 뜬다 · **평가할 실사용 질의가 아직 없다**(아래 결정 4) |
| C. 둘 다 한 슬라이스 | 임베딩 어댑터 + 리랭커 | 외부화가 한 번에 끝남 | 성격이 다른 둘을 섞는다 — D1 이 "축마다 wire 계약·실패 모드·조달이 달라 섞으면 안 된다" 고 이미 기각한 형태 |

**추천: A.** 두 가지 이유다. ① **배포 서버를 막는 것은 임베딩 하나뿐**이다 — 리랭커를 먼저 만들어도 배포 서버는 안 뜬다. ② **리랭커는 "만들면 끝"이 아니다** — D5 본문이 오프라인 평가(*"리랭킹이 실제로 Gate 품질을 올리는지"*)를 완료 조건으로 적었는데, dogfood(GATE-1)를 아직 시작하지 않아 **평가할 실사용 질의가 없다.** 평가 없이 붙이면 품질이 올랐는지 내렸는지 모른 채 파이프라인 단계만 늘어난다.

> **다만 이것은 강한 추천이 아니다.** 리랭커를 먼저 열어도 잃는 것은 순서뿐이고, 아래 결정 2~4 는 그대로 유효하다.

## 결정 2 — self-host(B) 먼저인가 외부 seam(C) 먼저인가

D5 는 둘 다 하기로 했고 순서를 안 정했다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. seam + 외부 어댑터 먼저(C)** | `RerankProvider` 를 뚫고 외부 API 어댑터 하나. **로컬 기본은 no-op**(= 지금 동작 그대로) | 배포 서버 방향과 정합 · 모델 0 유지 · 슬라이스가 가장 작다 · seam 이 서면 self-host 는 **어댑터 하나 추가**로 끝난다 | 외부 리랭커 키가 없으면 실제 효과를 못 본다 · "로컬 기본" 이라는 D5 문언과 순서가 반대 |
| B. self-host 먼저 | `bge-reranker` 컨테이너를 embedding 과 같은 패턴으로 | D5 문언 그대로 · per-call 비용 0 · 키 없이 지금 당장 측정 가능 | **torch 서비스가 하나 더 는다**(오늘 방향과 역행) · GPU 사정이 머신마다 다름(알파 3060 12GB · 베타 1060 3GB · 감마 없음) · **CPU 추론 지연 미측정** |
| C. 동시 | seam + self-host + 외부 어댑터 | 완결 | D5 가 *"슬라이스가 크게 부푼다"* 로 이미 기각한 형태 |

**추천: A.** seam 이 먼저 서면 B 와 C 가 **대칭적으로 얹힌다** — 그것이 D5 가 seam 을 요구한 이유다. 그리고 이 저장소에는 이미 같은 형태의 선례가 있다: 임베딩이 `EmbeddingProvider` Protocol 뒤에 `RemoteEmbeddingProvider` 와 `DeterministicFakeEmbeddingProvider` 를 나란히 두고, **env 유무로 조립에서 고른다.**

**★ 다만 B 를 먼저 할 실질적 이유가 하나 있다 — 측정.** 외부 키가 없으면 A 로는 *"붙는다"* 만 확인되고 **품질도 지연도 못 잰다.** 오너가 키를 곧 받을 계획이면 A, 아니라면 B 가 실측을 앞당긴다.

## 결정 3 — 어떤 모양으로 끼우는가

seam 이 `retrieve()` 라는 것은 정해졌지만, **코드 모양**은 세 가지가 가능하다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. retriever 데코레이터** | `RerankingRetriever(inner, provider)` 가 `CanonicalMemoryRetriever` Protocol 을 만족하고, 조립 지점(`main.py:1009`·`:1069`)에서 감싼다 | **도메인 코드 0줄 변경** · 두 자리에 같은 것을 씌운다 · 이 저장소가 이미 쓰는 패턴(`ObservedProvider` 계측) · 끄면 완전히 사라진다 | 조립에서 빠뜨리면 조용히 미작동 — **`ObservedProvider` 가 정확히 그 사고를 냈다**(조립 가드가 처방) |
| B. Hybrid 클래스 내부 | `HybridCanonicalMemoryRetriever` 안에서 융합 뒤 재채점 | 자리가 명시적 | **두 클래스에 같은 코드가 복제**된다 · 리랭커를 끄려면 분기가 생긴다 · Hybrid 가 아닌 경로(vector-only·lexical-only)는 리랭킹을 못 받는다 |
| C. 호출부에서 | context search 서비스가 `retrieve()` 결과를 받아 재채점 | 파이프라인이 한눈에 보임 | 호출부가 여러 곳이라 **누락이 조용하다** · 두 retriever 계열 각각에 손이 간다 |

**추천: A(데코레이터).** 이유 셋이다. ① 두 융합 자리의 seam 이 **이미 같아서** 한 데코레이터가 둘 다 덮는다. ② **vector-only·lexical-only 구성에서도 리랭킹이 걸린다** — B 는 hybrid 에만 걸려 구성에 따라 동작이 갈린다. ③ **끄기가 조립에서 끝난다**(감싸지 않으면 없다) — 배포 서버에서 리랭커를 빼는 것이 env 한 줄이 된다.

**★ A 를 고르면 조립 가드가 함께 간다.** 이 저장소는 *"감싸기를 빠뜨려도 스위트는 green 이고 배포에서만 계측이 사라지는"* 사고를 `ObservedProvider` 로 이미 겪었고, 처방이 **조립 가드(리터럴까지 단정)** 였다. 리랭커도 같은 형태의 위험을 갖는다 — 감싸기를 빠뜨리면 **검색이 조용히 예전 품질로 돌아간다.**

## 결정 4 — 완료 기준: 무엇을 보고 "좋아졌다"고 하는가

D5 본문이 *"리랭킹이 실제로 Gate 품질을 올리는지"* 오프라인 평가를 요구한다. **그 기준이 정해진 적은 없다.**

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 배선만 검증, 품질 평가는 dogfood 뒤** | 리랭커가 순서를 바꾸는가 · 끌 수 있는가 · 실패해도 검색이 죽지 않는가만 잠근다 | 지금 실제로 가능한 유일한 것 · 슬라이스가 닫힌다 | *"좋아졌는가"* 에 답을 못 한 채 기능이 배포된다 |
| B. 소규모 수기 평가셋 | 질의 20~30개에 정답 memory 를 손으로 붙여 리랭킹 전후 비교 | 숫자가 나온다 | **평가셋을 만드는 것이 슬라이스보다 클 수 있다** · 손으로 만든 정답은 편향된다 |
| C. dogfood 실사용 질의 축적 후 평가 | GATE-1 이후 실제 질의로 | 가장 정직 | 리랭커 슬라이스가 dogfood 에 종속된다 |

**추천: A + C.** 이번 슬라이스는 **배선·안전성만** 잠그고(끌 수 있는가 · 실패가 검색을 죽이지 않는가 · 순서가 실제로 바뀌는가), **품질 판정은 dogfood 뒤로 명시적으로 미룬다** — 트리거와 함께 적으면 그것은 망각이 아니다. **B 를 권하지 않는 이유**: 이 저장소는 `analysis_extract` 프롬프트를 손으로 핀했다가 데인 선례가 있고, 손으로 만든 20개 정답셋은 *"측정했다"* 는 착각만 준다.

**★ 그러나 A 를 고르면 정직하게 적어야 한다** — 리랭커가 붙었다는 사실이 *"검색이 좋아졌다"* 를 뜻하지 않는다. README·포트폴리오 표기는 **"cross-encoder 리랭커 있음, 품질 평가는 미실시"** 가 정확하다(현행 표기 규칙 = 추적 부채의 *"코드가 붙기 전까지 '있음'으로 쓰면 거짓"* 과 같은 계열).

## 후속 고려 — 이 결정이 열어 둬야 하는 문

- **`docker-compose.external.yml` 에 리랭커 자리가 생긴다.** self-host 리랭커는 모델을 받으므로 `embedding` 과 같이 profile 뒤로 가야 한다. 오너 지시 *"모델 업로드 되는 것들은 다 넣자"* 가 그때 실행된다 — **지금 env 를 미리 만들지 않은 것은 의도다**(아무도 읽지 않는 변수는 그것이 붙어 있다는 착각을 만든다).
- **env 표기는 코드가 그 변수를 읽는 방식과 짝**이다(2026-08-14 에 배운 규칙). `if not os.environ.get(x)` 면 dash `${VAR-기본}`, `os.environ.get(x, DEFAULT)` 면 콜론 `${VAR:-기본}`.
- **D4(call-site 별 provider 오버라이드)는 설계만 열어 두기로 이미 결정**됐다 — 리랭커 seam 도 전역 기본 하나로 시작한다.
- **관측(KPI)에 리랭커를 넣을지**는 별개 판단이다. 지금 `LlmCallSite` enum 은 **LLM 어댑터 8종**이고 리랭커는 LLM 호출이 아니다 — 넣으려면 그 정의부터 바뀐다.

## 유예 / 범위 밖 — 이 브리프가 정하지 않는 것

- **리랭커 품질 평가셋** — 결정 4=A+C 면 dogfood 이후. 트리거 = GATE-1 착수.
- **모델 크기·지연 실측** — `bge-reranker-v2-m3-ko` 의 VRAM·CPU 추론 지연을 **아직 아무도 안 쟀다.** 결정 2 에서 B(self-host)를 고르면 그것이 슬라이스의 첫 작업이다. 감마(GPU 없음)에서 돌아가는지도 그때 답이 나온다.
- **리랭킹 대상 개수(top-k)** — 융합 결과 전부를 재채점할지 상위 N 개만 할지. 지연이 여기 비례하므로 **실측 뒤에 정한다.**
- **Anthropic·Cohere 전용 어댑터** — D2=A 대로 generic 이후 additive.
- **candidate 쪽에도 리랭킹을 걸지** — 두 융합 자리 중 정본만 걸지, 검토 대기 candidate 에도 걸지는 **결정 3=A 를 고르면 조립에서 한 줄로 갈린다.** 지금 정할 필요가 없어 남긴다.

## 승인 전 보류

이 문서의 결정 1~4 가 확정되기 전에는 **코드를 쓰지 않는다.** 특히 결정 3 은 잘못 고르면 되돌리는 비용이 크다(B 를 골랐다가 A 로 옮기면 두 클래스에서 걷어내야 한다).
