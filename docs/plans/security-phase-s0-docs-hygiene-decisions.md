## Decision needed

**공개 저장소에 남은 실제 사설 주소(2대의 llama.cpp 호스트 + 배포 호스트 LAN IP)와 평문 비밀번호를, *어느 파일 계열까지* 고쳐 쓰는가.**

선례에서 유도되지 않는 이유가 **셋**이다.

1. **저장소 안에 충돌하는 두 규칙이 있다.**
   - [`HANDOFF.md:4`](../../HANDOFF.md) — *"원격 배포 대상의 IP·호스트명…을 `HANDOFF.md`·`docs/daily_logs/`·`docs/verifications/`·`CHANGELOG.md` 등 저장소 문서에 기록하지 않는다."* → **이력 계열을 명시적으로 지목한다.**
   - [`HANDOFF.md`](../../HANDOFF.md) 표준 제약(제품명 D5) — *"★ 이력 문서는 대상이 아니다 — `HANDOFF.md`·`CHANGELOG.md`·`docs/` 에 옛 이름이 남는 것은 맞다(그것이 그때의 사실이다)."* → **같은 파일 계열을 명시적으로 면제한다.**

   두 규칙은 서로 다른 축(보안 / 표시명)에 대한 것이지만 **대상 파일 목록이 같다.** 어느 쪽이 이 축에서 canonical 인지는 오너만 정할 수 있다.

2. **히트의 87%가 독립 검증 기록과 작업 로그다** — 그중에는 **이 발견을 만든 감사 기록 자신**도 있다. 감사 기록을 고쳐 쓰면 *발견의 근거가 발견 문서에서 사라진다.*

3. **재유입 방지 가드의 폭이 곧 앞으로의 마찰**이다. 테스트 픽스처가 일부러 사설 대역을 쓰고(`192.168.1.50`·`10.9.x`·`172.19.x`) 계약 literal 에도 사설 CIDR 이 있어(`172.16.0.0/12`·`127.0.0.0/8`), 광의 정규식은 **정상 코드를 문다**.

## D1 — 스윕 범위: 어느 파일 계열까지 고쳐 쓰는가

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 살아 있는 것만** | `docs/plans/` · `system-contract-sot.md` · `scripts/` 만 고친다. `CHANGELOG.md`·이력 계열은 그대로 | 이력 보존 원칙과 충돌 0. 변경 10파일 미만이라 리뷰가 싸다 | **134히트 중 18만 걷힌다.** "공개 저장소 보안 규칙"이 명시적으로 지목한 `daily_logs`·`verifications`·`CHANGELOG` 가 통째로 남아 규칙 위반 상태가 지속된다 |
| **B. 현행 주소만 전 계열** | `192.168.1.22`(현재 쓰는 것) + `172.30.135.149` 만 **모든 파일**에서 걷고, 이미 안 쓰는 `192.168.1.29` 는 이력에 둔다 | **살아 있는 표적만 없앤다** — 위험 감소분의 대부분을 얻으면서 이력 편집을 절반으로 줄인다. 감사가 매긴 심각도(LOW)와 비용이 맞는다 | 규칙 문언은 "쓰는 주소"가 아니라 "IP·토폴로지"를 금지한다 — 문언 위반은 남는다. `.29` 가 남아 **"어느 대역이 이 집 LAN인가"는 그대로 드러난다** |
| **C. 전 계열 전건** (감사 기록 포함) | 3개 주소 + 평문 비밀번호를 **56파일 전건** 역할 별칭으로 치환 | 규칙과 저장소 상태가 처음으로 일치한다. 가드를 예외 없이 걸 수 있다(D3 가 단순해진다) | **이력 문서 46개를 사후 편집한다** — "그때의 사실" 원칙을 이 축에서 깬다. **감사 기록이 자기 발견의 근거를 잃는다**(따로 보존 문구 필요). 벤치마크 JSON 의 `base_url` 은 측정 아티팩트라 수정이 곧 데이터 변조로 읽힐 수 있다 |
| **D. 전 계열 전건 + 감사 기록 예외** | C 와 같되 [`security_audit_dual_workflow.md`](../verifications/2026-09-05/security_audit_dual_workflow.md) 한 파일만 원문 보존(발견의 근거이므로) | 이력 편집의 이득을 다 얻으면서 **발견 문서의 증거력을 지킨다** | 예외가 하나 생기므로 D3 가드에 허용목록이 반드시 필요하다. "감사 기록만 왜 예외냐"를 다음 사람이 매번 다시 묻는다(주석으로 잠가야 한다) |

**추천: D.** 이유는 셋이다. ① 두 규칙의 충돌은 **보안 규칙이 더 최근이고 더 구체적**이다(2026-08-28 추가, 파일 계열을 열거) — 제품명 면제는 *표시명* 축의 판단이지 비밀값 축의 판단이 아니다. ② 이 저장소는 이미 **역할 별칭**을 배포 기록의 표준 표기로 쓰고 있어(S-6·S-7 행 전체가 그 형식) 이력 편집이 *사실을 지우는 것이 아니라 표기를 규칙에 맞추는 것*이 된다 — 어느 머신이 무엇을 했는지는 별칭으로 그대로 읽힌다. ③ 감사 기록만 예외로 두는 비용은 **가드 허용목록 한 줄**인데, 그것을 안 두면 *발견을 서술한 문서가 발견을 재현할 수 없게* 된다.

D 를 택하면 벤치마크 JSON 2건은 **필드값을 별칭으로 바꾸지 않고 키를 지우거나 `"base_url": "<베타-LLM>"` 로 치환**할지 함께 정해야 한다(추천: 후자 — 스키마를 유지한다).

## D2 — 치환 리터럴: 무엇으로 바꾸는가

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 역할 별칭** | `192.168.1.22:9080` → `<베타-LLM>:9080`, `172.30.135.149` → `<알파-호스트 LAN>` | **이 저장소의 기존 표기와 같다**(HANDOFF 머신 표·S-6·S-7 이 전부 역할 별칭). 문장이 읽는 사람에게 더 나아진다 | 원문 재현이 불가능하다(이력 축에서 손실). 별칭↔실주소 대응표를 저장소 밖에서 관리해야 한다 |
| **B. 문서 대역 치환** | RFC5737 TEST-NET 으로 형태 유지: `203.0.113.22:9080` | grep·복붙 예시가 문법적으로 계속 유효하다. 자릿수·형태가 보존돼 diff 가 작다 | **가짜 IP 를 진짜처럼 보이게 남긴다** — 다음 사람이 그것을 실주소로 오해할 수 있다. 이 저장소에 선례가 없다 |
| **C. 마스킹** | `192.168.1.xx:9080` | 최소 변경. 대역은 남기고 호스트만 가린다 | **대역이 남으면 스캔 비용 절감분이 거의 그대로다**(감사 시나리오가 노린 것이 "두 IP 를 정확히 아는 것"이지만 /24 스캔도 싸다). 반쪽 조치 |
| **D. 변수 표기** | `${LLAMA_BASE_URL}` | 코드·스크립트에는 정확한 표현 | 산문 이력에는 안 맞는다("그날 무엇에 붙었는가"가 사라진다) |

**추천: A(산문·문서) + D(코드·스크립트).** 두 자리는 성질이 다르다 — 산문은 *어느 머신이었나*를 남겨야 하므로 별칭이 맞고, `scripts/*_live_smoke.py` 의 하드코딩 기본값은 애초에 값이 아니라 **환경변수여야 하는 자리**다.

## D3 — 재유입 방지 가드: 얼마나 넓게 무는가

가드가 이 슬라이스의 **실제 산출물**이다(파일 수정은 1회성, 가드는 영속). 다만 **테스트 픽스처가 일부러 사설 대역을 쓴다** — 광의 정규식은 정상 코드를 문다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 금지 목록(정확 일치)** | 3개 실주소 + 평문 비밀번호 문자열을 **추적 파일 전건**에서 금지 | 오탐 0. 픽스처·CIDR literal 을 건드리지 않는다. 구현이 20줄 | **새 주소의 재유입은 못 막는다** — 다음 머신 주소가 들어오면 가드는 조용하다. 이번 사고의 재발만 막고 같은 종류의 사고는 못 막는다 |
| **B. 광의 RFC1918 + 허용목록** | `192.168.*`·`10.*`·`172.16~31.*` 전건 금지, 픽스처·CIDR literal·감사 기록을 허용목록으로 뺀다 | **종류를 막는다** — 새 주소도 걸린다. 규칙 문언("IP·토폴로지 기록 금지")과 폭이 같다 | 허용목록 유지비가 영구적이다. 정상 작업(새 테스트가 사설 IP 픽스처를 쓴다)이 빨간 불이 되어 **가드를 끄고 싶어지는 압력**이 생긴다 |
| **C. B + 대상 경로 한정** | 광의 정규식을 `docs/` 와 루트 `*.md` 에만 건다(`tests/`·`scripts/` 제외) | 픽스처 마찰이 구조적으로 0(경로로 갈린다). 산문 축은 종류를 막는다 | **`scripts/` 하드코딩이 가드 밖이다** — 이번 사고의 원인 중 하나가 정확히 그 자리다. 경로 예외가 곧 다음 구멍 |
| **D. A + C 겹치기** | 정확 일치는 **전건**(`scripts/` 포함), 광의 정규식은 **문서 경로만** | 두 실패 모드를 각각의 자리에서 막는다. 픽스처 마찰 0이면서 `scripts/` 도 덮인다 | 가드가 두 개라 읽는 비용이 조금 는다 |

**추천: D.** 픽스처 마찰(B 의 실질 비용)과 `scripts/` 구멍(C 의 실질 비용)이 서로 다른 축이라 한 규칙으로는 둘 다 못 잡는다. 두 규칙이면 각각 단순해진다.

**두 방향 회귀**(CLAUDE.md §4): ① 실주소를 문서에 되넣으면 실패한다 ② 픽스처가 쓰는 `192.168.1.50`·`10.9.0.0/16`·계약 literal `172.16.0.0/12` 는 **통과해야** 한다 — 과잉 교정으로 정상 대역을 막으면 그 셀이 문다.

## D4 — `scripts/` 3건의 하드코딩 기본값 (코드 변경)

`phase2a_provider_live_smoke.py:53` · `phase2b3_compare_judge_live_smoke.py:59` · `phase4_context_search_planner_live_smoke.py:48` 이 `DEFAULT_LLAMA_BASE_URL = "http://192.168.1.29:9080"` 로 **동작하는 기본값**을 들고 있다. 문서가 아니라 코드이므로 치환은 곧 동작 변경이다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 환경변수 필수** | 기본값을 없애고 `LLAMA_BASE_URL` 미설정이면 즉시 실패 | 주소가 코드에서 사라진다. **fail-fast** — 이 저장소가 다른 곳에서 쓰는 패턴과 같다(외부 API 형식 추론 금지 선례) | 인자 없이 돌던 스크립트가 이제 안 돈다(전부 live smoke 라 어차피 환경을 갖춰야 하지만, 절차 문서에 한 줄 추가가 필요) |
| **B. `http://localhost:9080`** | 기본값을 로컬로 | 무해하고 실행 가능성 유지 | **조용히 틀린 곳에 붙는다** — 로컬에 llama 가 없으면 연결 거부, 있으면 *의도하지 않은 모델*로 측정한다. 이 저장소가 반복해서 경계한 "조용한 품질 저하" |
| **C. 그대로 둔다** | 스크립트는 스윕 대상에서 제외 | 변경 0 | 규칙 위반이 코드에 남는다. D3-A 가드가 이 파일에서 실패한다(예외를 또 파야 한다) |

**추천: A.** 세 스크립트 모두 외부 LLM 이 있어야만 의미가 있는 live smoke 이고, 기본값이 맞은 적은 `.29` 머신이 현역이던 기간뿐이다 — **지금 그 기본값은 이미 틀렸다.**

## D5 — 평문 비밀번호 3히트

HANDOFF S-0 행은 **계정 축이 닫혔다**고 적는다(오너 확인: 알파 로컬 DB 에만 있었고 배포에는 존재한 적 없음 → 살아 있는 계정 없음). 그래서 남은 것은 **위험이 아니라 문자열**이다.

| 선택지 | 설명 | 장점 | 단점 |

## Follow-up considerations

- **D3 가드가 생기면 `.env.example`·compose 주석이 검사 대상에 들어온다.** 현재 둘 다 깨끗하지만(`0.0.0.0`·`127.0.0.1` 는 바인딩 서술이라 대상 아님), 가드 정규식이 바인딩 표기를 물지 않는지 확인해야 한다.
