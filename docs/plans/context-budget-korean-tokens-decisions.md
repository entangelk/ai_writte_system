### 1-1. 실측 ②가 드러낸 현재 영향 — self-report 6144는 이미 도달 불가능할 수 있다

측정 ②(프롬프트는 들어가지만 `프롬프트+n_predict`가 창을 넘으면 **200인데 출력만 잘린다**)를
현재 설정에 대입하면 이렇게 된다. `WRITING_REPORT_DEFAULT_MAX_TOKENS = 6144`이고 창이 8192이므로,
**6144를 전부 쓰려면 프롬프트가 2048 토큰 이하여야 한다.**
[`main.py:630`](../../services/application/app/main.py#L630) 주석도 정확히 그렇게 적고 있다
("6144 leaves 2048 tokens of prompt headroom"). 그런데 **입력 예산 기본값은 4096**이고, `len/4`
과소평가 때문에 실제 프롬프트는 그보다 더 커질 수 있다. 즉 프롬프트가 2048 토큰을 넘는 순간
report 출력은 `8192 − 프롬프트`로 조용히 잘리고, **잘린 JSON은 `invalid_report` 파싱 실패**가 된다.

**이것은 2026-07-22에 관측된 `invalid_report`와 증상은 같지만 원인이 다르다.** 그때는 `n_predict`
자체가 1024로 낮아서 잘린 것이고(그 주석이 서술하는 사건), 여기서 말하는 것은 **`n_predict`가
충분해도 창 잔여가 모자라 잘리는** 두 번째 경로다. 지금 주석은 이 두 번째 경로를 다루지 않는다.

**단, 오늘 실제 report 실패를 관측한 것은 아니다** — 잘림 메커니즘만 실측했고, 현재 배포에서
프롬프트가 실제로 2048을 넘는지는 측정하지 않았다. C-1에서 확인할 항목으로 남긴다.

> **→ C-1 결과(2026-07-28)**: 프롬프트는 **넘는다**(§1-2). 그리고 **§2-2에서 report 출력까지
> 재고 나니, 이 "두 번째 경로"는 가설이 아니라 오늘 배포의 상태다** — 창 8192 · `long` 프리셋 ·
> 컨텍스트 0에서 출력 여유가 3,598뿐인데 관측 report 출력 분포(3,089~4,341, n=6)의 **4/6이
> 그 선을 넘는다.** 실행 중인 시스템에서 `invalid_report`를 직접 관측한 것은 아직 아니라는
> 단서는 §2-2에 그대로 있다.

### 1-2. C-1 실측 (2026-07-28, 알파 머신) — 위 질문의 답: **넘는다**

프롬프트 리터럴을 소스에서 `ast`로 뽑아 **알파의 in-stack 모델 `/tokenize`로** 쟀다. 고정
system 프롬프트는 report **473 tok** · 생성 **215 tok**.

**컨텍스트가 0인 바닥값** — 검색이 아무것도 못 찾아도 성립하는 하한이므로 운영 데이터가 없어도
확정된다:

| 프리셋 | 후보 산문 | report 입력 바닥값 | 주석의 2048 헤드룸 | 창 8192의 실제 출력 여유 |
|---|---|---|---|---|
| short (1024) | 981 tok | **1,486 tok** | 이내 | 6,706 tok (6144 확보) |
| medium (2048) | 1,962 tok | **2,485 tok** | **초과** | 5,707 tok (**6144 미만 → 조용히 clamp**) |
| long (4096) | 4,033 tok | **4,594 tok** | **초과** | 3,598 tok (**6144 미만 → 조용히 clamp**) |

즉 **medium·long에서는 컨텍스트를 하나도 안 넣어도 §1-1의 전제가 깨진다.** 주석이 방지하려던
상태("cap이 서버에 의해 조용히 clamp되지 않게")는 이미 무너져 있다.

**다만 확인된 범위를 넘겨 읽지 말 것**: 확인한 것은 "6144 상한이 clamp된다"이지 "그 clamp

`invalid_report` 실패도 관측하지 않았다.

### 1-3. C-1 실측 — A안 기동 확인 (알파, RTX 3060 12GB)

**결론: A는 뜬다. VRAM·속도 모두 실질 비용이 없다. §2의 후퇴선은 쓸 필요가 없었다.**

| 항목 | `--ctx-size 8192` | `--ctx-size 16384` |
|---|---|---|
| 기동 · `/props`의 `n_ctx` | 성공 · 8192 | **성공 · 16384** |
| 모델 적재 후 VRAM | 9,326 MiB | 9,481 MiB (**+155**) |
| 생성 중 VRAM 최대 | 9,329 MiB | **9,502 MiB** (12,288 중 여유 **2,786**) |
| prompt eval (1,946 / 4,031 tok) | 1,236.5 / 1,241.1 tok/s | 1,190.1 / 1,223.5 tok/s |
| generation (같은 두 프롬프트) | 37.5 / 34.8 tok/s | 38.1 / 34.9 tok/s |

- 속도 차이는 **노이즈 범위**다(각 값은 3회 중앙값). 한글 밀도는 **1.68자/token**으로
  §1의 범위(1.62~1.79, 평균 1.70)**안에서 관측**됐다 — 다른 머신·다른 서버 인스턴스이므로
  `len/4`(4.0)가 과소평가한다는 §1의 전제를 뒷받침한다. **다만 표본은 문단 1종이므로
  "평균 1.70의 재현"이라고 쓰면 과장이다**(§1은 산문 5종 측정이었다).
- **창이 실제로 커졌음은 동작으로 확인했다**: 같은 프롬프트(12,971 tok) + `n_predict` 2,048이
  창 16384에서는 **HTTP 200 · `truncated: false` · 2,048 전량 생성**, 창 8192에서는
  **HTTP 400 `exceed_context_size_error`**. 400 본문의 `n_prompt_tokens: 12972`는 **BOS +1**을
  독립 재현한다.
- **VRAM +155 MiB는 KV 2배 치고 작아서 따로 검증했다**: 창을 12,971 tok까지 실제로 채우는
  동안 0.3초 간격으로 표본해도 최대 9,502 MiB — **지연 할당이 아니라 실제로 싸다.** 다만
  *왜* 싼지는 확인 수단이 없어 **단정하지 않는다**(`/props`는 SWA 정보를 노출하지 않는다).
  "창 2배 = VRAM 2배"로 추정하지 말 것.
- **측정 조건**: llama 단독 기동(스택 전체 down), 모델은 `-m`으로 캐시 snapshot 직접 지정
  (§7의 `-hf` 문제 때문). `-hf`↔`-m` 차이는 모델 해석 경로뿐이라 창 측정에는 영향이 없다.

## 2. ★ 착수를 막던 충돌 — "입력 8192"는 현재 창에서 성립하지 않는다 (→ A로 해소)

**`n_ctx = 8192`는 입력과 출력이 나눠 쓰는 총량이다.** 입력 예산을 8192로 두면 출력·프롬프트
템플릿 몫이 **0**이 된다. 즉 오너 지시 ②(창 가드)와 ④(입력 8192)는 **현재 창 크기에서 서로
모순**이며, 넷 중 하나를 골라야 한다.

현재 출력 예산: short 1024 / medium 2048 / long 4096, self-report 6144
([`main.py:1489`](../../services/application/app/main.py#L1489)·[`:634`](../../services/application/app/main.py#L634)).
**프론트는 셋 다 제공한다** — short·medium·long
([`WritingPanel.tsx:540-542`](../../frontend/src/writing/WritingPanel.tsx#L540-L542)).

> **정정(C-1, 2026-07-28)**: 이 문단은 원래 "프론트가 실제로 제공하는 것은 short·medium
> 둘뿐"이라고 적었으나 **사실이 아니었다.** `long` 옵션("전체 작성 (자동 개선 없음)")은
> **2026-07-21 커밋 `4c04a9e`**에 들어와 있었다 — 브리프 작성보다 일주일 앞서므로 최신화
> 누락이 아니라 조사 시점의 오독이다. **아래 선택지 표의 C는 그 오독 위에 서 있다**("A에
> 더해 프론트에 long을 노출"): long은 이미 노출돼 있으므로 C의 "노출" 부분은 실행할 것이
> 없고, 남는 차이는 **출력 long(4096)을 창 계산에 포함하느냐**뿐이다. 표는 결정 이력이라
> 지우지 않고 이 각주로 정정한다. 실무적 함의는 **§2-1**에 있다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 창을 16384로 올리고 입력 8192 (오너 지시에 가장 충실)** | `LLAMA_CTX_SIZE` 8192→16384, 입력 예산 8192, 출력 medium 2048 + 템플릿 여유 | 오너가 원한 8192를 **그대로** 얻는다 · 긴 회차·많은 근거를 실제로 넣을 수 있다 | **KV 캐시가 2배**가 되어 알파(3060 Ti 12GB, in-stack)에서 VRAM·속도 영향 **미측정** · 베타는 **외부 서버**라 repo가 그 설정을 통제하지 못한다(그 머신에서 별도 조치 필요) · 감마는 LLM 자체가 없다 |
| B. 창 8192 유지, 입력 상한 ~5120 | 8192 − medium 2048 − 템플릿 여유 ≈ 5,120 토큰(한글 ~8,700자) | 인프라 변경 0 · 지금 당장 안전해진다 · **현재 4096보다는 여전히 상향** | 오너가 말한 8192가 아니다 · self-report 6144와 함께 쓰면 다시 빠듯하다 |
| C. 창 16384 + 입력 8192 + 출력 long(4096) 개방 | A에 더해 프론트에 long을 노출 | 가장 긴 생성까지 일관 | A의 비용 + 8192+4096+템플릿 = 12,288+ 로 16384도 빠듯 |
| D. 창을 모델 최대까지 (gemma 계열은 128K 지원) | 대폭 상향 | 상한 고민이 사라진다 | q4_0 12B에서 KV 캐시가 VRAM을 압도 · 로컬 GPU 배포(알파)가 목적이므로 비현실적 |

**→ 오너 결정: A 확정(2026-07-28).** VRAM은 "테스트 해보면 된다"는 판단이며, **알파에서 실제로
띄워 확인**한다. 따라서 알파 실측은 A/B를 고르는 관문이 아니라 **A의 기동 확인 절차**다.
(구현자 추천도 A였다: 오너의 8192 의도를 유일하게 그대로 만족하고, B는 "8192로 올렸다"는 기록과
실제 동작이 어긋나 다음 작업자가 또 헷갈린다.)

**A가 알파에서 안 뜨면** — 12B q4_0에 16384 KV 캐시가 3060 Ti 12GB에 안 들어가면 — 후퇴선은
순서대로 **(1) `LLAMA_KV_CACHE_TYPE` q8_0 양자화로 KV 캐시 축소 → (2) `LLAMA_GPU_LAYERS` 하향
(속도 저하 감수) → (3) B(창 8192 · 입력 ~5120)**. 이 순서를 여기 적어 두는 이유는, 안 떴을 때
다음 작업자가 곧바로 B로 후퇴해 오너 결정을 되돌리는 일을 막기 위해서다 — B는 마지막 수단이다.

> **베타는 A의 영향을 받지 않는다.** 베타의 LLM은 **외부 서버**(`192.168.1.22:9080`, `n_ctx=8192`
> 실측)이고 `docker-compose.llama.yml`이 그 설정을 통제하지 않는다. 그러므로 **가드는 창 크기를
> 상수로 박으면 안 되고 서버에서 읽어야 한다**(llama.cpp `/props`가 `n_ctx`를 주고, 400 에러 본문도
> `n_ctx`를 실어 준다). 그래야 같은 코드가 알파(16384)와 베타(8192) 양쪽에서 옳다. §5의 "창을
> provider 속성으로" 항목과 같은 이야기다.

## 2-1. ★ C-1이 찾은 것 — A안만으로는 **report 호출**이 여전히 창을 넘는다

**C-3 착수 전에 반드시 읽어야 하는 절이다.** §2의 A(창 16384 + 입력 8192)는 **생성 호출은
전부 흡수하지만 self-report 호출은 흡수하지 못한다.**

두 호출의 `입력 + 출력`을 **현행 입력 예산이 허용하는 최대치**(`ContextBudget(4096)` ×
`len/4` = 16,384자 = 실측 **10,094 tok**)로 계산한 결과(2026-07-28, 알파 in-stack 모델
`/tokenize` 실측):

> **표를 읽는 전제 — 이 표는 "만재(滿載)" 시나리오다.** 컨텍스트가 예산 상한까지 검색됐을
> 때의 값이며, **운영에서 만재가 얼마나 자주 일어나는지는 미측정이다.** 컨텍스트가 적으면
> 넘지 않는다 — 아래 "언제부터 넘는가"를 함께 볼 것.
>
> **생성 입력 10,382의 분해**(다음 작업자가 역추론하지 않도록): 생성 system **215** +
> `지시 스캐폴딩 + 만재 컨텍스트 + 마무리 지시`를 **이어붙인 상태로 잰** 10,166 + BOS **1**.
> 만재 컨텍스트 단독이 10,094이므로 스캐폴딩·연결 경계 몫은 약 **72 tok**이다(토큰화는
> 이어붙이기에 대해 가산적이지 않으므로 "약"이다).
>
> **밀도 표기 주의**: §1-3의 **1.68자/tok**은 문단 단위 표본이고, 이 표의 만재 값을 역산하면
> 16,384자 ÷ 10,094 tok = **1.62자/tok**이다. 둘 다 §1의 1.62~1.79 범위 안이고, 만재 쪽이
> **하한 밀도 = 같은 글자 수에 토큰이 더 많다 = 창을 더 잘 넘긴다**는 **보수적 방향**이다.
> 재산정할 때 두 숫자를 섞지 말 것.

| 호출 | 프리셋 | 입력 + 출력 | 창 8192 | 창 16384 |
|---|---|---|---|---|
| 생성 | short | 10,382 + 1,024 = 11,406 | 초과 | 이내 |
| 생성 | medium | 10,382 + 2,048 = 12,430 | 초과 | 이내 |
| 생성 | long | 10,382 + 4,096 = 14,478 | 초과 | 이내 |
| **report** | short | 11,765 + 6,144 = **17,909** | 초과 | **초과** |
| **report** | medium | 12,764 + 6,144 = **18,908** | 초과 | **초과** |
| **report** | long | 14,873 + 6,144 = **21,017** | 초과 | **초과** |

**왜 report만 넘는가**: report의 입력은 `system(473 tok) + 후보 산문 + 컨텍스트 패키지`인데,
**직전 생성의 출력(후보 산문)과 컨텍스트를 둘 다 싣기** 때문이다
([`report.py:138-144`](../../services/application/app/writing/report.py#L138-L144)). 게다가 위
수치는 report가 컨텍스트를 **포인터 포함**으로 렌더링하는 몫(`include_pointers=True`)을 빼고
잰 것이라 **실제로는 더 크다** — 표는 과소평가된 하한이다.

**빠져나갈 구멍이 없는 이유 3가지:**

- report는 **프리셋과 무관하게 모든 생성 호출에서 실행된다**
  ([`service.py:126`](../../services/application/app/writing/service.py#L126)). "long은 자동 개선
  루프를 안 탄다"는 것은 revise loop 이야기이고 report는 그대로 탄다.
- `long`은 이미 프론트에 노출돼 있다(§2 각주). 즉 21,017 tok 경우는 **가상의 미래가 아니라
  오늘 사용자가 고를 수 있는 경로**다.
- **C-2로도 해소되지 않는다.** 추정식이 정확해지면 입력 예산 8192는 실제 ~8,192 tok이 되는데,
  report 입력은 `473 + 8,192 + 후보 4,096 + JSON 오버헤드 ≈ 12,800`이고 출력 6,144를 더하면
  **약 18,900 > 16,384**로 여전히 넘는다.

### 언제부터 넘는가 — 창 16384에서의 컨텍스트 임계치

**"항상 넘는다"가 아니다.** 컨텍스트가 0이면 창 16384에서는 세 프리셋 모두 들어간다
(long이 최악: 4,594 + 6,144 = **10,738 < 16,384**). 넘기 시작하는 지점은 검색된 컨텍스트
크기에 달려 있다:

| 프리셋 | report 바닥값(컨텍스트 0) + 출력 6,144 | 창 16384의 컨텍스트 여유 | 현행 예산 상한(10,094) 대비 |
|---|---|---|---|
| short | 1,486 + 6,144 = 7,630 | 약 **8,754 tok**까지 | 87% 지점부터 초과 |
| medium | 2,485 + 6,144 = 8,629 | 약 **7,755 tok**까지 | 77% 지점부터 초과 |
| long | 4,594 + 6,144 = 10,738 | 약 **5,646 tok**까지 | **56% 지점부터 초과** |

(여유는 `16,384 − 바닥값 − 6,144`다. 토큰화가 이어붙이기에 가산적이지 않고 포인터 렌더링
몫이 빠져 있으므로 **낙관적 상한**이며, 실제 임계치는 이보다 낮다.)

**함의**: K-3의 `입력 + 출력 ≤ 창` 가드는 report 경로에서 **예외적 방어가 아니라 정상 운영
중에 닿을 수 있는 선**이다 — 특히 `long`은 예산의 **절반만 차도** 넘는다. 따라서 "가드가
걸리면 무엇을 하는가"가 report에서는 **기능 차이로 직결된다** — 400으로 거부하면 report가
정상 경로에서 실패하고, 조용히 통과시키면 §1의 실측 ②대로 **JSON이 잘려 `invalid_report`**가
된다.

~~**단, 빈도는 미측정이다.**~~ **→ 2026-07-29 베타에서 측정됐다(§2-3). 실제 원고 분량
입력에서는 "가끔"이 아니라 4/4다.** 이 문단은 결정 이력으로 남긴다: 실제 검색이 예산의 몇 %를
채우는지 재지 않았고 실제 report 실패도 관측하지 않았던 시점의 서술이며, 그때는 "구조적으로
도달 가능"까지가 확인된 범위였다. 마지막 문장("빈도를 먼저 재고 싶다면 `llm_call_audits`의
토큰 분포가 이미 그 신호를 갖고 있다")은 **절반만 맞았다** — 감사 레코드는 `total_tokens`
(prompt+completion 합)만 싣고 분해도 `finish_reason`도 `truncated`도 싣지 않아 **잘림 자체는
원리적으로 안 보인다**(§2-3 ⑤).

### 2-2. ★★ report 출력 실측 — 6144는 과잉이 아니고, **오늘 배포가 이미 잘리고 있다**

R-b("출력 상한 6144를 낮춘다")를 평가하려면 **실제 report가 몇 토큰을 쓰는지**를 알아야 하는데
아무도 잰 적이 없었다. 쟀다(2026-07-28, 알파. 운영과 **같은 system 프롬프트·같은 user 형식**,
**temperature 미지정** — 프로덕션이 그렇기 때문이다):

| 후보 산문 | 컨텍스트 | 입력 | **출력** | 파싱 | 종료 사유 |
|---|---|---|---|---|---|
| 336 | 582 | 1,419 | **3,623** | 성공 | stop |
| 336 | 582 | 1,419 | **3,698** | 성공 | stop |
| 1,120 | 1,690 | 3,341 | **3,089** | 성공 | stop |
| 1,120 | 1,690 | 3,341 | **4,341** | 성공 | stop |
| 2,688 | 4,070 | 7,351 | **3,997** | 성공 | stop |
| 2,688 | 4,070 | 7,351 | **3,370** | 성공 | stop |

**관측 report 출력 = 3,089~4,341 tok (n=6, 중앙값 ~3,660).** 6건 모두 파싱 성공·`stop` 종료라
**이 표본 자체는 잘리지 않았다**(입력이 작아 여유가 충분했다). 두 가지가 드러났다:

1. **6144는 과잉이 아니다.** 관측 최대 4,341은 상한의 **71%**다. 여유가 1.4배뿐이므로
   **R-b(상한 하향)는 실측으로 위험이 확인됐다** — 5,000 근처로만 낮춰도 잘리기 시작한다.
2. **출력 크기는 입력에 비례하지 않는다.** 후보 산문이 336 tok일 때도 3,623을 쓴다.
   report 분량을 정하는 것은 후보 길이가 아니라 **스키마의 장황함**(4개 배열 × 항목마다
   포인터 객체)이다. 즉 **입력을 줄여도 출력은 안 줄어든다** — R-a가 유일하게 남는 지렛대인
   이유다.

**그리고 이것을 "확보되는 출력 여유"와 대조하면 오늘 배포의 상태가 나온다.**
llama.cpp는 `프롬프트 + n_predict > n_ctx`일 때 **200을 주면서 출력만 조용히 자른다**(§1 실측
②). 실제로 쓸 수 있는 출력은 `창 − 프롬프트`다:

| 상황 | 프롬프트 | 출력 여유 | 관측 6건 대비 |
|---|---|---|---|
| 창 8192 · 컨텍스트 0 · short | 1,486 | 6,706 | 안전 |
| 창 8192 · 컨텍스트 0 · medium | 2,485 | 5,707 | 안전 |
| **창 8192 · 컨텍스트 0 · long** | 4,594 | **3,598** | **4/6 잘림** |
| 창 16384 · 만재 · short | 11,765 | 4,619 | 안전(빠듯 — 최대 4,341) |
| **창 16384 · 만재 · medium** | 12,764 | **3,620** | **4/6 잘림** |
| **창 16384 · 만재 · long** | 14,873 | **1,511** | **6/6 잘림** |

**세 번째 행이 오늘의 배포다** — 창 8192, `long` 프리셋, **컨텍스트를 하나도 못 찾아도**
출력 여유가 3,598뿐이라 관측 분포의 **4/6이 그 선을 넘는다.** 잘린 JSON은 `invalid_report`다.
이것이 §1-1이 "가설"로 남겨 둔 **두 번째 경로**이며, 이제 가설이 아니다.

**A안(창 16384)이 이것을 고치지 못한다는 점이 중요하다** — 창을 두 배로 키워도 만재 medium은
여전히 4/6, long은 6/6이다. **창을 키우면 입력 예산도 함께 커져 여유가 되돌아오지 않기
때문이다.** K-6을 정하지 않고 C-3을 하면 이 표의 아래 세 행이 그대로 남는다.

> **확인된 범위를 정확히**: 잰 것은 (i) 운영과 같은 형식의 프롬프트에 대한 **report 출력 크기**와
> (ii) 그것을 `창 − 프롬프트`와 대조한 **산술**이다. **실행 중인 시스템에서 실제
> `invalid_report`를 관측한 것은 아직 아니다.** 후보 산문·컨텍스트가 합성이고 표본이 6건이므로,
> 실제 프로젝트에서 report가 더 짧을 가능성은 남아 있다. 다만 **"6144가 과잉이라 낮춰도 된다"는
> 가설은 이 표본으로 반증됐다** — 그 방향의 결론에는 표본 크기가 충분하다.

### 2-3. ★★★ 베타 실측 (2026-07-29) — 오늘 배포에서 `long`은 4/4 실패하고, 원인은 포인터다

§2-2까지는 **알파에서의 산술 대조**였다("관측 report 출력의 4/6이 창 여유를 넘는다"). 베타에서
**실행 중인 시스템을 실제로 관통시켜** 확인했다. 베타는 외부 서버(`n_ctx=8192`, `total_slots=1`
실측)이므로 §2-2 표의 **세 번째 행 그 자체**다.

**① 결과 — 입력 크기에 따라 갈린다(두 방향 다 쟀다)**

| 시드 | 지시문 | 회차 | `writing_generation` | `writing_report` | job |
|---|---|---|---|---|---|
| 약 700자 | 평범 | 3 | 3/3 success (평균 1,160 tok) | **4 calls / 3 corr — 전부 success, repair 1회** | 3/3 성공 |
| **3,586자** | "한 회차 분량으로" | 4 | 4/4 success (**4,623~5,209 tok**) | **0/4 success · 4/4 `provider_error`** | **4/4 실패** |

즉 **모델이 실제로 긴 산문을 쓰는 순간 report가 죽고 generation job 전체가 실패한다.**

**② 실패 방식이 이 브리프의 예측과 다르다 — `parse_error`가 아니라 `provider_error`**

- 워커 실패 사유는 `provider rejected the request`이고, 그 문자열은 게이트웨이가 provider의
  **4xx**를 `REQUEST_REJECTED`로 매핑할 때만 나온다([`transport.py:122-128`](../../services/llm_gateway/app/transport.py#L122-L128)).
- 베타 서버에서 직접 확인: 과대 프롬프트 → `400 exceed_context_size_error` (`n_ctx: 8192`).
- **다른 원인을 배제했다**: `프롬프트+n_predict` 초과(2,166+6,144)는 **200**, `max_tokens`
  6144·4096과 `chat_template_kwargs={"enable_thinking":false}`를 실은 요청도 **둘 다 200**.
  (`enable_thinking`은 게이트웨이가 모든 호출에 붙이므로 report만의 차이가 아니다.)
- **즉 §1 실측 ①의 경로**(400 하드 거부, 자르지 않음)다. 사용자에게는 조용한 품질 저하가
  아니라 **job 실패**로 나오며, 프론트는 "생성 모델 호출에 실패했습니다."와 **"다시 시도"**를
  보여준다 — 이 실패는 결정적이라 **재시도는 반드시 같은 실패로 끝난다.**

**③ 근본 원인 — 예산 회계가 포인터를 한 토큰도 세지 않는다**

어림으로는 넘지 않아야 했으므로(시드가 3,586자뿐이다) 실제로 쟀다. 운영과 같은 요청으로
패키지를 만들고 report와 **같은 렌더링 형식**([`prompt.py:113-126`](../../services/application/app/writing/prompt.py#L113-L126))으로
재구성해 **실제 모델 토크나이저**로 측정:

| 측정 대상 | 실측 |
|---|---|
| 패키지 항목 수 | **69개** |
| **예산 코드가 믿는 값**(`token_estimate_total`) | **887 tok** |
| **생성**이 싣는 컨텍스트 (`include_pointers=False`) | 4,588자 / **2,412 tok** |
| **report**가 싣는 컨텍스트 (`include_pointers=True`) | 18,586자 / **11,304 tok** |
| report system | 473 tok |
| **report 프롬프트 합계**(후보 1,000자 기준) | **12,462 tok** |
| 창 | **8,192** |

- 항목마다 붙는 포인터 JSON(키 4개 중 **`content_hash`가 64자**,
  [`context_pointer.py:26`](../../services/application/app/writing/context_pointer.py#L26)·[`:94-99`](../../services/application/app/writing/context_pointer.py#L94-L99))이
  회계에서 빠져 있어 **887 → 11,304, 12.7배 과소평가**다.
- **포인터 몫이 report 컨텍스트의 79%**(11,304 − 2,412 = 8,892 tok)다. 이 경로의 지배 항은
  원고도 후보 산문도 아니고 **메타데이터**다.
- **"생성은 되는데 report만 죽는" 비대칭이 이것으로 정확히 설명된다** — 같은 69개 항목을
  생성은 포인터 없이(2,412), report만 포인터 포함으로(11,304) 싣는다.
  `include_pointers=True`는 report 한 곳뿐이다([`report.py:139-141`](../../services/application/app/writing/report.py#L139-L141)).

**④ 이것이 §2-1·§3-1을 어떻게 바꾸는가**

- §2-1은 포인터 몫을 알고 있었지만 **"표는 과소평가된 하한"이라는 단서**로만 다뤘다. 실측은
  그것이 보정 항이 아니라 **지배 항**임을 보여준다. §2-1의 임계치 표(short 8,754 / medium
  7,755 / long 5,646)는 **포인터를 뺀 낙관적 상한**이며, 실제 임계는 훨씬 낮다.
- **K-1을 아무리 정확히 고쳐도 이 12.7배는 남는다.** 밀도(1.62~2.46자/tok)는 `text`를 **어떻게
  세는가**의 문제이고, 이것은 `text` **밖을 아예 안 세는** 문제다. 두 오차는 곱해진다.
- 따라서 **K-6에서 "report 예산을 얼마로 줄일지"보다 "무엇을 세는지"가 먼저다** — 예산 숫자를
  낮춰도 포인터를 세지 않으면 같은 일이 반복된다.

**⑤ 확인 경로 자체의 한계(감사 레코드로는 잘림이 안 보인다)**

`StoredLlmCall`은 `total_tokens`(= prompt + completion, [`provider.py:13-18`](../../services/llm_gateway/app/provider.py#L13-L18))만
싣고 **분해도 `finish_reason`도 `truncated`도 기록하지 않는다.** 그래서 §2-2가 예측한
"조용한 잘림"은 **감사에서 `parse_error`로만** 보이고 잘림 자체는 원리적으로 관측 불가능하다.
오늘 실패가 보인 것은 4xx라 `provider_error`로 잡혔기 때문이다. **두 경로는 감사에서 다른
얼굴을 가지며, 이 구분 없이는 "무엇이 발화했는지"를 잘못 읽는다.**

**⑥ 확인된 범위를 정확히**: 잰 것은 (i) 베타 배포의 실제 관통 결과 8회, (ii) 그 실패가
provider 4xx임과 이 서버가 창 초과에 400을 낸다는 것, (iii) 운영과 같은 형식으로 재구성한
프롬프트 크기다. **`long` 이외 프리셋(short·medium)은 오늘 재지 않았다** — medium도 async
경로라 같은 구조지만 후보 산문이 짧아 임계가 다르며, 그 수치는 없다.

**⑦ ★ 창 크기가 실패의 *방식*을 바꾼다 — A안은 고치는 것이 아니라 얼굴을 바꾼다**

같은 입력(report 프롬프트 12,462 + 출력 6,144 = **18,606**)을 두 창에 대입하면:

| 창 | 프롬프트(12,462) | 프롬프트+출력(18,606) | 결과 | 근거 |
|---|---|---|---|---|
| **8,192 (베타·오늘)** | **초과** | 초과 | **400 하드 거부** → `provider_error` → **job 실패** | **실측**(관통 4/4 + 스윕 7/7) |
| **16,384 (A안·알파)** | 이내 | **초과** | **200이고 출력이 잘린다** → 잘린 JSON이면 `invalid_report` → `parse_error` | **추론** — 아래 참조 |

> **두 번째 행이 어디까지 측정인지 정확히**: 측정된 것은 **"400이 아니라 200"**까지다
> (`프롬프트 < 창 ∧ 프롬프트+출력 > 창`은 200이라는 §1 실측 ②를 **베타 서버에서도 재확인**:
> prompt 2,166 + `max_tokens` 6,144 = 8,310 → 200). **창 16,384 환경에서 이 입력을 실제로
> 던져 `truncated: true`와 `invalid_report`까지 본 것은 아니다** — 이 머신은 외부 서버라
> 창을 못 바꾸고, 알파에서 재현되지 않았다. 즉 **"200이 된다"는 실측이고 "잘려서
> `parse_error`가 된다"는 §1 실측 ②의 메커니즘에서 나온 추론**이다. 알파에 접근하는
> 사람이 확인해 주면 이 칸이 닫힌다.

- **즉 창을 16384로 올리면 이 입력은 "실패"에서 "조용히 잘린 report"로 바뀔 것으로 보인다.**
  §2-2가 예측한 경로가 그때 발화한다. **A안은 이 문제를 해결하지 않고 증상을 바꾼다** — 그리고
  바뀐 쪽이 **더 조용하다**(job은 성공으로 보이고 report만 비어 간다).
- 이것은 §2-1의 "A안만으로는 report가 여전히 창을 넘는다"를 **실측으로 뒷받침하면서 동시에
  구체화**한다: 넘는 방식이 창에 따라 다르고, **관측 가능성도 함께 달라진다.**
- **K-6을 정하지 않고 K-2=A만 적용하면, 오늘 베타에서 눈에 보이는 실패가 알파에서는 안 보이게
  된다.** 이것이 C-3에서 창과 예산을 함께 다뤄야 하는 이유다.

## 2-4. 구현 확정 사항 — 예산이 **무엇을** 세는가 (슬라이스 1, 2026-07-29)

§2-3이 진단이라면 이것은 그 위에서 내린 구현 결정이다. 코드 주석·HANDOFF에만 있으면 정본
계획에서 보이지 않으므로 여기 올린다(독립 검증 하드닝 #2).

- **예산은 항목의 `text`가 아니라 항목이 프롬프트에 렌더링되는 한 줄을 센다**
  (`- [label] {pointer_json} {text}`).
- **두 소비자 중 큰 쪽(report, 포인터 포함)을 기준으로 센다.** 생성 경로(포인터 없음)는
  그만큼 **보수적으로** 잡히며 이는 의도된 것이다 — 근거는 **과소평가가 버그 방향**이라는 점이다.
  예산이 과대평가하면 항목이 덜 들어가고(품질 손해), 과소평가하면 요청이 창을 넘어 **죽는다**.
  두 소비자에 다른 예산을 주는 형태(소비자별 비용 함수)는 배선이 커지고, **R-e 이후 두 렌더링이
  수렴하면 차이 자체가 사라진다** — 그래서 지금 그 축을 만들지 않았다.
- **구조적 래퍼(`<context_package>`·섹션 태그·`project_id`)는 예산에 넣지 않는다.** 어떤 항목에도
  귀속되지 않기 때문이며, **창 가드(K-3)가 system 프롬프트·후보 산문과 함께 고정 오버헤드로
  더해야 하는 몫**이다. 경계는 **항목별 비용 = 예산 / 고정 오버헤드 = 가드**로 갈랐다.
- **회계와 렌더러의 일치는 동등(equality)으로 잠근다.** 두 계산이 같은 문자열을 만들도록 되어
  있어 항목 단위로 정확히 같으며, 느슨한 상한(예: ×2)을 두면 **포인터를 두 번 세는 과잉 교정이
  그대로 통과한다**(실측). 의도적 여유를 두기로 결정하면 그 여유를 회귀에 **명시**한다.

| **K-5** | **splitter 블록 크기 상한** | 없음(현행) · 문자수 상한 후 강제 분할 | 상한 도입 검토. 현재 splitter는 **빈 줄로만** 문단을 나누므로([`core_sot/splitter.py:25`](../../services/application/app/core_sot/splitter.py#L25), 크기 상한 없음) **빈 줄 없는 원고를 붙여넣으면 1화 전체가 한 블록**이 되고, `len/4`가 7,000자를 1,750 토큰으로 보고해 예산을 그대로 통과한다. 다만 **offset·`content_hash` 계약**을 건드리므로 별도 슬라이스 |

### 3-1. K-1 실측 — 상수 보정만으로는 부족하다 (2026-07-28, 알파)

§1은 **산문 5종**에서 밀도 1.62~1.79를 얻었다. 그 범위만 보면 "상수 1.70이면 충분하다"로
읽히는데, **산문이 아닌 것을 포함하면 범위가 훨씬 넓다**:

| 종류 | 실제 밀도(자/tok) | 현행 `len/4` 오차 | 상수 `len/1.70` 오차 |
|---|---|---|---|
| 대사 위주 | 1.55 | −61.0% | −9.1% |
| 서술 위주 | 1.67 | −58.3% | −2.1% |
| 묘사·수식 많음 | 1.58 | −59.5% | −7.1% |
| 한자어·관념어 | 1.76 | −55.4% | +3.6% |
| **영문 혼합** | **2.46** | −38.1% | **+44.4%** |
| **숫자·고유명사** | **1.30** | −67.0% | **−23.6%** |
| 짧은 단문 반복 | 1.76 | −55.3% | +2.6% |

(음수 = **과소평가** = 예산을 넘겨 통과시키는 위험 방향.)

**상수 1.70은 `len/4`보다 압도적으로 낫다**(최악 과소평가 −67% → −23.6%). 그러나 **그것만으로
끝내면 안 되는 이유는 오차가 상쇄되지 않는 경우가 정상 동작이기 때문이다**:

- 위 7종을 **섞은** 코퍼스(918자)에서 상수 1.70의 오차는 **−1.3%**뿐이다 — 섞이면 상쇄된다.
- 그러나 **동종만 모인** 코퍼스에서는 상쇄가 없다: 숫자·고유명사만 1,656자 → **−23.4%**,
  영문 혼합만 1,860자 → **+44.7%**.
- **그리고 검색은 정의상 유사한 항목을 모은다.** 날짜·인명·수치가 중요한 장면을 쓰면 검색은
  숫자·고유명사가 많은 항목을 모아 오고, 그때 예산은 **−23%까지 과소평가된 채로 집행된다.**
  즉 "여러 종류가 섞여 상쇄될 것"이라는 가정은 **하필 문제가 되는 상황에서 깨진다.**

**결론**: 예산 8192를 상수로 집행하면 최악 표본에서 실제 프롬프트가 **약 10,124 tok**까지
커진다 — C-3의 `입력 + 출력 ≤ 창` 가드를 상수 위에 세우면 **가드 자체가 −23% 틀린 값을
검사하게 된다.** 따라서 **K-1은 (c) 색인 시 정확 계수 + (a) 상수 fallback**이 실측으로
뒷받침된다. 상수는 **LLM이 없는 환경(감마·유닛 테스트)의 fallback**으로 남기면 되고,
그 자리에서는 −23%가 예산 초과가 아니라 테스트 편의의 문제라 허용된다.

> **표본의 한계**: 각 표본은 67~160자로 짧고 **합성 문장**이다. 실제 프로젝트 원고로 다시
> 재면 종류별 비중이 달라질 수 있다. 다만 **밀도가 종류에 따라 1.30~2.46으로 갈린다**는
> 사실 자체는 표본 길이와 무관하고, 그것이 이 결론의 근거다.

## 5. Follow-up considerations (열어 둘 문)

- **외부 API 확장(`external-api-expansion-decisions.md`)과 만난다**: 외부 LLM은 창 크기가 제각각이라
  창 값을 **provider 속성**으로 두면 이 가드가 그대로 재사용된다. 지금 상수로 박으면 그때 다시 뜯는다.
- **관측 KPI와 만난다**: 토큰 추정이 정확해지면 `total_tokens` 집계의 의미도 정확해진다. 다만 감사
  레코드의 토큰은 **provider 응답의 usage 실측값**이라 이 보정과 별개다(혼동 금지).
- 리랭커 슬라이스가 붙으면 검색 항목 수가 바뀌므로 K-1의 "29개" 산정도 함께 갱신한다.

## 6. Deferred / out of scope

- 원고 본문 자체의 길이 제한(1화 몇 자까지 쓸 수 있는가) — **지금 범위 아님**. 원고는 통째로 LLM에
  가지 않으므로 창 문제와 직결되지 않는다. 필요해지면 별도 결정.
- 프롬프트 템플릿 자체의 토큰 다이어트.
- 토크나이저를 애플리케이션에 내장(`transformers` 의존성 추가) — 지금은 게이트웨이/색인으로 충분.

## 7. C-1 부수 발견 — `-hf` 재다운로드의 원인 (이 트랙 밖이지만 알파 작업을 막는다)

repo 그대로 `docker compose -f docker-compose.yml -f docker-compose.llama.yml up -d llama`를
하면, 캐시에 온전한 모델(6.5 GB)이 있는데도 기동하지 않고 **다른 blob을 새로 받기 시작한다**
(실측 약 4 MB/s). HANDOFF가 "재다운로드 정체가 잦다"고 적은 그 현상이며, **원인은 정체가
아니었다**:

- HF 캐시의 `refs/main`이 **`29d0977…`**인데 디스크의 snapshot은 **`f6e7774…`·`2b318d6…`**
  둘뿐이다. `-hf …:Q4_0`은 **리비전을 고정하지 않고 `main`을 따라가므로**, 업스트림이 새
  리비전으로 이동하면 캐시가 멀쩡해도 **새 리비전 파일을 다시 받는다.**
- 회피(측정 한정): 캐시 snapshot을 `-m`으로 직접 지정하면 즉시 뜬다.
- 볼륨에 **stale `.downloadInProgress` 약 4.9 GB**(11.8 GB 중)가 남아 있다. 이어받기용
  파일이라 C-1에서는 지우지 않았다.

**이 트랙의 결정 사항이 아니다** — `-hf`에 리비전을 고정할지, 모델 리비전을 최신으로 올릴지는
별개 판단이므로 추적 부채로만 올린다. 다만 **알파에서 LLM 작업을 하려는 다음 사람은 여기서
막힌다.**
