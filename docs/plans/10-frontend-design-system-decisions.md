### ★ 회귀가 무엇을 잠그고 있는가 — 이 페이즈의 비용을 정하는 실측

HANDOFF 는 *"회귀 285셀이 문구·구조를 상당히 잠그고 있어 그 수정 비용을 예산에 넣어야
한다"* 고 경고했다. **그 경고는 맞지만 절반만 맞다** — 무엇이 잠겨 있고 무엇이 안 잠겨
있는지가 갈린다(전 테스트 파일 grep, 2026-08-11):

| 단정 종류 | 건수 | 무엇을 잠그는가 |
|---|---|---|
| `ByRole` | **299** | 접근성 semantics(역할 + accessible name) |
| `ByText` | **251** | **화면 문구 리터럴** |
| `ByLabelText` | **179** | 폼 라벨 문구 |
| `toHaveTextContent` | **60** | 문구 |
| `toHaveClass` | **0** | — |
| `ByTestId` | **0** | — |

**결론 셋**:

1. **★ 순수 시각 변경은 사실상 공짜다.** 클래스명·스타일을 단정하는 셀이 **0개**다.
   색·간격·타이포·그림자·레이아웃을 CSS 에서 바꾸는 것은 **회귀를 한 셀도 건드리지
   않는다**. 오너가 말한 *"사소한 css 정도나 배치 정도"* 는 예산이 거의 0이다.
2. **문구를 바꾸는 것은 비싸다** — 311곳(`ByText` 251 + `toHaveTextContent` 60)이
   리터럴을 문다. 카피 리라이팅을 하겠다면 그것이 이 페이즈의 실제 비용이다.
3. **마크업 재구성은 role·label 을 보존하는 한 싸다** — `<div>` 를 `<section>` 으로
   바꾸거나 감싸는 것은 안 물지만, **heading 레벨·버튼 이름·폼 라벨을 바꾸면 478곳이
   반응한다**(`ByRole` 299 + `ByLabelText` 179).

이것은 **좋은 소식이다**: 잠긴 것이 *시각*이 아니라 *의미*라는 뜻이고, 의미를 보존하는
리디자인은 회귀가 방해하지 않는다. 그리고 **깨진다면 그것은 접근성이 퇴행했다는 신호**라
가드로서 옳게 작동하고 있다.

### ★ 구현자 권고가 틀렸다 — 현행 팔레트는 "AI 기본값"이었다

이 브리프 초판은 **ⓐ(현행 유지)를 권고하며** *"크림+벽돌 조합은 글쓰기 도구에 어울리는
방향이 이미 잡혀 있다"* 고 적었다. **그 판단은 틀렸고 오너가 기각한 것이 옳다.**

현재 생성형 AI 가 만드는 디자인은 세 가지 외양으로 수렴하는 것으로 알려져 있고, **그중
1번이 "따뜻한 크림 배경(#F4F1EA 근처) + 고대비 세리프 + 테라코타 강조"** 다. 이 저장소의
현행 값은 배경 **`#f4f0e7`** · 강조 **`#a4452f`(벽돌/테라코타)** 로 **그 기본값과 사실상
같은 좌표**다. 즉 *"글쓰기 도구다운 방향"* 이 아니라 **아무 브리프에나 나오는 기본값**이었고,
오너가 *"현행이 이상해서"* 라고 느낀 것이 정확한 관찰이다.

**교훈**: 미학 판단에서 "이미 방향이 잡혀 있다"는 관찰은 **그 방향이 선택된 것인지 기본값인지**
확인하기 전에는 근거가 못 된다.

### 확정 팔레트 — 잉크블루 (계산으로 세웠다)

**따른 기준 셋** (출처는 §참고문헌):

1. **3계층 토큰**(primitive → semantic → component). primitive 는 값을 이름으로
   (`blue-600`), semantic 은 **의도**를 이름으로(`--surface-page`·`--text-body`).
   **컴포넌트 계층은 이번에 만들지 않는다**(Deferred).
2. **OKLCH 로 램프 생성.** hue·chroma 를 고정하고 **L 을 등간격**으로 움직이면 눈에
   균등한 단계가 나온다. HSL 로 만들면 같은 L 값이 색상마다 다른 밝기로 보인다.
3. **WCAG 2.2 AA 를 통과 여부가 아니라 설계 입력으로.** 본문 4.5:1 · 큰 글자 3:1 ·
   **비텍스트 UI(테두리·포커스링) 3:1**.

**★ 파스텔과 대비는 충돌한다 — 역할을 갈라서 푼다.** 파스텔은 밝고 채도가 낮아 그 위에
파스텔 글자를 얹으면 4.5:1 이 안 나온다. 그래서 **파스텔은 면(surface)에만 쓰고, 글자와
강조는 같은 hue 의 깊은 쪽**을 쓴다. 화면은 파스텔로 보이고 대비는 잉크가 만든다.

**생성·검산 스크립트**: [`10_palette_contrast.py`](10_palette_contrast.py) — 의존성 없이
OKLCH→sRGB 변환과 WCAG 대비를 계산한다. **숫자를 손으로 적지 않았다**; 아래 표는 이
스크립트 출력이며 `python3 docs/plans/10_palette_contrast.py` 로 재현한다.

### ⓐ+ⓒ 를 함께 한다는 것의 의미 (오너 2026-08-11)

*"일반적으로 C가 맞지 않나? a랑 C랑 같이 해"* — 구현자는 ⓒ 를 **과설계로 보고 기각**했으나
오너가 **관용성**을 근거로 채택했다. 실제로 이것이 사용자가 학습 없이 찾는 자리다.

**둘을 합치면 형태가 하나로 정해진다**: username 이 **버튼이면서** 그것을 누르면 메뉴가
열리고, 메뉴 안에 **내 작업(`/me`) · 관리(관리자만) · 로그아웃**이 들어간다. 즉 ⓐ 는
"username 이 클릭 가능한 자리"라는 사실이고 ⓒ 는 "클릭하면 무엇이 나오는가"다.

**구현 시 지켜야 하는 것 넷** (이 저장소의 기존 가드가 요구한다):

1. ~~**`role="menu"`/`menuitem` 을 붙일 것**~~ — **★ 구현하며 고쳤다(2026-08-11, 10.0).**
   ARIA 의 `menu` 는 **애플리케이션 명령 메뉴**용이고 화살표 키 탐색·타입어헤드를
   사용자에게 약속한다. 여기 담긴 것은 **내비게이션 링크 둘 + 액션 하나**라 그 약속을
   지킬 이유도 방법도 없다 — 표준 **disclosure**(버튼 `aria-expanded`/`aria-controls`
   + 접히는 영역)가 맞다. **부수 효과로 기존 셀이 살았다**: `role="menuitem"` 을 얹으면
   `<a>` 의 link 역할이 덮여 `getByRole("link", { name: "관리" })` 가 무효가 되는데,
   disclosure 는 그것을 보존한다. 접근성 semantics 를 잠그는 규율(`ByRole` 299곳)은
   그대로 따르되 **패턴 선택이 달라진 것**이다.
2. **키보드로 열리고 닫혀야 한다** — `Esc` 로 닫기, 포커스가 트리거로 돌아오기.
   포커스 링 토큰(`--focus-ring`, 4.93:1)이 그래서 필요하다.
3. **관리자 링크는 조건부 유지** — 지금 `user.is_admin && <Link to="/admin">` 이다.
   메뉴 안으로 옮기되 **조건을 잃지 말 것**(잃으면 비관리자에게 404 로 가는 링크가 보인다).
4. **로그아웃 버튼의 기존 동작을 옮기기만 한다** — `loggingOut` 상태·`disabled`·
   `logoutError` 배너가 이미 있다. 재작성이 아니라 이동이다.
