# K-3 — 창을 모르는 호출을 예산 가드가 어떻게 다루는가

상태: `Resolved — ⓐ 그대로 유지(오너 2026-09-08)`
작성: 2026-09-08
선행: SoT **v1.7.60**(창 조회의 격리 계약) · v1.7.63·v1.7.64(예산 축) · 라이브 스모크 [`../../scripts/gateway_generate_live_smoke.py`](../../scripts/gateway_generate_live_smoke.py)

## 결정 필요

**게이트웨이가 모델의 컨텍스트 창을 아직 모를 때, 예산 가드는 통과시켜야 하는가 기다려야 하는가.**

v1.7.60 이 확정한 것은 **격리**다: 창 조회(`/props`)는 생성과 **동시에** 시작하고 **결과를 기다리지 않는다**. 기다렸더니 조회 지연이 게이트웨이 응답을 늦추고, 게이트웨이 transport 와 앱 클라이언트가 **같은 120s deadline** 을 써서 **이미 성공한 생성이 timeout 실패로 뒤집혔다**. 그래서 조회가 안 끝난 호출의 창은 `None`("모른다")이고 그것이 정직한 값이다.

**남은 빈 칸**: 창이 `None` 이면 가드는 **판정 대상 자체가 아니다**(`context_window_guard.exercised: false`). 즉 **첫 호출 몇 번은 예산 초과를 잡지 못한다.** 실패가 아니라 *"아직 몰라서 안 쟀다"* 인데, 그 구간이 얼마나 되는지·그동안 무엇을 놓치는지가 계약에 없다.

**★ 왜 지금 값이 올라갔나**: 배포가 **외부 API 로** 돈다. `/props`·`/tokenize`·`/apply-template` 는 **llama.cpp 전용이고 셋 다 예외를 삼켜 `None` 을 반환**하므로, 외부 벤더에서는 창을 **영영 모를 수 있다** — 그러면 `exercised: false` 가 과도기가 아니라 **정상 상태**가 되고 예산 가드는 사실상 꺼져 있다. 이것은 에러가 아니라 **조용한 품질 저하**다(HANDOFF 함정 절이 같은 것을 경고한다).

## 선택지

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 그대로** | 창을 모르면 가드 밖. 조회는 배경으로 계속 | v1.7.60 의 격리가 가장 단순하게 유지된다 · 생성이 조회 때문에 절대 안 죽는다 | **외부 API 에서는 영구히 가드가 안 걸린다.** 예산 초과가 400/잘린 출력로 **원인에서 먼 자리**에 나타난다 |
| **ⓑ 짧은 대기 허용** | 첫 호출에 한해 창 조회를 **아주 짧게**(예: 수백 ms) 기다린다 | 첫 호출부터 가드가 산다 · 대기 상한이 deadline 보다 훨씬 작으면 v1.7.60 의 사고는 안 난다 | **v1.7.60 이 고친 결함의 방향으로 한 걸음 돌아간다.** "짧다"의 값이 새 리터럴이고, 그 값이 맞는지는 머신·벤더마다 다르다 |
| **ⓒ `/props` 1회 재시도** | 실패하면 한 번 더 조회(여전히 비차단) | 일시적 실패에 강해진다 · 격리는 그대로 | **외부 API 는 재시도해도 `None` 이다**(엔드포인트 자체가 없다) — 이 결정의 실제 동기를 못 푼다 |
| **ⓓ 창을 설정으로 받는다**(신규) | `.env` 의 명시 값을 조회 실패 시 대체값으로 쓴다 | 벤더가 무엇이든 가드가 산다 · 조회를 전혀 안 기다린다(격리 완전 보존) | **또 하나의 값이 배포 설정에 는다**(틀리게 적으면 가드가 거짓말을 한다) · 값의 정본이 모델이 아니라 사람이 된다 |

## 추천 — ⓓ, 아니면 ⓐ 유지

**ⓓ 를 권한다.** 이 결정의 실제 동기는 *"조회가 느리다"* 가 아니라 **"배포 벤더에 그 엔드포인트가 아예 없다"** 로 바뀌었다. ⓑ·ⓒ 는 둘 다 *조회가 언젠가 성공한다*를 전제하므로 그 동기를 못 푼다. ⓓ 는 격리를 **전혀 건드리지 않으면서**(기다리지 않는다) 가드를 살린다.

**다만 ⓓ 는 조건부다** — 값이 틀리면 가드가 **거짓 안심**을 준다. 그래서 ⓓ 를 고른다면 함께 가야 하는 것: ① 조회가 성공하면 **조회값이 이긴다**(설정은 대체값이지 정본이 아니다) ② 설정값과 조회값이 **다르면 경고 로그**(둘 중 하나가 틀렸다는 신호) ③ 설정이 없으면 지금과 같은 ⓐ 동작.

**ⓐ 유지도 정당하다** — 지금 단계가 로컬 1인 도그푸드이고, 예산 초과의 실제 피해가 아직 관측 0건이라면 *"가드가 꺼져 있음을 알고 둔다"* 가 값싼 답이다. **그 경우 HANDOFF 함정 절에 "외부 API 에서는 예산 가드가 사실상 꺼져 있다"를 명시**해야 한다 — 지금은 그 사실이 K-3 표 한 줄에만 있어 다음 사람이 `exercised: false` 를 과도기로 읽는다.

## 후속 고려

- 어느 쪽이든 **`exercised: false` 의 뜻을 스모크 출력에 문장으로** 남긴다(지금은 HANDOFF 가 *"실패가 아니라 창을 아직 몰라 판정 대상이 아니었다"* 를 설명한다 — 그 문장이 출력 옆에 있어야 한다).
- ⓓ 를 고르면 값은 **`.env` 축**이고 저장소에 적지 않는다(공개 저장소 보안 규칙).
- 토큰 계수(`/tokenize`)도 같은 성질로 죽는다 — **예산 회계가 실측에서 추정으로 내려간다**(과소평가 방향 = 가드가 늦게 걸린다). 이 결정과 **같은 창에서 함께 보는 편이 싸다**.

## 유예 · 범위 밖

- **게이트웨이 transport deadline 자체의 조정**은 이 결정이 아니다(v1.7.60 이 같은 deadline 공유를 이미 계약으로 다뤘다).
- **벤더별 창 자동 탐지**(모델명 → 창 표)는 유지 부담이 크고 이 단계에서 값이 낮다.

## ✅ 오너 결정 (2026-09-08) — **ⓐ 그대로**

**구현자 추천(ⓓ 설정 대체값)과 다른 선택이다.** 오너가 ⓐ 를 골랐다.

**이 결정이 뜻하는 것을 정확히 적는다** — 브리프가 ⓐ 를 *"정당하다"* 고 한 조건이 *"가드가 꺼져 있음을 **알고** 둔다"* 였기 때문이다:

- **외부 API 배포에서 컨텍스트 예산 가드는 사실상 걸리지 않는다.** `/props` 가 llama.cpp 전용이고 예외를 삼켜 `None` 을 반환하므로, 창을 **영영 모른 채**로 돌 수 있다. `context_window_guard.exercised: false` 는 **과도기가 아니라 정상 상태**다.
- 따라서 **예산 초과는 가드가 아니라 벤더의 400 이나 잘린 출력으로** 나타난다 — 즉 **원인에서 가장 먼 자리**에서 드러난다.
- 토큰 계수(`/tokenize`)도 같은 성질로 죽어 **예산 회계가 실측에서 추정으로 내려간다**(과소평가 방향 = 가드가 더 늦게 걸린다).

**→ 그래서 이 사실을 HANDOFF 함정 절에 올렸다**(2026-09-08). 브리프가 ⓐ 의 조건으로 요구한 것이 그것이고, 그 한 줄이 없으면 다음 사람이 `exercised: false` 를 *"아직 안 쟀다"* 로 읽는다.

**되돌아볼 트리거**: 프롬프트가 창을 넘겨 **벤더 400 이나 잘린 출력을 실제로 겪는 순간**. 그때 다시 열 안은 ⓓ 다(격리를 안 건드리면서 가드를 살리는 유일한 안이라는 판단은 유효하다).
