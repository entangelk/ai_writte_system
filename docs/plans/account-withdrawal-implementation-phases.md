## 착수 전 실측 (2026-09-07) — 이 셋이 설계를 좌우한다

### 1. 파기 본체는 이미 있고 **한 벌뿐이다**

[`routers/admin.py::execute_project_purge`](../../services/application/app/routers/admin.py) 가 프로젝트 파기의 **유일한 본체**이며 admin purge 와 소유자 purge 가 그것을 공유한다(D8-6d). *"두 벌이 되면 어느 한쪽만 새 서비스를 받아 조용한 고아를 만든다."* **탈퇴 파기도 반드시 이 본체를 쓴다** — 사용자 축 파기 그래프를 새로 쓰면 세 벌째가 된다.

**다만 그대로는 못 쓴다:** 이 함수는 `HTTPException`(404·409)을 **던진다**. HTTP 문맥 밖(데몬)에서 부르면 워커가 HTTP 예외를 받게 되므로 **경계 하나가 필요하다**(슬라이스 3).

### 2. **파기 재시도는 멱등이 아니다** — 데몬 설계의 전제다

`execute_project_purge` 주석의 알려진 한계: core_sot 을 **먼저** 지우므로 derived 단계에서 실패하면 **재시도가 404 로 끝나 derived 에 도달하지 못한다.** 남는 derived 는 무해하지 않다(`llm_call_audits` 에 프롬프트 본문, `scratch` 에 원고 후보). 수습은 [`scripts/purge_reconciler.py`](../../scripts/purge_reconciler.py) 가 한다.

→ **데몬은 "실패하면 재시도" 로 짜면 안 된다.** 한 프로젝트가 중간에 실패하면 그 계정은 **부분 파기 상태**가 되고, 남은 청소는 reconciler 몫이다. 데몬은 그 사실을 **기록하고 멈춰야** 하며 같은 프로젝트를 다시 때리면 안 된다(D3).

### 3. ★ **사용량 원장이 `user_id` 를 쓴다 — 우리는 그것을 남기기로 했다**

프로젝트 축에서 이미 한 번 푼 문제가 사용자 축에서 그대로 반복된다.

- **파기 대상의 표식은 필드 이름이다.** `purge_reconciler` 는 `project_id` 필드를 가진 컬렉션을 DB 에서 발견해 고아를 쓸어 간다. 그래서 활동 로그는 반드시 `project_id` 여야 하고([`activity/log.py:31`](../../services/application/app/activity/log.py)), **남아야 하는 원장은 `target_project_id` 로 개명**해 그 쓸이를 피했다(8.2 L1=B). `project_name_history` 가 `_id` 를 project id 로 쓰는 것도 같은 이유다(08-2c N1=A).
- **그런데 원장의 사용자 축은 아직 `user_id` 다**([`quota/ledger.py:54`](../../services/application/app/quota/ledger.py)).
- 따라서 **사용자 축 reconciler 를 `user_id` 기준으로 만드는 순간 원장이 쓸려 간다** — 오너 결정(*"원장은 남긴다"*)과 정면으로 어긋난다.

→ **D4 가 이것을 정한다.** 지금은 사용자 축 reconciler 가 없어 잠재 위험이지만, **파기 축을 여는 이 슬라이스가 그 문을 연다.**

## Slice 0 — 상태 축과 계약 (백엔드, 화면 없음) — ✅ 완료(2026-09-08, SoT v1.8.45)

**범위:** 사용자에 탈퇴 상태를 더한다 — `withdrawal_requested_at`(+ 그로부터 유도되는 파기 예정 시각). **유예 기간 30일은 상수 한 곳**에 둔다(`auth/users.py::WITHDRAWAL_GRACE_PERIOD`, 산술은 `purge_due_at` 한 곳).

**★ 정책 문서 §6 승격은 이 슬라이스가 아니다(2026-09-08 정정).** 종전 문언은 *"정책 문서 §6 이 그것을 가리키게 한다"* 였는데 **Slice 5 가 같은 편집(§8 → §6 승격)을 자기 범위로 적어** 두 슬라이스가 한 편집을 자기 것이라고 말했다. 심판은 정책 문서 자신이다 — 머리말과 §8 절 머리가 *"§1~7 은 **코드가 지금 시행하는 것**, §8 은 정해졌지만 아직 코드에 없는 것"* 을 두 번 박아 두었고, Slice 0 뒤에도 **셀프 경로도 파기 데몬도 없어 탈퇴는 시행 중이 아니다.** 여기서 올리면 문서가 없는 기능을 시행 중이라고 말한다. → **승격은 Slice 5**, 그때까지 30일은 **핀 셀**(`test_auth_users.py::WithdrawalGracePeriodLiteralTest`)이 잠근다. 상징 참조 셀은 상수를 60일로 바꿔도 자기 자신과 비교하느라 초록이라 값을 못 잠근다(`MIN_PASSWORD_LENGTH` 선례).

**검증:** 상태 전이(활성→탈퇴 요청→취소→활성 · 요청→파기)의 양방향 셀. 30일 경계값(29일·30일·31일)을 **경계 셀**로 잠근다 — `>` / `>=` 과잉 교정이 통과하지 못하게.

**인계:** 이 슬라이스는 상태만 만든다. **아무것도 지우지 않는다.** 남는 계약 주의: **탈퇴 상태는 `is_active`·`status` 와 별개인 세 번째 축**이다(접으면 D1=C 의 *"유예 중에도 로그인해 취소"* 와 D6=A 의 *"비활성화는 단방향"* 이 함께 깨진다) · 재요청은 **첫 시각을 지키는 멱등** · 취소는 **스탬프 제거**라 취소한 계정이 요청한 적 없는 계정과 구별되지 않는다 · **Mongo 의 naive→UTC 재라벨링은 일관성이 아니라 수정이다**(빼면 파기 데몬이 `TypeError` 로 죽고 fake collection 은 그것을 못 본다).

## Slice 1 — 탈퇴 요청·취소 API — ✅ 완료(2026-09-08, SoT v1.8.46)

**범위:** 회원 본인의 `POST /me/withdrawal`(요청)·`DELETE /me/withdrawal`(취소). **마지막 활성 관리자는 거부**한다 — `deactivate_user` 가 이미 `LastActiveAdmin` 으로 거부하므로 **같은 규칙을 재사용**하고 새로 만들지 않는다.

**검증:** 중복 요청 멱등(200) · 취소 후 재요청 가능 · 마지막 관리자 거부(409) · 세션 없으면 401.

**★ 검증 목록 두 줄을 계약에 맞게 고쳤다(2026-09-08).**
- *"본인만 가능(타인 403)"* → **도달 불가**다. 경로가 대상을 지목하지 않으므로 남의 계정을 향한 요청을 **만들 수 없고**, 그래서 403 을 선언하지 않는다(더하면 화면이 오지 않을 응답을 처리한다). 잠그는 것은 403 이 아니라 **403 이 없다는 사실**이다 — 행위 축과 선언 축 두 셀.
- *"활동 로그 기록"* → **불가능**하다. `activity_events` 는 `project_id` 를 쓰는 **프로젝트 축**이고 파기와 함께 사라진다(D8-6 I1). 탈퇴는 계정 축이라 지목할 프로젝트가 없고, `/auth/login`·`/auth/logout`·`/auth/signup` 이 이미 같은 자리에 `not_project_scoped` 로 등재돼 있다. `admin_audit` 도 아니다(`admin_user_id` 를 요구하는 관리자 행위 축 — 셀프 탈퇴는 행위자가 곧 대상이라 그 필드가 거짓말이 된다). **사유와 함께 EXCLUDED 등재**로 대체했다.

**남는 계약 주의:** 재요청은 **200 멱등**(201 이면 재요청이 무언가를 새로 만든 것처럼 읽힌다) · 취소 없는 취소는 **404 가 아니라 409**(계정은 있다) · `purge_due_at` 를 응답이 실어 준다(유예 정본이 서버 상수 한 곳이라 프런트가 30 을 박으면 안 된다) · 저장소 seam 의 **조건부 쓰기**(`only_if_absent`)가 동시 첫 요청을 가른다. 다만 **취소를 가로지르는 지연 요청은 안 막는다** — 순서의 모호함이지 결함이 아니다.

## Slice 2 — 유예 중의 접근 규칙 — ✅ 완료(2026-09-08, SoT v1.8.48)

**범위:** D1=ⓒ 를 시행한다 — **유예 중에는 로그인·조회·취소만 되고 쓰기와 유료 경로는 막힌다.** 취소한 뒤에는 계정이 다시 활성이므로 제한이 전부 사라진다(별도 규칙이 아니라 상태가 돌아온 결과다). 화면은 Slice 4의 몫이다.

**구현 결과:** 오너 결정대로 별도 `GET /me/withdrawal`을 열고 `WithdrawalResponse`를 재사용했다(`/auth/me` 무변, operation 104→105). 중앙 `require_active_user_for_write`가 탈퇴 스탬프가 있는 계정의 일반 쓰기를 403으로 막는다. `POST /me/withdrawal`은 Slice 1의 반복 요청 200 멱등을, `DELETE`는 유예 중 상시 취소를 지키도록 예외 스택을 쓴다. 유료 경로에서는 이 가드가 quota보다 먼저 실행된다.

**검증:** 상태 조회 active/withdrawing 양면 · 유예 중 GET 허용/일반 쓰기 403 · 유료 경로가 quota/handler 전에 403 · 취소 뒤 쓰기·유료 경로 복구 · POST/DELETE 예외 정확 집합 · 모든 guarded write의 403 선언 · guard→quota 순서. under-strict와 over-strict 변이를 모두 재실패시켰다.

## Slice 3 — 파기 데몬 — ✅ 완료(2026-09-09, SoT v1.8.51)

**확정 계약**([`slice3-withdrawal-purge-daemon-decisions.md`](slice3-withdrawal-purge-daemon-decisions.md) ⓑ·ⓔ):
계정 축 식별은 **`user_id` 필드 또는 `_id`** 두 규칙이고 **보존 표식은 `target_user_id`** 다.
범위는 **데몬 + reconciler 스크립트**이며 관리자 화면은 Slice 4 다.

**구현 결과**

| 무엇 | 자리 |
|---|---|
| 파기 오케스트레이션(청구 → 묘비 → 프로젝트 → 스윕 → 계정 행) | `deletion/account_purge.py` |
| 두 규칙 스윕(목록을 손으로 안 든다) | `deletion/account_axis_sweep.py` |
| 사용자명 묘비(`_id` = `user_name:<id>` · 표식 `target_user_id`) | `deletion/user_name_history.py`(+`_mongo`) |
| 청구·부분 파기 표식 · 저장소 seam | `auth/models.py::User.purge_started_at` · `auth/users*.py` |
| 데몬(one-shot · `--loop` · `--dry-run`) + compose `withdrawal_worker` | `scripts/account_withdrawal_worker.py` · `docker-compose.yml` |
| 수습 경로 | `scripts/account_purge_reconciler.py` |

**★ 착수 실측이 이 문서를 두 군데 정정했다.**
① *"목록은 DB 에서 유도"* 는 사용자 축에서 **컬렉션 하나를 놓친다**(`request_quota_policies` 가 `_id` = user id).
② 그 규칙을 `_id` 로 넓히면 **3번의 사용자명 묘비를 스스로 지운다**(선례의 `_id` 키잉이 곧 *파기를 살아남는다* 의 표식이라).
둘이 한 갈림길의 양쪽이라 브리프로 물었고 오너가 ⓑ 로 닫았다.

**남는 계약 주의**
- **재시도하지 않는다.** `purge_started_at` 이 찍힌 계정은 다시 청구되지 않는다 — 재시도는 404 로 끝나고 derived 에 못 간다.
- **`purge_started_at` 은 리스가 아니다.** 리스는 *"나중에 다시 가져가라"* 인데 이 축이 절대 하면 안 되는 것이 그것이다.
- **한 계정의 실패는 거기서 멈춘다** — 다음 프로젝트로 넘어가면 부분 파기가 커진다.
- **묘비가 맨 앞이다**(프로젝트 축 8.2c N3 와 같은 이유). 뒤로 미루면 저장 장애 한 번에 이름이 영영 사라진다.
- **`login_failures`(`_id` = username)는 어느 규칙도 못 찾는다** — 이 슬라이스에서 정하지 않았다(브리프 후속 고려).
- **reconciler 는 프로젝트가 남았거나 묘비가 없으면 계정 행을 안 지운다.**

| **D3** | **ⓐ + 관리자 재실행 통제** | 실패하면 부분 파기로 표시하고 멈춘다. **다만 관리자 화면에서 잔여 정리를 실행할 수 있어야 한다**(오너 추가). **★ 그 버튼은 `execute_project_purge` 재호출이 아니다** — 재호출은 core_sot 이 비어 **404 로 끝나고 derived 에 도달하지 못한다**(실측 2). 부를 것은 **reconciler 경로**다: `scripts/purge_reconciler.py` 가 하듯 *"`project_id` 필드를 쓰는 컬렉션을 DB 에서 발견해 고아를 지운다"* — 목록을 손으로 들지 않는 그 성질을 그대로 가져온다 |
| **D4** | **ⓐ — 원장의 `user_id` → `target_user_id` 개명** | 프로젝트 축에서 이미 같은 값을 치렀다(8.2 L1=B). **★ 2026-09-07 완료** — 저장 필드·인덱스 키·질의 개명 + 멱등 마이그레이션(`scripts/migrate_ledger_user_axis.py`) + 셀 6. **배포 시 마이그레이션 선행**(아래) |
| **D5** | **ⓐ — 파기 실행 전까지 언제나 취소 가능** | 화면이 남은 일수를 그대로 말하면 된다 |
| **D6** | **ⓐ — 마지막 활성 관리자는 거부** | `deactivate_user` 의 `LastActiveAdmin` 선례를 재사용한다 |

### ✅ D4 완료 (2026-09-07) — 배포 시 주의

- 개명 대상은 **저장 필드·인덱스 키·질의**다. 서비스 층의 **메서드 인자 이름**(`has_usage(user_id, ...)`)은 그대로 뒀다 — 저장되지 않는 값이라 개명해도 안전이 늘지 않고 변경 면만 넓어진다.
- `admin_user_id` 는 **행위자**라 대상이 아니다(활동 로그의 `actor_user_id` 와 같은 선례). 정확 일치 판정에 걸리지 않는다.
- **★ 배포 전에 `python scripts/migrate_ledger_user_axis.py` 를 돌려야 한다.** 옛 문서가 `user_id` 를 든 채 남으면 ① 새 질의가 그 행을 못 찾아 **사용량이 0 으로 보이고** ② 사용자 축 reconciler 가 생기는 날 그 행들만 쓸려 간다. 마이그레이션은 **멱등**이고 `--dry-run` 이 있다. **옛 인덱스 3개를 지운다** — 키가 바뀌어 같은 이름으로 재생성할 수 없기 때문이며, 새 인덱스는 어댑터가 기동 때 만든다.
- **★ 다른 컬렉션은 개명하지 않는다. 그것이 옳다.** 세션·색인·생성 job·회원 한도 정책도 `user_id` 를 쓰지만 **탈퇴 시 지워져야 하는 계정 데이터**라 쓸이 대상인 것이 맞다. 활동 로그가 `project_id` 를 **일부러** 유지해 파기에 쓸리는 것과 같은 구조다 — **필드 이름은 파기의 opt-in/opt-out 스위치**이고, 원장만 opt-out 이다.
  - **★ 정정(2026-09-09 실측)**: 이 문단이 **회원 한도 정책에 대해 틀렸다** — `request_quota_policies` 는 `user_id` **필드를 쓰지 않는다.** `_id` 가 곧 user_id 다([`quota/policy_mongo.py:46`](../../services/application/app/quota/policy_mongo.py); 회원당 한 행이라는 P1 계약을 DB 가 강제하게 한 의도적 설계라 그 자체는 옳다). 따라서 *필드 이름이 스위치* 라는 문장은 **사용자 축에서 컬렉션 하나를 조용히 빠뜨린다.** 무엇으로 정정할지는 [`slice3-withdrawal-purge-daemon-decisions.md`](slice3-withdrawal-purge-daemon-decisions.md) 가 묻는다 — 여기서 미리 고르지 않는다.
