# Phase N — 중성색 중심 집필 스튜디오

상태: Draft — 색상 적용 범위 오너 확인 대기, 구현 전
작성: 2026-09-14

## 목적과 현재 확인

사용자는 프론트 전체의 파란색 비중이 과하다고 평가하고, 현대적이면서 눈길을 끄는 디자인을 요청했다. 현황 확인 → 페이즈 계획 → 구현 순서가 요청 범위다.

소스 확인 결과 `frontend/src/styles.css`의 페이지는 `--blue-50`, 침강면과 강조면은 `--blue-100`, 본문은 `--blue-900`이다. 같은 계열이 큰 면적과 본문까지 차지해 액션의 강조 효과가 약하다. 작품 서재는 구분선 목록이며, 헤더·목록 제목에 serif가 남아 있다. Phase W에서 원고면·모바일 도구·목록 행은 이미 정돈했으므로 그 성과를 이어간다. 이 진단은 코드 기준이며 실제 브라우저 시각 검수는 아직 하지 않았다.

## Decision needed

기존 승인인 블루 파스텔을 포인트로 축소할지, 키색 자체를 교체할지 확인해야 한다. 새 요청은 파란색의 과다 사용을 지적하지만 교체 범위까지 지정하지는 않았다.

정본 우선순위는 [시스템 계약](../system-contract-sot.md)의 문서 우선순위를 따른다. [Phase 10 D2](10-frontend-design-system-decisions.md)와 [Phase W](frontend-writing-studio-phase.md)는 블루 파스텔 유지를 명시한다. 아래 선택지는 그 결정의 변경 범위를 명시하기 위한 것이며 아직 승인된 구현 명세가 아니다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A — 중성색 중심 + 블루 포인트 | 페이지·본문·보조 컨트롤을 중성색으로, 주요 버튼·선택·포커스에 블루 유지 | 기존 정체성과 동작 인지 유지, 큰 면적의 파랑 해소 | 새 키색만큼 급격한 인상 변화는 아님 |
| B — 새 키색 | 중성색 바탕에 블루를 대체할 단일 액션 색 설계 | 제품 인상을 크게 바꿀 수 있음 | 새 키색 비교와 대비 검산 필요, 기존 D2 교체 |
| C — 팔레트 유지, 배치만 개선 | 현행 토큰 배정을 유지하고 서체·간격·레이아웃 변경 | 기존 승인과 일치, 색 검산 범위 최소 | 사용자가 지적한 파란 면적을 충분히 해소하기 어려움 |

**추천과 이유:** A. 이미 동작이 갖춰진 집필 앱이므로 중성 면과 진한 글자, 한정된 액션 블루로 시각적 위계를 만드는 편이 효율적이다. 다크 테마 전환이나 장식 이미지 없이 원고와 작품명이 중심이 된다.

## 디자인 제안 — A 선택 시

- **시각 방향:** 밝은 중성 면과 짙은 잉크색의 선명한 대비, 여백과 타이포가 중심인 현대적 집필 도구.
- **콘텐츠 구성:** 제품 헤더 → 작품명과 생성 행동 → 서재 목록; 편집기는 원고 → 저장 상태 → 필요할 때 여는 보조 도구 순으로 읽힌다. 홍보용 대형 헤더를 작업 화면에 추가하지 않는다.
- **상호작용:** 기존 짧은 페이지 등장, 목록 hover/focus의 행 강조와 화살표 이동, 도구 선택·드로어 전환을 정돈한다. reduced-motion을 보존하고 fixed 도구의 조상에 transform을 추가하지 않는다.
- 흰 원고면을 시각적 중심으로 두고 일반 패널의 파란 배경과 그림자를 줄인다. 선택 상태·오류·읽기 전용은 문구와 형태로도 구별한다.
- 한글 UI는 현행 시스템 고딕, 원고는 현행 명조를 유지한다. 제목 계층은 UI와 조화시키되 크기 토큰과 화면 폭 단일 규칙을 따른다.

## 검증 절차

1. `cd frontend && npm test` 및 `npm run build`.
2. `python3 docs/plans/10_palette_contrast.py`. primitive 변경은 생성기와 CSS를 함께 갱신한다. semantic 배정을 바꾼 경우에도 실제 표면 조합을 검산에 반영한다.
3. `python3 -m pytest tests/test_docs_indexes.py tests/test_repo_hygiene.py tests/test_design_token_provenance.py -q`와 `git diff --check`.
4. 실제 앱에서 1440×900, 768×1024, 390×844, 320px 폭 확인. 테스트 데이터는 검증용으로 분리하고 실제 작품을 수정하지 않는다. 브라우저 검증 제약은 결과에 명시한다.
5. 단순 색·간격 값을 복사하는 테스트를 추가하지 않는다. 동작 변경이 필요해지면 회귀부터 작성한다. 변이 검증이 필요하면 커밋과 깨끗한 트리 확인을 먼저 한다.

## Follow-up considerations

semantic 토큰 구조와 독립된 차트 계열색을 유지해 이후 테마 확장 가능성을 남긴다. 새 색을 상태색으로 겸용하지 않는다. 공통 페이지 폭과 원고 읽기 폭은 서로 다른 책임으로 유지한다.

## Deferred / 범위 밖

- API·저장 계약·라우팅·생성 정책 변경.
- 다크 모드, 외부 웹폰트·UI 라이브러리 추가.
- 랜딩 콘텐츠 재기획, 제품명 변경, 이미지 자산 도입.
- 새로운 검색·정렬·통계, 비활성 버튼 정책의 독립 재설계.

각 단계는 구현·검증·기록 후 현재 브랜치에 커밋하고 푸시하지 않는다. 다음 작업자는 N0 결정부터 이어간다.
