# 장면 메모 기능 — 착수 결정 브리프

상태: `Proposed — 오너 결정 대기`
작성: 2026-08-29
선행: Chapter→Scene 계층화·운영 migration 마감, 이동 링크 가시성 개선 완료

## Decision needed

**창작 중 남기는 메모를 어느 화면·어느 저장 단위·누구에게 보이게 할지 결정해야 한다.**
메모를 원고 본문·버전·LLM 문맥에 섞으면 정본 보존과 export 계약이 변하고, 브라우저에만
두면 다중 기기·소유권·파기 계약을 지킬 수 없으므로 기존 구현에서 유도할 수 없다.

## 현재 제약과 실측

- 원고의 정본은 `Chapter` 아래 `Scene(Draft)`와 append-only `draft_versions`다.
  Scene 본문에 메모를 넣으면 원고 저장·수정 이력·export의 대상이 된다.
- 프로젝트 설정은 작품 정보·내보내기·활동 타임라인처럼 **자주 하지 않는 일**을 모아 둔
  화면이다. 반대로 편집기 우측 드로어는 집필 중 반복해서 여는 작업 표면이다.
- 프로젝트는 현재 소유자 한 명의 자산이다. 관리자는 유효한 access grant로 **읽기 전용**
  접근만 할 수 있으며, 공동 편집자·팀 역할 모델은 없다.
- 프로젝트 purge는 `project_id`를 가진 자식 데이터를 제거하고, Scene purge는 Scene의
  정본·버전·파생 데이터를 함께 제거한다. 메모가 서버에 생기면 두 파기 그래프에 명시적으로
  들어가야 한다.
- 새 mutating route는 `activity/actions.py` 분류표에서 logged 또는 excluded(사유) 중 하나로
  전수 등재해야 한다.

## D1 — 메모를 두는 화면과 소속

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 편집기 드로어의 Scene 메모 탭** | 현재 열어 둔 Scene마다 메모 한 묶음을 본다 | 집필 맥락을 잃지 않는다 · 기존 우측 도구 독/드로어와 맞는다 · 장면 전환 때 대상이 명확하다 | 프로젝트 전체 아이디어를 한곳에 모으는 노트는 아니다 |
| B. 프로젝트 설정의 메모 탭 | 프로젝트 단위 노트 한 곳을 설정 화면에서 관리한다 | 전체 기획을 한 문서로 보기 쉽다 | 집필 중 반복 접근하기에 멀다 · 기존 설정 탭의 “저빈도 작업” 성격과 다르다 |
| C. 별도 `/projects/:id/notes` 화면 | Scene·Chapter·프로젝트 메모를 한 화면에서 다룬다 | 미래의 검색·분류·공유로 확장하기 좋다 | 새 IA·route·목록·필터를 지금 먼저 설계해야 하며, 최소 기능 범위를 넘는다 |

### Recommendation + reason

**A를 추천한다.** 지금은 도그푸드로 집필 흐름을 다듬는 단계이고, 메모의 즉시 가치는
“이 장면을 쓰다가 떠오른 것을 같은 화면에서 잃지 않는 것”이다. 기존 드로어가 이어쓰기·분석·검토를
작업 맥락으로 묶고 있으므로 메모도 같은 표면에 두는 것이 가장 작고 발견 가능하다.
프로젝트 전체 노트가 실제로 필요해지면 B 또는 C를 **별도 기능**으로 연다.

## D2 — 저장 단위와 수명

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 서버의 전용 `scene_notes` 컬렉션, Scene당 현재 메모 한 건** | `{project_id, draft_id, body, updated_at}`를 별도 저장하고 명시적 저장으로 교체한다 | 기기·세션을 넘어 보존 · 원고/버전/export/LLM 문맥과 분리 · project/Scene purge에 수명을 정확히 연결할 수 있다 | API·Mongo·파기 그래프·회귀가 새로 필요하다 |
| B. 브라우저 `localStorage` | 서버 없이 현재 브라우저에만 저장한다 | 가장 빠르고 API가 없다 | 다른 기기·브라우저에서 사라짐 · 소유권/백업/파기와 무관 · 사용자가 저장된 줄 오해하기 쉽다 |
| C. `Draft` 또는 `draft_versions`에 필드 추가 | 원고 정본과 함께 메모를 저장한다 | 조회가 한 번으로 끝난다 | 메모가 export·버전·본문 관련 LLM 흐름에 섞일 위험 · 메모 수정이 원고 정본 변경처럼 보인다 |

### Recommendation + reason

**A를 추천한다.** 메모는 원고의 일부가 아니라 작성 중의 보조 정보다. 전용 컬렉션으로 분리하면
원고 정본 보존 정책과 `draft_versions`의 append-only 성질을 건드리지 않으면서, 프로젝트·Scene
파기에서는 자식 데이터로 정확히 제거할 수 있다. 첫 슬라이스는 **Scene당 최신 plaintext 메모 한 건**과
명시적 저장만 제공하는 것이 적절하다.

## D3 — 읽기·쓰기 공개 범위

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 소유자 쓰기, 유효한 관리자 access grant는 읽기 전용** | 메모를 프로젝트 콘텐츠로 취급한다 | 현행 grant의 “프로젝트를 읽는다”는 의미와 일관 · 별도 예외 인가가 없다 · 관리 열람도 access-log에 남는다 | 개인적인 메모를 관리자 열람 범위에 포함한다 |
| B. 소유자만 읽기·쓰기 | 관리자 grant로도 메모를 보지 못한다 | 가장 강한 개인성 | 프로젝트를 읽는 grant의 예외가 생겨 인가·운영 설명이 복잡해진다 |
| C. 프로젝트 구성원 공동 편집 | 여러 사용자가 함께 읽고 수정한다 | 협업 노트로 확장된다 | 구성원/역할/충돌 해결 모델이 아직 없고, 현 단계에서 만들 수 없는 범위다 |

### Recommendation + reason

**A를 추천한다.** 현행 access grant는 승인된 관리자가 사유·시간 제한·감사 아래 프로젝트
콘텐츠를 읽는 경로다. 메모만 숨기면 “프로젝트 읽기”의 예외가 생기고 지원·운영 시 설명이 어려워진다.
다만 grant는 끝까지 읽기 전용이며, 메모 생성·수정·삭제는 소유자만 할 수 있어야 한다.

## D4 — 저장 경험과 변경 이력

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 명시적 저장, 최신 한 값만 보존** | textarea와 저장 버튼으로 현재 본문을 교체한다 | 저장 성공/실패가 명확 · 활동 로그가 keystroke마다 넘치지 않음 · 첫 슬라이스가 작다 | 자동 저장·되돌리기 이력이 없다 |
| B. debounce 자동 저장 | 입력 후 짧은 지연으로 서버에 저장한다 | 입력 흐름이 끊기지 않는다 | 네트워크 실패·탭 이동·중복 요청 UX를 별도 설계해야 한다 |
| C. append-only 메모 버전 | 메모 수정마다 버전을 남긴다 | 되돌리기·감사를 제공한다 | 원고 버전과 별도 이력 UX·보존 정책을 지금 설계해야 한다 |

### Recommendation + reason

**A를 추천한다.** 현재 원고도 명시적 저장을 사용하고, 메모가 원고보다 더 복잡한 충돌·자동 저장
정책을 먼저 가져갈 이유가 없다. `scene_note_saved` 한 활동 행은 **저장 성공 뒤에만** 남긴다.

## 선택 조합별 구현 범위

| 조합 | 첫 슬라이스에 생기는 것 |
|---|---|
| D1=A · D2=A · D3=A · D4=A (추천) | `GET/PUT /projects/{pid}/drafts/{did}/note`, 전용 Mongo 저장소, 소유자 쓰기/grant 읽기, 편집기 드로어 탭, Scene·project purge 연결, `scene_note_saved` 활동 기록 |
| D1=B/C | 화면 IA·route 및 프로젝트 단위 데이터 모델을 먼저 다시 결정해야 하므로 이 브리프의 추천 구현 범위를 벗어난다 |
| D2=B | API·권한·파기·활동 기록은 없지만, 기기 간 보존 불가라는 제품 제약을 화면에 명시해야 한다 |
| D3=B/C 또는 D4=B/C | 별도 인가/협업 또는 동기화·버전 계약이 필요해 구현을 시작하지 않는다 |

## Follow-up considerations

- `scene_notes`는 `project_id`와 `draft_id`를 모두 가져 프로젝트 purge reconciler의 자식
  발견 대상이 된다. Scene purge graph도 `draft_id`로 명시 삭제해야 고아가 남지 않는다.
- 메모 본문은 plaintext로 시작하고, 상한·빈 문자열의 의미(삭제인가, 빈 메모 저장인가)는 API
  모델과 UI가 같은 값으로 결정해야 한다. 첫 구현 전에 그 literal을 정본에 추가한다.
- `PUT`이 mutating route인 만큼 활동 분류표·OpenAPI·`schema.d.ts`·401/403 선언·소유자/grant
  경계 테스트를 함께 갱신한다. activity 기록은 handler에서 성공 결과 뒤에 남긴다.
- 메모는 export와 LLM 프롬프트에 **자동 포함하지 않는다**. 포함하려면 컨텍스트 예산·사용량·
  Gate 입력이 바뀌므로 별도 결정 슬라이스여야 한다.
- Scene를 archive했을 때 메모를 숨길지 읽기 전용으로 둘지는 기존 archived Scene 읽기 정책과
  함께 구현 시 확정한다. archive가 메모를 파기하지는 않는다.

## Deferred / out of scope

- Chapter/프로젝트 전체 메모, 여러 메모 카드·태그·검색·핀·드래그 정렬
- Markdown/rich text, 첨부 파일, 링크 프리뷰, 댓글·멘션
- 공동 편집, 사용자별 private note, 공유/공개 링크
- 자동 저장, 메모 버전·undo, 메모 전용 활동 타임라인
- export 포함, LLM 컨텍스트 주입, AI 요약·메모 기반 생성
- 기존 원고·버전에서의 메모 migration (새 기능이므로 기존 데이터 없음)
