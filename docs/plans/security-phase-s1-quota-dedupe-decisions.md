정본 연결: 감사 [`../verifications/2026-09-05/security_audit_dual_workflow.md`](../verifications/2026-09-05/security_audit_dual_workflow.md) §A.1~A.4 · [`../system-contract-sot.md`](../system-contract-sot.md) v1.7.88(Q9=A 매핑·B5·Q8)·v1.7.97(accept 멱등)·[`08-2b-duplicate-request-lock-decisions.md`](08-2b-duplicate-request-lock-decisions.md) G4=A
목적: **가입을 여는 순간 위험해지는** 유일한 HIGH 를 착수 전에 결정 축으로 쪼개 오너에게 올린다. 감사 권고("키 서버 검증 — 신선성 창 또는 서버 발급")는 처방의 뼈대만 줬고, 이 저장소의 등록 계약(B5·G4·Q9)과 충돌하지 않는 닫힘을 고르는 것은 오너 결정이다.

## Owner decisions — 2026-09-05

- **D1 = "A+D + report만 응답 저장"** — 구현자 추천(A+D 결합)에 report 국소 C 를
  얹었다. 유실된 성공 응답의 회복 문제(브리프가 단점으로 적은 것)를 오너가
  받아들이지 않고 저장 재생으로 닫는 쪽을 택했다.
- **D2 = "둘 다"** — 상한(2회)+쿨다운(60s)+입장 게이트. 단 입장은 유료 dependency
  literal 이 아니라 **입장 판정 재사용**(`require_quota_standing`)으로 시행했다 —
  그대로 붙이면 등재 목록 계약(유료 11경로)과 충돌한다(구현이 밝힌 제약).
- **D3 = "지금 run당 상한+이월"** — 추천(유예)과 달리 이번 슬라이스에 바로 시행.

## Decision needed

**클라이언트가 고른 원장 dedupe 키(`body.request_id`)를 서버가 어떻게 검증하는가(D1)** — 이것은 등록 계약의 경계를 고치는 일이라(아래 사실관계 2·6) 구현자가 조용히 고를 수 없다. 함께 **실패 job 재시도의 상한(D2)** 과 **identity 판정 팬아웃 상한(D3)** 을 정한다.

## 지금 사실관계 (2026-09-05 실측)

1. **공격(§A.1, HIGH)**: 인증 회원이 `body.request_id="evade-1"` + `X-Confirm-Duplicate: 1` 로
   `POST /writing/generate` 를 반복 — 매번 실제 파이프라인(context search + 생성 +
   self-report)이 돌지만 원장은 `(user, writing_generate, "evade-1")` 1행뿐, 이후 정산은
   전부 유니크 인덱스에서 `None` 으로 접혀 무과금. 일/주 한도(402)에 영영 도달하지 않는다.
   글쓰기 유료 5경로(generate·gate·revise·revise-and-gate·report)가 같은 축이다.
2. **★ 원장이 잠금의 등록 약속을 배반한다(브리프 세로 읽기에서 발견)** — 8.2b G4=A 는
   *"확인된 요청은 강제 재차지한다 … 확인 한 번으로 통과하고 **사용량 1회를 더 쓴다**"*
   라고 약속하지만(`quota/lock.py` 모듈 서술), 같은 키의 확인된 재실행은 원장에서 **무료로
   접힌다**. 정산 영수증 `QuotaCharge` 에 `confirmed` 필드 자체가 없다
   (`quota/enforcement.py:114-127`). 즉 잠금이 약속한 +1 과금은 **한 번도 시행된 적이
   없다** — 감사가 지적한 우회와 정확히 같은 뿌리의 계약 내부 모순이다.
3. **정상 클라이언트의 키 수명주기**: 프론트는 클릭마다 새 uuid 를 만든다(lock.py 서술).
   같은 키의 재전송은 **네트워크 재시도뿐**이다 — "재클릭"은 애초에 새 키로 새 과금이다.
4. **409-consumed 의 회복 가능성(경로별 결과 지속 여부)**: generate(gate findings·후보)·
   gate(findings)·revise(버전)·revise-and-gate·accept(정본+replay 조회) 는 결과가 서버에
   지속돼 상태 재조회로 회복된다. **`writing_report` 만 응답을 지속하지 않는다**
   (`routers/writing.py:763` 반환 직전 저장 없음) — 유실된 성공 응답의 재시도가 409 를
   받으면 그 결과는 되돌릴 수 없고 새 클릭(+1 과금)로 다시 얻는다. `context_search` 도
   같은 성격(검색 결과 미지속).
5. **잠금의 실질 댐**: confirm 헤더 없는 재전송은 `(user, action, project)` 잠금이
   진행 중 + 최소 5s 냉각으로 묶는다 — **빠른 루프에는 confirm 이 필요하고, 그 confirm 이
   지금은 무료다**(사실관계 2).
6. **경로별 갈림**: `analysis_extract` 의 키는 경로 파라미터 `job_id` 로 클라이언트가 못
   바꾼다(dedupe.py 서술 — §A.1 무관). `writing_accept` 는 키가 `idempotency_key` 인데
   **replay 조회가 `reporter.enrich`(provider 호출)보다 뒤다** — 같은 키 재전송마다 진짜
   report 호출이 돈 채 replay 가 200 으로 답한다(§A.1 말미). `draft_finalize`·
   `context_search` 도 `body.idempotency_key` 축으로 같은 형태다.

## 선택지 — D1: dedupe 키 신뢰(§A.1 HIGH)

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A — 정산된 키 소비(409)** | 입장 시점에 `(user, action, dedupe_key)` 정산 행을 조회해, 있으면 provider 실행 **전에** 409 `"request_id already consumed"`. 진행 중 재전송은 기존 잠금 429 가 담당 | 가장 작은 코드로 "무료 재실행"을 원천 차단(느린 루프도 실행 자체가 안 됨). 유니크 인덱스가 이미 있어 포인트 리드만 추가 | 성공 응답이 유실된 정직한 재시도가 결과를 못 받음 — 5경로 중 4+accept 는 재조회로 회복, **report 는 회복 불가**(사실관계 4). 5경로+finalize·context_search 선언 갱신 필요 |
| **B — 신선성 창** | 정산 collapse 를 창(예 1시간) 안에서만 인정, 창 밖 동일 키는 새 논리 요청으로 과금 | B5 문장을 거의 안 건드림 | **창 안 무료 재실행이 그대로다** — HIGH 를 닫지 못함(단독 불가) |
| **C — 동기 멱등 replay** | 정산 시점에 `(user, action, key)`→응답을 저장, 같은 키 재전송은 **저장 응답을 재생**(provider 미실행). 비동기 job 저장소의 Q8 철학을 동기로 확장 | 정확한 멱등 — 재전송이 무료이되 provider 도 안 돈다. report 유실 회복 문제도 사라짐 | 가장 큰 슬라이스(응답 저장+TTL+경로별 재생 분기+schema). 지금 필요한 넓이 대비 비쌈 |
| **D — 확인 실행 재과금(G4 정렬)** | `QuotaCharge` 에 `confirmed` 를 싣고, 확인된 실행의 정산은 유니크 충돌을 무시하고 **강제 신규 행(+1 과금)** | 등록 약속(G4)을 이행해 계약 내부 모순을 닫는다. **동시 경합**(둘 다 미정산인 채 실행돼 둘째가 공짜)을 물리는 유일한 안 | 단독으로는 confirm **없는** 재전송이 잠금 냉각(≈1회/실행시간+5s)으로만 묶여 느린 무료 재실행이 잔존 |
| **E — 서버 발급 키** | 유료 호출 전 키 발급(챌린지/논스) 을 먼저 받게 한다 | 가장 강한 검증 | 신규 엔드포인트+프론트 재작업 — 표면이 결함 대비 과대 |

**A안의 계약 문장(제안)**: *"같은 논리 요청(B5)은 한 번만 실행된다 — 정산된 키의 재제출은
실행 전 409, 진행 중 재전송은 잠금 429, 확인된 재실행은 +1 과금(G4 이행)."* 층마다 얼굴이
하나씩이다. `writing_accept` 는 409 가 아니라 **replay 조회를 enrich 앞으로 옮기는 순서
교정**으로 닫는다(이미 등록된 멱등 replay 계약과 일치 — §A.1 말미 지적). `draft_finalize` 는
구현 시 replay 조회 존재 여부를 확인해 있으면 accept 와 같은 교정, 없으면 A안을 적용한다.

## Recommendation(구현자 추천 — D1 은 추천에 report 국소 C 를 얹은 변형이, D3 는 추천과 다르게 **지금 시행**이 채택됐다)

- **D1 = A+D 결합 + accept 순서 교정.** A 가 "무료 재실행"을 원천 차단하고(confirm 없는
  느린 루프도 실행 전에 409), D 가 잠금이 이미 약속한 +1 과금을 이행해 동시 경합과
  confirm 헤더 남용을 동시에 닫는다 — 둘은 정확히 보완 관계다. B 는 단독으로 HIGH 를 못
  닫고, C 는 정본이지만 지금 필요한 넓이보다 비싸다(A+D 뒤에도 잔여 위험이 있으면 그때
  오를 단계). E 는 결함 대비 과대. **report 경로의 유실-재시도 트레이드오프(사실관계 4)는
  오너 취향 사안이다 — 받아들이거나, report 에만 국소 C(응답 저장)를 얹을 수 있다.**
- **D2 = (c) 둘 다.** 상한 literal 제안: **job당 재시도 2회, 쿨다운 60초**(값은 오너 확정).
- **D3 = (c) 유예, 단 (a)를 가입 개방 슬라이스(랜딩·약관)에 끼워 넣는다.** 팬아웃은 과금
  우회가 아니라 DoS 축이라 S-1 본류와 트리거가 다르고, 단일 워커 배포에선 공격자가 자기
  요청으로 직렬화된다.

## 확정 시 이행 계약(제안 — 오너 결정 후 슬라이스에서 확정)

- B5 문장 갱신(minor): "같은 논리 요청은 한 번만 실행·과금된다" + 층별 얼굴(409/429/+1).
- 5경로(+finalize·context_search) `responses=` 에 409 consumed 얼굴 등재, `schema.d.ts`
  재생성, 프론트 문구 하나(재조회 안내).
- 원장 포인트 리드(`(user, action, dedupe_key)` 조회) — 유니크 인덱스 재사용, 신규 인덱스 없음.
- `QuotaCharge.confirmed` 필드 + 정산 강제 신규 행 경로.
- retry 상한 literal(재시도 2회·쿨다운 60s — 확정값은 오너).

## Follow-up considerations

- A+D 뒤에도 **서버 재기동 창**(원장/in-memory 배포에서 정산 행이 메모리에만 있음)은
  남는다 — Mongo 배포가 정본이라 실배포 영향 없으나 문서화할 것.
- C(동기 멱등 replay)로의 확장길은 A+D 가 남기는 것(없는지)을 검증 기록이 확인한 뒤 판단.
- report 국소 C 를 나중에 얹어도 A안의 409 는 그대로 재사용된다(키 소비 후 저장 응답 재생).

## Deferred / out of scope

- E(서버 발급 키) — 결함이 A+D 로 닫히는 한 도입 근거 없음.
- 잠금의 분산 한계(8.2b §0.3 "최선 노력" 서술 그대로).
- 관측·감사 스키마 확장(409 consumed 도 셀지 여부) — 필요 시 별도.
