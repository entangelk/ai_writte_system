# Phase 9 — 서비스 활동 로그 (사용자 행위 기록)

상태: `Planned — 페이즈 신설만 확정(오너 2026-08-05). 착수 결정 브리프 대기`
발원: [`08-2c-project-name-history-decisions.md`](08-2c-project-name-history-decisions.md) §N2-a
(오너 문언: *"일반 서비스 로그에는 당연히 수정, 저장 뭐 이런 항목들이 저장되어야 할 테니까."*)
목적: **누가 · 언제 · 무엇을 바꿨는가**에 제품이 답할 수 있게 한다. 지금은 답할 수 없다.

> **번호 주의**: Phase 8(회원 요청 quota)과 독립이다. 8.2c를 결정하다 드러난 공백이라 발원만
> 8.2c이며, quota·과금 트랙에 속하지 않는다.

## 1. 왜 이 페이즈가 있는가 — 실측 공백 (2026-08-05, HEAD `1f8b99c`)

| 확인 대상 | 결과 |
|---|---|
| 범용 이벤트 로그 `system_events`([`mongo_collections.md` §43](../mongo_collections.md)) | **문서에만 있고 코드 0줄.** `services/`·`scripts/`·`tests/` 전수 grep 0건이며 §55에서 "Optional for MVP" |
| 프로젝트 개명 | 기록 없음 — `replace(project, name=…)` → `put_project` 덮어쓰기([`core_sot/service.py:450`](../../services/application/app/core_sot/service.py#L450)) |
| draft 제목 변경 | 동일하게 덮어쓰기, 기록 없음([`:458`](../../services/application/app/core_sot/service.py#L458)) |
| 본문 저장 이력 | `draft_versions`+`source_snapshots`는 append-only지만 **`created_at`도 `user_id`도 없다** — `version_number` 순번뿐([`core_sot/models.py:78`](../../services/application/app/core_sot/models.py#L78)) |
| 기존 감사 3종 | `admin_audit_events`(관리자 행위) · `access_grant_uses`(승격 접근) · `llm_call_audits`/`request_usage_ledger`(관측·과금). 어느 것도 **소유자의 일상 편집**을 기록하지 않으며, SoT v1.7.78이 *"섞이면 접근 이력이 소유자 활동 로그로 오염된다"*고 그 분리를 못박았다 |

즉 다중 사용자 서비스가 됐는데도 **"내가 어제 뭘 고쳤더라"·"이 원고를 누가 언제 저장했나"에 답할
수단이 전무하다.** 본문은 버전으로 복원되지만 그 버전이 *언제* 생겼는지조차 저장돼 있지 않다.

## 2. 목표 상태

이 페이즈가 끝나면 제품은 다음에 답할 수 있어야 한다.

- 이 프로젝트에서 최근 무슨 일이 있었는가 (생성·개명·저장·archive)
- 그 행위의 주체는 누구이고 시각은 언제인가
- 특정 원고가 마지막으로 저장된 것은 언제인가
- 프로젝트가 파기되면 그 로그도 **함께 사라지는가** (답은 예다 — §4 I1·I2)

## 3. 범위

### 포함

- 사용자 행위 이벤트의 저장 계약(문서 형태·인덱스·주체·시각)
- 쓰기 지점 배선과 **누락을 막는 전수 가드**
- purge·reconciler 연동(프로젝트 자식으로서 함께 파기)
- 회귀·뮤테이션 검증

### 제외

- 관리자 행위 감사(`admin_audit_events`)·승격 접근 이력(`access_grant_uses`)의 개정 — 별개 트랙이다
- LLM 호출 관측(`llm_call_audits`)·사용량 원장(`request_usage_ledger`) — 각각 관측·과금 축이다
- 되돌리기(undo)·시점 복원 기능 — 로그는 사실 기록이지 복원 도구가 아니다
- 프로젝트 파기 후에도 남는 기록 — **명시적으로 제외한다**(§4 I2)

## 4. 지켜야 하는 불변식 (착수 브리프가 뒤집을 수 없는 것)

- **I1. 활동 로그는 프로젝트 자식이다.** `project_id` 필드를 쓰고 purge 대상이며 reconciler가
  발견해 쓸어 간다([`purge_reconciler.py:49`](../../scripts/purge_reconciler.py#L49)).
  **8.2c의 `project_name_history`와 정반대 방향이고 그것이 의도다** — 그쪽은 `_id`를 project id로
  써서 reconciler를 구조적으로 피한다.
- **I2. 삭제 계약의 예외가 아니다.** 활동 로그를 purge 생존으로 만들면 개명 이력·제목·저장
  이벤트 전체가 삭제 예외로 승격돼 **D8-6이 무너진다**. 근거는 8.2c §N2-a의 축 1/축 2 구분이며,
  **이 페이즈를 여는 사람이 가장 먼저 읽어야 하는 문단이다.**
- **I3. 기존 감사 컬렉션에 얹지 않는다.** 관리자 행위·승격 접근과 섞으면 양쪽이 쓸모를 잃는다
  (SoT v1.7.78이 이미 명시).
- **I4. `project_id` 격리는 다른 모든 저장소와 동일하게 강제된다.**
- **I5. 새 operation이 생기면 인증 tier 전수 가드에 등재된다**(`tests/test_auth_api.py`).

## 5. 착수 결정 브리프 — [`09-0-service-activity-log-decisions.md`](09-0-service-activity-log-decisions.md)

**A1~A8이 선택지 표(`선택지 | 설명 | 장점 | 단점`) + 구현자 추천 + 근거로 그 문서에 있다.**
여기서는 무엇을 정하는지만 적는다. **오너 결정 전에는 구현하지 않는다.**

| # | 정하는 것 | 구현자 추천 |
|---|---|---|
| A1 | 저장 위치 — §43 `system_events` 자리인가 새 컬렉션인가 | A(새 `activity_events`, §43은 폐기 포인터) |
| A2 | 기록 대상 — 정본 변경만인가, 검토 결정까지인가, 전 mutating인가 | B(정본 10 + 검토 결정 9 = **19**) |
| A3 | 문서 형태 — 값 변화(before/after)를 담는가 | B(고정 코어 + **짧은 값**만, 본문 금지) |
| A4 | 기록 실패의 방향 — 격리인가 fail-closed인가 | A(격리 — 보안 하중이 없다) |
| A5 | 조회 통로를 이번에 여는가 | B(소유자 조회 하나, operation 77) |
| A6 | 보존 기간 — TTL을 두는가 | A(없음 — 파기가 수명을 정한다) |
| A7 | 쓰기 지점과 누락 가드 | A(endpoint + 전수 가드) |
| A8 | 원장·관측과 중복 기록하는가 | A(중복 없음, 소비 시점 조인) |

**셋은 되돌리기가 비싸다** — A2(쌓인 데이터가 남는다) · A4·A7(40개 endpoint에 퍼진 뒤의 변경은
전면 수정이다). 나머지는 나중에 넓힐 수 있다.

## 6. 선행과 순서

- **선행**: Slice 8.2c 구현 완료(같은 삭제 계약을 건드리므로 동시에 열지 않는다).
- **권장 순서**: [`main.py` 라우터 정리](../../HANDOFF.md) **뒤**가 유리하다. 활동 로그의 쓰기
  지점은 mutating endpoint 전체에 퍼지는데, 지금 그것은 **6,145줄**(2026-08-05 실측) 한 파일
  안에 있다. 라우터 분리 뒤라면 등록 함수 단위로 배선과 가드를 함께 세울 수 있다. **강한 의존은
  아니다** — 순서를 바꿔도 되지만, 바꾸면 같은 자리를 두 번 만진다.

## 7. Phase 완료 기준

- 주체·시각·대상을 가진 행위 기록이 남고, 회귀가 그 필드 집합을 고정한다.
- **purge가 활동 로그도 지운다는 것이 실 Mongo 셀로 증명된다**(I1·I2의 시행).
- 로그를 빠뜨린 새 mutating 경로가 가드에서 **실패한다**(A7 결정에 따른 형태로).
- 뮤테이션이 각 회귀 셀을 실제로 물었음이 work_log 표에 기록된다.
- 독립 검증을 통과한다.
