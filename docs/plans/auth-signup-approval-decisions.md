# 자기 가입(승인제) 슬라이스 — 착수 결정 브리프

상태: **Resolved (2026-08-22, 오너)**
부모: 다중 사용자 인증 D8 (`multi-user-auth-cms-decisions.md`). 본 슬라이스는
v1.7.82의 *"첫 관리자 없이 자기 가입하는 표면은 없다"* 를 **승인제로 개정**한다.

## 배경

오너 정정(2026-08-22): v1.7.82 문구의 의도는 무검증 개방 가입 금지였다 —

> *"요청은 할 수 있지만 그 확인은 관리자가 한다는 소리였어. 나중에 자동 가입처리를 하더라도."*

즉 표면은 **요청(누구나) → 관리자 승인 → 로그인**. 자동 승인 전환은
**승인 단계 제거만으로** 가능해야 한다(그 전제가 아래 파생 설계 전부를 결정했다).

같은 세션의 보안 점검(2026-08-22) 결과가 설계에 반영됐다:
- 로그인 브루트포스 방어 없음 → 이 슬라이스에 동봉(오너 결정 3).
- `AUTH_SESSION_TTL_HOURS` 기동 거부 가드 0건(추적 부채) → 같이 닫는다(인증을 만지는 슬라이스).
- 시드 계정 `visual_demo`(admin)·`visual_user` 정리 + 오너 계정 생성(오너 결정 3).

## 오너 결정 (2026-08-22, 전부 AskUserQuestion으로 확정)

### 1 — 승인 상태의 로그인 응답 = **403 + 사유**

대기/거절을 **다른 안내문**으로 구분한다. 노출 증가가 아닌 근거: 그 403을
받으려면 username+비밀번호가 이미 정확해야 하므로 사실상 본인에게만 보인다.
틀린 자격증명은 종전대로 401 통일(타이밍 방어 유지).

### 2 — 브루트포스 방어를 이 슬라이스에 **함께 담는다**

로그인 시도 제한. 공개 표면이 넓어지는(가입) 변경과 방어가 같이 선다.

### 3 — 시드 계정 **정리 + 오너 계정 생성**

`visual_demo`(admin)·`visual_user` 비활성화 후 오너용 admin 계정 생성
(첫 로그인에 비밀번호 교체 — C-6 흐름). 계정명은 오너가 지정한다.

## 파생 설계 (오너 규칙 "나중에 자동 가입처리" 로 이미 결정되는 것들)

### P-1 — 상태는 `User` 문서의 한 필드다 (별도 컬렉션이 아니다)

`status: "pending" | "active" | "rejected"`. 자동 승인 전환은 가입 요청이
active 로 행을 만드는 것뿐이어야 한다 — 별도 `signup_requests` 컬렉션이면
그 순간 계정 생성 경로가 둘이 된다.

- 기존 행(필드 없음)은 코드 기본값 `active` 로 해석한다(스키마리스 병합,
  마이그레이션 없음). Mongo 는旧行 에 필드를 **쓰지 않는다** — 첫 갱신 시에만 생긴다.
- `is_active`(관리자 비활성화, D6=A 단방향)는 **별개의 축**으로 유지된다.
  비활성화는 로그인 401 통일 메시지에 묶여 있다(열거 방어 대상) — 바뀌지 않는다.

### P-2 — 비밀번호는 요청 시 수령한다

자동 승인 전환 시 요청만으로 끝나야 하므로. 12자 최소 정책은 C-6 와 동일하고
Argon2id 해시가 pending 행에 저장된다(승인을 기다리는 동안 해시가 이미 확정).

### P-3 — `POST /auth/signup` 공개 경로

- 201 "접수" — 본문은 username·password. **비밀번호 확인란은 프론트 전용**이다.
- username 중복(active·pending 과) = **409** — 아이디 선택 안내를 위한
  **의도된 노출**이다(가입자에게 "다른 아이디를 골라라"를 알려야 한다).
- rejected 와의 충돌 = **재요청 허용**(행을 덮어쓴다) — 거절 후 재요청이 막히면
  거절이 영구 밴이 된다. 밴은 관리자 비활성화(D6)의 역할이다.
- 토큰·세션은 발급하지 않는다.

### P-4 — 로그인 게이트 순서

```
자격증명 검증 (실패 = 401 통일, 타이밍 방어 유지)
  → status pending/rejected = 403 + 사유 detail
  → must_change_password = 409 (C-6, 종전 무변)
  → 세션 발급
```

pending 계정에 **틀린 비밀번호** = 401 이다(상태가 403 보다 먼저 아니라 자격증명이
먼저다 — 열거 방어가 유지되는 이유).

### P-5 — 403 생산자는 이제 셋이다 (계약 개정)

D8-5 이래 *"403 has exactly two producers (ownership, admin)"* 불변식이
`tests/test_auth_api.py:416`·`:1241` 에 잠겨 있다. 로그인 403 이 생산자를
셋으로 만들므로 **두 셀을 함께 갱신**한다(소유권·관리자·가입 상태).
403 사유 구분은 detail 문구(로그인 경로 한정) — H3 "detail 분기 금지"의
**등재된 예외**다(기존 `describeWritingError` 예외와 같은 취급, SoT 에 명시).

### P-6 — 브루트포스 방어 = username 축 잠금

- 로그인 실패(401)를 username별로 계수, **기본 5회 실패 → 5분 잠금**
  (env `AUTH_LOGIN_MAX_FAILURES`·`AUTH_LOGIN_LOCKOUT_SECONDS` 로 override).
- 잠금 중에는 **올바른 비밀번호도 401 통일** — 잠금 여부가 응답으로 새지 않는다.
- 저장은 Mongo(재시작 생존 + 다중 인스턴스). 계수 창은 고정 슬라이딩이 아니라
  **잠금 만료 시 전체 리셋** — 정직하고 상태가 작다.
- **알려진 트레이드오프**: 누군가 희생자 username 으로 5회 틀리면 희생자가
  5분 잠긴다(DoS 면). 창을 짧게 둔 것이 완화다. IP 축은 nginx 경유(5520)와
  직접(8520)의 `X-Forwarded-For` 신뢰 문제로 **보류** — 별도 판단.
- 가입 요청 폭탄(서로 다른 username)은 pending 이 즉시 아무 권한도 못 얻고
  username 고유 제약이 반복을 막으므로 이 슬라이스에서 **IP 제한 없이** 둔다.

### P-7 — 관리자 승인 API + 감사는 현행 패턴을 따른다

- `GET /admin/signup-requests` — pending 목록(username·요청 시각).
- `POST /admin/signup-requests/{user_id}/approve` — status → active.
- `POST /admin/signup-requests/{user_id}/reject` — status → rejected.
- 감사는 계정 관리 조작(생성·비활성화)과 같은 취급 — **미기록**. 현행
  `admin_audit` 는 purge·승격 축만 기록한다. 승인 감사 확장은 별도 판단.
- 승인된 계정은 기본 quota 정책(일 20/주 100)을 받는다 — 정책 행이 없으면
  코드 기본값인 현행과 동일.

## 프론트

- `AuthGate` — 로그인 폼 아래 **"새 계정 요청"** 토글 → 가입 폼(username·비밀번호·확인) →
  접수 안내("관리자 승인 후 로그인할 수 있습니다").
- 로그인 403 detail 을 대기/거절 안내문으로 구분 표시(P-5 예외의 유일한 소비자).
- 관리자 콘솔 — 가입 요청 섹션(목록 + 승인/거절). 관리자 화면 노출은 오너 요청 사항.

## 시드 정리 (결정 3, 코드 슬라이스와 독립)

`visual_demo`·`visual_user` 비활성화(스크립트) 후 오너 admin 계정 생성.
계정명·초기 비밀번호는 오너가 지정(비밀번호는 argv 가 아니라 env 로 —
`create_user.py` 선례). 마지막 활성 관리자 보호(F2=A)상 비활성화 순서는
**오너 계정 생성 → 시드 비활성화** 순으로 한다.

## 유예 (이 슬라이스 범위 밖, 트리거 명시)

- IP 축 rate limit — `X-Forwarded-For` 신뢰 정책이 선행돼야 한다(공개 배포 전).
- 자동 승인 전환 — 오너가 켜는 날 P-1 구조 그대로(가입 시 active 생성).
- 승인 감사(`admin_audit` 확장) — 승인 이력이 운영상 필요해지는 날.
- 이메일 알림(가입 접수·승인 통보) — 이메일 인프라가 없다.
