# 계정 탈퇴 Slice 4b — 관리자 잔여 정리 착수 결정 브리프

상태: Proposed — 오너 결정 대기(2026-09-12)
작성: 2026-09-12 (구현 세션 70)
근거 계획: [`account-withdrawal-implementation-phases.md`](account-withdrawal-implementation-phases.md) §Slice 4b · 갈래 셋은 [`slice4-withdrawal-screen-decisions.md`](slice4-withdrawal-screen-decisions.md) §후속 고려 첫 항목 그대로

## 결정이 필요한 것

**잔여 정리(부분 파기된 계정의 수습)를 관리자 화면으로 올릴 때 — ① 대상 범위(계정 하나인가 전역 스윕인가) ② dry-run 두 단계를 그대로 옮기는가 ③ 실행을 `admin_audit`에 남기는가.** 셋 다 기존 계약·선례에서 유도되지 않는 갈래라 구현자가 임의로 고르면 안 된다(Slice 4 브리프 ⓐ 추천의 근거 3이 정확히 이것을 막으려는 것이었다).

## 배경 — 지금 어떻게 돌는가

- 파기 데몬은 실패하면 **그 계정에서 멈춘다**(D3=ⓐ). 재시도가 수습이 아니다 — 파기 본체가 core_sot 을 먼저 지우므로 두 번째 호출은 404 로 끝나고 derived(프롬프트 본문·원고 후보)에 도달하지 못한다.
- 실패한 계정은 `purge_started_at` 이 찍힌 채 남는다(성공하면 `users` 행 자체가 사라진다). 이 값이 곧 *시작됐지만 안 끝난 계정*의 정의다.
- 수습은 [`scripts/account_purge_reconciler.py`](../../scripts/account_purge_reconciler.py) 하나다: stalled 계정마다 **계정 축 두 규칙 스윕 → 사용자명 묘비 확인 → (프로젝트 잔여 없음 + 묘비 있음)이면 계정 행 삭제**. 프로젝트 잔여는 이름만 보고한다(프로젝트 축은 `purge_reconciler.py` 소관). **기본 dry-run, `--apply` 로만 지운다.**
- `AdminUserPayload` 에 탈퇴 축 필드는 하나도 없다 — 관리자 목록·상세가 유예 중·파기 중 계정을 **아무렇게도** 보여주지 않는다(2026-09-10 실측, Slice 4 브리프가 ⓑ 대신 ⓐ 를 고른 이유).

## 갈래 ① — 대상 범위

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 계정 하나** | `GET/POST /admin/users/{user_id}/reconcile` — 관리자 **사용자 상세** 화면 맥락에서 그 계정만 | 대상을 눈으로 확인하고 실행(비가역 파괴에 맞는 결). 404 계약 자연스러움. 오너 결정 D3(2026-09-07) 문언 *"관리자가 잔여 정리를 실행할 수 있어야 한다"* 와 맞는 자리(계정 상세). stalled 는 데몬 실패시에만 생기는 예외 상태라 전역 일괄의 이득이 작다 | stalled 계정을 **먼저 찾아야** 한다 — 읽기 필드가 목록·상세에 함께 가지 않으면 "어떤 계정이 대상인지"를 모른 채 상세를 열어야 한다 |
| **ⓑ 전역 스윕** | `POST /admin/withdrawals/reconcile` — 스크립트 1:1 로 stalled 전체를 한 번에 | 스크립트 경로를 완전히 대체한다. "빠뜨린 계정"이 없다 | **무엇이 지워질지 실행 전에 사람이 못 본다**(스키마상 요약을 먼저 보여줘도 결국 두 번 누른다). 한 번의 실행이 여러 계정의 파괴를 묶는다 — Slice 4 브리프 ⓑ 를 물리친 논거(되돌릴 단위가 없다)가 같은 크기로 재현 |
| **ⓒ 둘 다** | 계정 하나 op + 전역 op | 어느 흐름이든 열려 있다 | operation 둘·화면 둘·검증 둘 — **아직 stalled 계정이 실전에 한 번도 없다**(도그푸드 0건). 수요가 생기면 ⓑ 를 그때 얹는 게 싸다 |

## 갈래 ② — dry-run 두 단계

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 두 액션(조사 → 실행)** | `GET …/reconcile`(dry-run: 잔여 프로젝트·묘비 유무 조사, 파괴 없음) → 결과를 화면에 보여주고 → **사용자명 입력 확인**(프로젝트 파기 UI 선례: `.confirm-panel` + `.danger-button`) → `POST …/reconcile` | 스크립트의 *"조사가 기본"* 정체성을 그대로. 비가역 실행 직전에 사람이 잔여 목록을 본다. dry-run은 GET(부수효과 없음)이라 계약이 깔끔 | 액션이 둘 — 화면·셀이 한 단계 모델보다 많다 |
| **ⓑ 한 액션(실행만)** | dry-run 없이 확인 대화 후 바로 `POST` | 단순하다 | **무엇이 지워질지 실행 전에 못 본다** — 스크립트가 dry-run 을 기본으로 둔 이유(파기는 되돌릴 수 없다)를 화면에서 뒤집는 셈 |
| **ⓒ 상세 읽기에 잔여 상시 표시 + 실행 한 번** | `GET /admin/users/{id}` 응답에 잔여 요약을 끼워 보내고 실행만 노출 | 단축 경로. 발견성 좋음 | 상세 조회가 파기 판단을 끌고 다닌다(잔여 조사는 파기 맥락에서만 의미 있는 비용). **조회와 실행 사이 상태가 변할 수 있어** 어차피 실행 시점 재판정이 필요하다 — 그러면 ⓐ 의 dry-run 과 본질이 같은데 계약만 흐려진다 |

## 갈래 ③ — `admin_audit` 감사

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 남긴다** | `record_purge_requested`/`record_purge_outcome` 선례(프로젝트 purge)를 따른다 — action 신규(예: `account_reconcile`), `target_type="user"` | 이 operation 은 **계정 행 삭제 + 계정 축 스윕 = 파괴**다. `admin_audit` 는 파괴 예외(purge·grants)를 커버하는 컬렉션이라 정확히 그 자리. 감사 화면(`/admin/audit-events`)에서 읽힌다 | 감사 행 스키마·화면이 한 축 늘고, 계정 op 무감사 관례의 첫 예외가 된다 |
| **ⓑ 안 남긴다** | `deactivate`·signup 승인/거절 관례(계정 op 무감사 — admin.py 주석이 *"widening them is a separate decision"* 이라 명시)를 따른다 | 구현이 작다 | **비가역 파괴를 무감사로 두는 것** — S-5 가 *"관리자 행위 다수가 감사 원장에 안 남는다"* 로 아는 공백에 **파괴 op 하나를 스스로 더 얹는다**. Slice 4 브리프 후속 고려가 정확히 이 결정을 회피하려고 열어 둔 것 |

## 추천 — ①ⓐ · ②ⓐ · ③ⓐ

**이유.**

1. **①ⓐ** — stalled 는 데몬 실패시에만 생기는 드문 예외고, 실전 관측 0건이다. 전역 일괄의 이득이 없는 상태에서 비가역 파괴를 묶는 것은 되돌릴 단위를 없앤다. 상세 화면 맥락(D3 오너 문언)과 일치한다. **전역이 필요해지면(도그푸드에서 stalled 다발) 그때 ⓑ 를 얹는다.**
2. **②ⓐ** — 스크립트 정체성(조사 기본)·비가역성·프로젝트 파기 UI 선례(이름 입력) 셋이 같은 방향을 가리킨다. dry-run 은 GET 으로 — 부수효과 없는 조사는 읽기 계약이 맞다.
3. **③ⓐ** — 무감사 관례의 대상은 비파괴 계정 op 들이다. 이번 것은 파괴고, `admin_audit` 의 존재 이유가 그 예외다. **남는 것을 늘리지 않는 방향**이 S-5 정신과 맞다.

**발견성 걱정(①ⓐ 단점)은 읽기 필드가 닫는다** — `AdminUserPayload` 에 탈퇴 축(`withdrawal_requested_at`·`purge_started_at`)이 오르면 목록·상세가 stalled 계정을 스스로 보여주고, 조사/실행 버튼은 그 조건부로만 노출된다. 읽기 필드는 어느 갈래를 골라도 범위 안(아래 "따라오는 것").

## 결정을 따라오는 것 (어느 쪽이든 범위 안)

- **`AdminUserPayload` 확장** — `withdrawal_requested_at`·`purge_started_at`(둘 다 `datetime | None`). 서버 상태 그대로(파생값 `purge_due_at` 은 관리자가 필요로 하지 않는다 — 남은 일수는 회원 배너의 것이지 관리자 잔여 정리의 입력이 아니다).
- **파기 본체는 한 벌** — 스크립트의 `reconcile` 로직(`stalled_user_ids`·`leftover_projects`·`reconcile` 본체)을 `services/application/app/deletion/` 아래 모듈로 옮기고 **라우터와 스크립트 둘 다 그것을 호출**한다(Slice 3 계약 주의 ⓕ "두 벌째를 만들지 말 것" 과 같은 정신). 스크립트는 인자 파싱·JSON 출력만 남는다.
- **등재 전부** — tier 핀(`test_auth_api.py` 105·admin 17 갱신) · `responses=` + `_REQUIRE_ADMIN` · `activity/actions.py` EXCLUDED 등재(관리자 축; ③ⓐ 면 사유 코드 `admin_audited` 가 비로소 문자 그대로 사실이 된다) · 프런트 `gen:api` 재생성.
- **관리자 화면** — 상세: 탈퇴 축 표시 + 조사(dry-run 결과) + **사용자명 입력 확인** 후 실행. 목록: 탈퇴 상태 라벨(기존 `status` 라벨 순서 "비활성 > 승인 대기 > 거절됨 > 활성" 은 승인 축 — 탈퇴는 **세 번째 축**이므로 그 순서를 건드리지 않고 옆에 표시). **새 CSS 규칙 없이** `.confirm-panel`·`.danger-button` 재사용(Slice 4 브리프 선례).
- **셀** — dry-run 스펙(잔여 프로젝트·묘비 유무, 파괴 무변) · 실행(스윕 결과·계정 행 삭제 조건: 프로젝트 잔여 있으면 행 안 지움) · 404(없는 사용자) · 409(대상이 stalled 아님 — 프로젝트 purge 의 *"archived 선행 409"* 와 대칭) · 감사 행(③ⓐ) · tier 갱신 · 프런트(조사 결과 표시·사용자명 확인·실행 후 notice·409 처리).

## 후속 고려 (결정 후에도 열려 있는 것)

- **전역 스윕 op(①ⓑ)의 트리거** — 도그푸드에서 stalled 계정 다발을 만나면 그때 연다. 스크립트 경로는 그때까지 살아 있다(①ⓐ 를 골라도 스크립트는 제거되지 않는다).
- **실행 중 경합** — dry-run 과 실행 사이 데몬이 같은 계정을 청구할 수 있다. 실행 본체는 스크립트처럼 **실행 시점에 재조회**하므로 안전하지만, `purge_started_at` 재확인(있으면 진행, 없으면 409)이 응답 계약에 들어간다.
- **계정이 지워진 뒤의 상세 화면** — 실행 성공 응답(`removed_user_row: true`)을 받은 프런트는 그 사용자 상세에서 나가야 한다(행이 없으므로 재조회 404). 화면 처방은 구현이 정한다.

## 유예 · 범위 밖

- **관리자 대행 탈퇴**(유예 만료를 기다리지 않고 즉시 파기)·**탈퇴 전 데이터 내보내기**·**탈퇴 사유**·**재가입 차단**·**유예 만료 알림** — 계획서 Deferred 그대로.
- **`login_failures`(`_id` = username)를 어느 파기 규칙이 찾는가** — Slice 3 브리프 ⓔ 미결, 화면 축이 아니다.
- **파기 청구 뒤 취소(D5 경계)** — 별도 브리프 [`slice5-withdrawal-cancel-after-purge-claim-decisions.md`](slice5-withdrawal-cancel-after-purge-claim-decisions.md) 가 이미 오너 결정을 기다리는 중이다. 이 슬라이스는 그 결정과 독립이다(잔여 정리는 `purge_started_at` 이 찍힌 계정만 다룬다 — 취소 경계가 어떻게 정해도 대상 집합이 변하지 않는다).
- **목록 화면의 stalled 필터/정렬** — F1 커서 페이징 축과 같은 "목록이 커질 때" 이야기. 관리자 사용자 목록은 지금 소수다.
