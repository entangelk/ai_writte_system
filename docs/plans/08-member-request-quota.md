# Phase 8 — 회원별 요청 횟수 제한과 Billing Readiness

상태: `Planned — 상위 방향 승인, 슬라이스별 세부 결정 대기`  
오너 방향 확정: 2026-08-02  
목적: 회원별 서비스 요청 횟수를 계량·제한하고 관리자 CMS에서 운영할 수 있게 해, 결제 수단을 지금 구현하지 않아도 향후 BM과 구독/결제 시스템을 연결할 수 있는 백엔드 경계를 만든다.

> 번호 주의: 이 문서의 **Phase 8**은 `multi-user-auth-cms-decisions.md` 안의 인증 결정 항목
> **D8**과 다른 번호다. 인증 D8 트랙은 선행 기반이고, 이 Phase가 그 `users.id`와 관리자 경계를
> 소비한다.

## 1. 이번에 확정된 상위 원칙

1. **회원 한도의 기준은 토큰량이 아니라 서비스 요청 횟수다.**
2. 토큰은 요청별 생성 계약에서 상한을 통제한다. Phase 8은 토큰을 회원 quota나 과금 단위로
   누적하지 않는다.
3. 이번 문서는 구현 순서와 결정 지점만 정하는 부모 계획이다. 기간, 차감 시점, 실패 처리처럼
   제품 정책을 확정해야 하는 항목은 **해당 슬라이스 착수 직전에 별도 decision brief**로 제시하고
   오너 결정 뒤 구현한다.
4. 목표는 **결제 가능한 구조**까지다. 결제 승인, 카드 정보, 청구서, 환불, 세금 처리는 이 Phase의
   구현 범위가 아니다.

## 2. 목표 상태

Phase 8이 끝나면 백엔드는 다음 질문에 일관되게 답할 수 있어야 한다.

- 이 회원이 현재 기간에 사용할 수 있는 요청은 몇 회인가?
- 어떤 회원이 언제 어떤 제품 동작으로 몇 회를 사용했는가?
- 같은 요청의 재전송이나 동시 요청이 중복 차감 또는 한도 초과를 만들지 않는가?
- 한도 초과 시 비용이 발생하는 작업을 시작하기 전에 거부할 수 있는가?
- 관리자가 회원별 한도와 상태를 조회·변경하고 그 변경 이력을 감사할 수 있는가?
- 향후 결제 공급자가 플랜/권한을 갱신할 때 제품 내부 로직을 우회하지 않고 연결할 수 있는가?

## 3. 범위

### 포함

- 기존 인증 사용자를 기준으로 한 회원별 request quota
- 정책 저장, 사용량 원장, 기간별 집계
- 동시성·중복 요청을 고려한 quota 검사와 차감 경계
- 비동기 job을 포함한 사용자 요청의 귀속
- 적용 대상 제품 동작의 명시적 목록과 전수 가드
- 관리자 CMS 백엔드 API: 회원별 정책·현재 사용량 조회, 한도/상태 변경, 조정 이력
- 향후 결제/구독 시스템이 회원 권한을 갱신할 수 있는 내부 service seam
- API 계약, Mongo 인덱스, 회귀·뮤테이션·live 검증

### 제외

- 토큰 기반 quota·토큰별 가격 계산
- 실제 PG/Stripe 연동, 결제 승인·취소·환불·정산
- 카드 및 결제수단 저장
- 세금계산서·영수증·회계 기능
- 쿠폰, 프로모션, 좌석 과금, 팀/조직 플랜
- 회원용 결제 화면과 관리자 CMS 프론트엔드

제외 항목은 폐기가 아니라 연결점 이후의 별도 제품 Phase다. 특히 관리자 화면은 이 Phase의 API를
소비할 수 있지만, 이번 완료 기준은 **CMS 백엔드**까지다.

## 4. 슬라이스 계획

각 슬라이스는 **브리프 승인 → 회귀 먼저 작성 → 최소 구현 → 관련 전체 회귀 → 독립 검증** 순서로
진행한다. 아래 브리프 파일명은 착수 시 생성할 예정 경로이며, 이 부모 계획이 선택지를 선결하지 않는다.

| 슬라이스 | 목표 | 착수 시 별도 브리프에서 결정할 것 | 완료 증거 |
|---|---|---|---|
| **8.0 사용 동작 인벤토리** | 비용을 소비하는 사용자 동작과 내부 LLM 호출을 전수 조사하고 request 단위 후보를 만든다 | 무엇을 1회로 셀지, 복합 동작·내부 retry/repair·조회성 AI 동작의 취급 | billable-action 표, 호출 경로 전수 가드, `08-0-billable-request-boundary-decisions.md` |
| **8.1 정책 모델** | 회원별 요청 한도와 적용 상태를 저장한다 | 기간 종류와 경계 시각, 기본 정책/개별 override, 무제한·정지 표현, 정책 변경 효력 시점 | 저장 계약·인덱스·양방향 회귀, `08-1-request-quota-policy-decisions.md` |
| **8.2 사용량 원장** | 요청 사용·조정 사실을 추적 가능한 원장으로 남기고 집계한다 | append-only 범위, idempotency key 출처/수명, 보존 기간, 개인정보 최소화, 집계 정본 | 중복 방지·회원/기간 격리·집계 회귀, `08-2-usage-ledger-decisions.md` |
| **8.3 quota 시행** | 비용 작업 전에 한도를 검사하고 동시 요청에서도 초과를 막는다 | 선차감/예약-확정/성공차감, 실패·취소·timeout 환원, 저장소 장애 fail-open/closed, 초과 API status/literal | 경계값·동시성·실패 복구·양방향 뮤테이션, `08-3-quota-enforcement-decisions.md` |
| **8.4 제품 경로 배선** | 8.0에서 확정한 모든 대상 경로를 한 quota seam에 연결한다 | HTTP 요청과 generation worker의 주체 전달, 복합 writing loop 귀속, 관리자/내부 작업 면제 여부 | 대상 전수 wiring 가드, sync/async 관통 회귀, `08-4-product-wiring-decisions.md` |
| **8.5 관리자 CMS 백엔드** | 관리자가 정책·현재 사용량·이력을 조회하고 조정한다 | endpoint 집합, 조정 사유/권한, 강제 차단·해제, 개인정보 노출 범위, 감사 로그 필드 | ADMIN dependency·OpenAPI·감사·소유권 격리 회귀, `08-5-usage-admin-cms-decisions.md` |
| **8.6 결제 연결 seam** | 외부 결제 시스템이 제품 내부 권한을 안전하게 갱신할 경계를 만든다 | provider-neutral 명령 계약, 외부 event idempotency, out-of-order event, 수동 정책과 결제 정책 우선순위 | fake adapter 계약·재전송/역순 회귀, `08-6-billing-entitlement-seam-decisions.md` |
| **8.7 독립 검증·hardening** | Phase 전체의 우회와 과잉 차단을 적대적으로 검증한다 | 별도 제품 결정 없음. 발견된 계약 공백만 새 브리프로 되돌린다 | 독립 검증 기록, 전체 회귀, 주요 mutation matrix, 필요 시 live Mongo 동시성 smoke |

## 5. 슬라이스 공통 불변식

세부 정책은 미정이지만 다음 안전 성질은 모든 선택지가 지켜야 한다.

- quota의 주체는 인증된 `users.id`이며 `project_id` 격리를 대체하지 않는다.
- 새 AI 경로가 quota 적용 여부를 분류하지 않은 채 조용히 열리면 테스트가 실패해야 한다.
- 클라이언트 재전송과 worker 재처리는 같은 논리 요청을 임의로 여러 번 세지 않아야 한다.
- 한 회원의 정책·사용량·조정이 다른 회원에게 섞이지 않아야 한다.
- 관리자 조정은 일반 회원 API로 우회할 수 없고 누가·왜 바꿨는지 추적 가능해야 한다.
- 사용량 원장은 LLM 관측 KPI와 목적이 다르다. `llm_call_audits`의 호출 수를 회원 사용 횟수로
  간주하거나 그 컬렉션을 과금 정본으로 재사용하지 않는다.
- 결제 공급자가 없어도 quota 기능 전체를 fake/로컬 구성으로 검증할 수 있어야 한다.

## 6. 의존성과 권장 순서

선행 기반은 다중 사용자 인증·소유권·관리자 경계다. 모두 현재 구현돼 있다. 제품 작업 순서는 다음을
권장한다.

1. D8-6 영구 삭제 UI 잔여를 닫는다.
2. Phase 8의 **8.0 → 8.3**으로 request 정의·저장·시행 경계를 먼저 세운다.
3. **8.4**에서 현재 제품 경로를 연결한다.
4. 외부 LLM/임베딩 확장을 시작할 때 새 provider 경로도 같은 분류·quota 가드에 포함한다.
5. **8.5 → 8.6 → 8.7**로 운영과 향후 결제 연결을 닫는다.

외부 API 확장 전체를 기다릴 필요는 없다. 반대로 외부 provider를 먼저 늘리면 quota wiring 대상이
늘어나므로, 적어도 8.0~8.3을 먼저 끝내는 편이 재작업이 적다.

## 7. Phase 완료 기준

- 회원별 요청 한도와 현재 기간 사용량이 저장소 재시작 뒤에도 일치한다.
- 한도 직전 정상 요청과 한도 초과 요청을 양방향 회귀가 구분한다.
- 같은 idempotency key 재전송, 동시 요청, worker 재처리에서 중복 차감이 없다.
- 확정된 실패/취소 정책대로 사용량이 일관되게 남거나 환원된다.
- 적용 대상 경로 전부가 quota seam을 지나고 신규 경로 누락을 전수 가드가 잡는다.
- 관리자 CMS API가 조회·변경·차단·조정 감사 계약을 만족한다.
- 외부 결제 공급자 없이도 entitlement 갱신 seam을 fake로 검증한다.
- OpenAPI, Mongo collection 문서, SoT, 작업 로그와 독립 검증 기록이 실제 구현과 일치한다.

## 8. 착수 시점까지 의도적으로 미정인 항목

다음은 누락이 아니라 **각 슬라이스 브리프에서 오너가 결정할 사항**이다.

- 1회로 세는 정확한 사용자 동작과 무료 동작
- 월/일/rolling window 등 quota 기간
- 신규 회원 기본 한도와 무제한·관리자 면제 여부
- 요청 시작·성공·예약 중 어느 시점에 차감할지
- 실패, 취소, timeout, 내부 retry/repair의 차감 의미
- 한도 초과 및 quota 저장소 장애의 HTTP 계약
- 정책 변경의 즉시/다음 기간 적용과 수동 조정 규칙
- 사용량·감사 데이터 보존 기간
- 결제 정책과 관리자 수동 override의 우선순위

이 목록은 8.0에서 한꺼번에 결정하지 않는다. 각 항목을 실제로 소비하는 최초 슬라이스의 브리프가
선택지·장단점·추천·후속 고려·범위 밖을 제시한다.
