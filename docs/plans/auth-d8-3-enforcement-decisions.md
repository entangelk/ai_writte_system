## 0. 이 브리프가 정하지 않는 것 (이미 결정됨)

- **시행 방식 = D7=A**: FastAPI dependency + **전수 가드**. 미들웨어·서비스층은 이미 배제됐다(근거는 인증 브리프 D7).

- 따라서 아래는 **"어떻게 잠글까"가 아니라 "무엇을 어떤 의미로 잠글까"**만 다룬다.

## 2. 결정 항목

### E1 — `owner_id=None`(주인 없는 프로젝트)을 인가가 어떻게 다루는가 ★ 착수 차단

가장 중요한 결정이다. **"소유자 불일치면 거부"만 구현하면 주인 없는 데이터가 전부 열리거나 전부 닫힌다** — 어느 쪽인지가 코드에 우연히 결정되게 두면 안 된다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. dev 데이터 폐기 후 clean slate (추천)** | D4가 폐기를 허용하므로 현 dev 데이터를 비우고 시작. 코드는 `owner_id=None`을 **거부(deny)**로 처리 | legacy 문제 자체가 사라진다 · 가장 단순 · fail-closed | 실 창작물이 쌓인 뒤에는 못 쓴다 |
| B. `None` = 전부 허용 | 기존 데이터 접근 유지 | 호환 | **보안 구멍** — 누구나 무소유 데이터 열람. 배제 |
| C. `None` = 전부 거부(데이터는 보존) | 가장 안전 | 안전 | 오너 본인도 legacy 데이터에서 잠긴다(폐기와 실질 동일하되 데이터는 남음) |
| D. `None` → 부트스트랩 관리자 귀속 마이그레이션 | 무소유를 admin 소유로 이관 | 실 데이터 보존 | 마이그레이션 비용. 인증 브리프 D4가 **"실 데이터가 쌓인 뒤"**를 위해 예약해 둔 선택지 |

**추천: A.** 지금 DB에 있는 것은 개발 테스트 데이터뿐이고(오늘 볼륨을 한 번 비웠으며 현재 `owner` 계정 1개 + 프로젝트 소량), D4가 명시적으로 폐기를 허용했다. 실 창작물이 쌓이면 D로 전환한다.

**단, A를 골라도 코드가 `None`을 deny로 다루는 것은 선택이 아니라 필수다.** 폐기는 "지금 그런 행이 없다"를 보장할 뿐 "앞으로 생기지 않는다"를 보장하지 않는다 — 2b가 익명 생성을 여전히 허용하므로(D8-3 전까지) `None` 행은 계속 생길 수 있고, 그때 열려 있으면 그게 곧 우회로다.

### E2 — 인증만 요구할 곳 vs 소유권까지 볼 곳

64개가 다 같은 성격이 아니다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. project 경로는 소유권, 그 외는 인증 (추천)** | `/projects/{project_id}/…`는 소유자 검사, `POST /projects`·`GET /projects`처럼 특정 project를 지목하지 않는 것은 인증만(+목록은 본인 것만 반환) | 실제 위험(남의 원고 열람)에 정확히 대응 · 검사 지점이 project 조회 한 곳으로 수렴(D3=A의 설계 의도) | `GET /projects`의 필터링을 잊으면 목록으로 남의 project id가 샌다 |
| B. 전부 인증만 | 로그인만 하면 다 열림 | 단순 | **다중 사용자의 의미가 없다** — 격리가 목적인데 격리가 안 된다 |
| C. 전부 소유권 | 일괄 | project를 지목하지 않는 endpoint에는 검사할 대상이 없어 성립하지 않음 | |

**추천: A.** 그리고 **`GET /projects`가 본인 것만 반환하도록 바꾸는 것을 E2에 포함**한다 — 이것을 빼면 "격리했다"는 주장이 목록에서 곧바로 무너진다.

### E3 — D8-3을 어떻게 쪼갤 것인가

오너 지시("작은 단위로 차례차례")에 따라 64개를 한 번에 잠그지 않는다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 3-a 인증 dependency → 3-b 소유권 + 목록 필터 → 3-c 전수 가드 (추천)** | 먼저 "로그인 필요"를 붙이고(전 대상 401), 다음에 소유권(403), 마지막에 빠뜨림을 잡는 전수 가드 | 각 단계가 독립적으로 green · 실패 시 되돌릴 지점이 명확 | 3단계 동안 프론트가 깨져 있다(E4와 함께 봐야 함) |
| B. 한 번에 | 커밋 하나 | 64개 operation + 프론트 + 전수 가드가 한 덩어리 — 실패 원인 분리 불가 | |
| C. endpoint 그룹별(core_sot → analysis → writing …) | 점진 | 그룹 사이 기간에 **일부만 잠긴 상태**가 되어 "무엇이 보호되는지"를 아무도 말할 수 없다 | |

**추천: A.** 다만 **전수 가드(3-c)를 마지막에 두되 3-a와 3-b 각각에 자기 단계의 가드를 함께 넣는다** — 관측 페이즈에서 실측된 "배선을 빠뜨려도 green"이 인가에서 반복되면 결과가 데이터 유출이다.

### E4 — 프론트가 깨져 있는 기간을 어떻게 다룰 것인가 ★

**D8-3이 들어가는 순간 프론트는 로그인 화면이 없어 전부 401을 받는다.** 로그인 UI는 D8 순서상 step 4다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. D8-4(로그인 화면)를 D8-3보다 먼저 (추천)** | 화면·세션 처리·401 리다이렉트를 먼저 만들고, 그다음 백엔드를 잠근다 | 잠그는 순간 제품이 계속 동작한다 · 로그인 UI는 지금도 `/auth/*`로 **실제 테스트 가능**(1c 완료) | D8 브리프의 번호 순서와 다르다(순서는 제안이지 계약이 아니다) |
| B. 순서대로 3 → 4, 그 사이는 깨진 채로 | 브리프 순서 유지 | 백엔드 보안이 먼저 닫힌다 | 로컬 1인 개발이라 "깨진 기간"의 실해는 작지만, **dogfood를 그 기간에 못 한다** |
| C. 시행에 env 플래그(기본 off) | 켜고 끄며 이행 | 무중단 | **꺼진 채로 배포되는 것이 곧 무인증**이고, 플래그는 지워지지 않고 남는다 |

**추천: A(순서 교환).** D8 순서는 인증 브리프가 "제안"으로 적은 것이고, 1c가 이미 `/auth/*`를 실동작시켜 **로그인 화면을 지금 만들어 실제로 로그인/로그아웃까지 확인할 수 있다**. C는 명시적으로 피한다 — 보안 스위치를 기본 off로 두는 것은 이 저장소가 관측 페이즈에서 배운 "빠뜨려도 green"의 보안판이다.

## 3. 구현자 선결(오너 이견 없으면 이대로)

- **상태코드**: 미인증 = **401**, 인증됐으나 비소유자 = **403**. 표준이고, 비-목표 전수 가드가 두 코드 모두를 신호로 삼으므로(D8-2 검증 H-2 반영) 어느 쪽을 써도 가드가 정상 발화한다.
- **`/health`는 계속 무인증**. compose healthcheck가 로그인을 못 한다.
- **404 vs 403**: 남의 project에 대해 존재를 숨길지(404) 드러낼지(403). 지금은 **403**으로 간다 — 단일 사용자 → 소수 사용자 단계에서 존재 은닉의 실익이 작고, 404로 통일하면 "없음"과 "권한 없음"을 로그에서 구분 못 한다. 필요해지면 좁히는 방향은 언제든 additive다.

## 4. Follow-up considerations (열어 둘 문)

- **E1=A를 골라도 D는 죽지 않는다**: 실 창작물이 쌓인 뒤 다시 무소유 행이 생기면(예: 마이그레이션 실수) D의 귀속 스크립트가 필요하다. 전환 조건 = "폐기해도 되는 데이터가 아니게 된 시점".
- **관측 KPI의 사용자 축**: 인가가 들어오면 "누가 얼마나 썼나"가 자연스럽게 질문이 되지만, `llm_call_audits`에 `owner_id`를 넣는 것은 계측 계약을 넓히는 별도 결정이다(인증 브리프 Follow-up에 이미 있음).
- **인프라 인증(D8-7)**: Mongo·ES 무인증은 여전히 열려 있다. 워커가 Mongo에 **직접** 붙으므로, 그때는 HTTP 인가와 달리 **워커 자격증명이 실제로 필요하다**.

## 5. Deferred / out of scope

- 관리자 API·화면(D8-5), 영구 삭제(D8-6), 인프라 인증(D8-7) — 각자 슬라이스.
- 공유·협업·권한 등급 — 미래 확장(D3=A가 문만 열어 둠).
- `owner_id`의 공개 payload 노출(2c) — 프론트가 읽을 이유가 생길 때.
