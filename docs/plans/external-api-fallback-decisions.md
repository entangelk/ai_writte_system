# 외부 API 키 폴백 (키 회전 · 모델 폴백) 결정 브리프

상태: `오너 정책 확정(2026-08-22, §0) · 구현 완료(같은 날 — 슬라이스 8단계, 일지 참조)`
계기: 오너 요청(2026-08-22) — *"외부 API를 위한 폴백 장치… api키들을 리스트로 제공(1개만 제공되어도 상관없도록)… 모델들도 리스트로(0번째가 기본, 이후 폴백 모델)… 키당 기본 rpm 30회… 폴백이 진행되었을 때 1순위는 키변경, 2순위는 모델 변경… 키가 abc 모델이 12면 a1 b1 c1 a2 b2 c2."*
부모: [`plans/external-api-expansion-decisions.md`](external-api-expansion-decisions.md)(D1~D6, 2026-07-27). 이 슬라이스는 그 §4가 유예해 둔 **"429·401·5xx를 기존 taxonomy에 어떻게 매핑할지"**를 닫는다.

## 0. 오너 정책 (2026-08-22)

1. **키 리스트** — env로 제공, **1개만 있어도 정상 동작**. 시작 키는 **라운드로빈 배분**¹.
2. **모델 리스트** — `models[0]` = 기본, 이후 = 폴백 모델.
3. **키당 기본 RPM 30** — 슬라이딩 60초 창(요청 시작 시각 기록).
4. **폴백 순서** — ① 키 교체 → ② 모델 교체. keys=`[a,b,c]`·models=`[1,2]`의 표준 시도 순서: **a1 → b1 → c1 → a2 → b2 → c2**.
5. **전 조합 소진 시 fail-fast** — 대기하지 않고 retryable 오류로 즉시 반환.
6. **범위** — LLM 게이트웨이(키×모델) + 임베딩(**키만**) + 리랭커(**키만**).

> ¹ 최초 안은 "시작 키 랜덤"이었으나 같은 날 오너가 정정했다 — *"랜덤이라기보다는 라운드로빈 배분으로, 한 곳으로 집중되지 않게"*. 랜덤은 통계적으로만 분산되고 라운드로빈은 정확히 분산한다. 배분이 곧 RPM 예산이므로 정확한 쪽이 맞다.

임베딩 모델 폴백이 없는 근거: 임베딩 모델을 바꾸면 **차원이 변하고 재색인이 필요**하다 — 그 길은 차원 가드 설계([`embedding-adapter-slice-decisions.md`](embedding-adapter-slice-decisions.md) 결정 3=A fail-fast + 수동 재색인)가 일부러 막아 둔 길이다.

## 1. 구현 결정 (정책을 코드에 옮기며)

- **`KEY_REJECTED`(401/403) 신규 코드** — "요청이 거부됨"(`REQUEST_REJECTED`)과 "키가 거부됨"을 갈라야 폴백이 "키를 바꾸면 고쳐진다"를 판단할 수 있다. `retryable=False`지만 **키 치명**이므로 폴백 루프 안에서는 회전한다(플래그는 "이 요청을 그대로 재시도하면 되는가"라는 앱 쪽 계약 — 두 질문이 다르다).
- **KEY_REJECTED → HTTP 502**(게이트웨이 표면). 401이 아닌 이유: 게이트웨이의 클라이언트(앱)는 게이트웨이에 자격증명이 없다 — 401은 "너의 인증을 고쳐라"라는 거짓 메시지. 실패한 자격증명은 게이트웨이→상류 방향이므로 502가 정직하다.
- **쿨다운** — 401/403 = 600초(잘못된 키는 60초 뒤에도 잘못됐다), 429 = 60초(슬라이딩 창과 같은 길이). timeout/5xx는 쿨다운 없이 그냥 다음 조합.
- **요청이 명시한 모델은 체인의 첫 순위** — 앱이 `LLM_GATEWAY_MODEL`을 요청에 싣는 일이 흔하므로(main.py 8곳), 명시 모델이 env 체인을 덮어쓰는 게 아니라 **앞장서고 env 모델은 뒤따르는 폴백**이 된다(중복 제거).
- **체인 전체가 하나의 시간 예산을 공유** — 게이트웨이는 `asyncio.timeout(LLAMA_TIMEOUT_SECONDS)`, 임베딩·리랭커는 첫 시도 후 deadline 점검. N 조합이 시도당 타임아웃을 N배로 불리는 것을 막는다(1b(B1)이 이미 겪은 "성공한 생성이 timeout으로 뒤집히는" 실패의 예방).
- **소진 시 오류** — 시도가 0개(전부 RPM/쿨다운)면 `OVERLOADED` retryable(임베딩은 status 429) → 인덱스 재시도 backoff(60/300s)·리랭커 fail-open과 자연 조합. 시도는 했으나 전부 실패면 **마지막 오류 그대로**(진단 보존).
- **env 이름** — `LLAMA_API_KEYS`·`LLAMA_MODELS`·`LLAMA_KEY_RPM`(+ `EMBEDDING_`·`RERANK_` 축의 `*_API_KEYS`·`*_KEY_RPM`). 부모 브리프 §3이 스케치한 `LLM_API_KEY`(단수)를 **대체**한다 — 현행 `LLAMA_*` family와의 일관성이 스케치의 우선순위를 이긴다(스케치는 착수 전 추정 표면이었다).
- **compose 표기** — 리스트 변수는 대시(빈 값 = unset), RPM 변수는 콜론 `:-30`(`_env_float`은 빈 값에 `float("")` 크래시). [`tests/test_compose_backend_env.py`](../../tests/test_compose_backend_env.py) 표기 셀이 잠근다.
- **로그 위생** — 실패 시도는 `key_index` + 모델명 + 오류 코드만 남긴다. 게이트웨이의 `FallbackProvider`는 **키 값을 아예 모른다**(구조적 비유출).
- **무설정 무변** — 키 ≤1 且 모델 ≤1이면 래퍼·계수기 없이 오늘의 단일 provider. 로컬 llama 배포는 아무 대가도 지불하지 않는다(over-strict 총괄 가드가 잠금).

## 2. 유예 / out of scope

- **창이 큰 폴백 모델이 `CONTEXT_WINDOW_EXCEEDED`을 살리는 길** — 지금은 즉시 중단(왕복 비용 0인 우리 가드 거부를 폴백에 쓰는 것은 비용 역전). 필요가 관측되면 모델 체인에 "창 조건"을 다는 형태로.
- **call-site별 모델 오버라이드** — 부모 D4 후속, 설계만 열려 있다.
- **`Retry-After` 헤더 존중** — 429 쿨다운은 고정 60초. 실제 벤더 응답을 보고 나서.
- **소진 시 대기 모드** — 오너가 fail-fast를 골랐다(2026-08-22).
- **키별 개별 RPM** — 지금은 전역 기본값 하나(`*_KEY_RPM`).
- `/health/ready`의 upstream `GET /health` 비인증 프로브 — 기존 부채(`docker-compose.external.yml` 말미에 기록).
