## 0. 문제

관리자가 회원별 한도·사용량을 **운영할 수 있는 표면이 없다**. 현재 정책 행을 만지는 유일한
수단은 `create_user.py`(부트스트랩 시 무제한 행)과 mongo 직접 수정이다. 특히 **정지
(`SUSPENDED`)는 8.3이 시행까지 해 둔 상태(403, Q5=B)인데 켜고 끄는 관리자 수단이 없어
죽어 있는 기능**이다. 결제(8.6)를 붙이기 전에 수동 운영 경계가 먼저여야 한다(부모 계획 §6).

## 1. 결정 D1 — endpoint 집합: 조회 + 한도 변경 + 정지/해제 (오너 ⓒ)

> 오너 원문 선택: **"조회+한도+정지 (추천)"** (2026-08-23, 구현자 브리프 3옵션 중)

- **조회**: 전 회원 정책·사용량 목록 + 개별 상세. 정책이 없는 회원도 나온다(코드 기본
  일 20/주 100 해석 — `limits_for`가 그 값을 준다).
- **한도 변경**: 일·주 각각 값 또는 `null`(무제한). **P6 발효 규칙은 도메인 그대로**(D2).
- **정지/해제**: `SUSPENDED` 토글 — **즉시 발효**. "긴급 차단"의 역할은 여기가 담당한다
  (한도 축소의 창 경계 유예와 역할이 분리된다).

각하된 대안: ⓐ 조회만(정치적 운영이 스크립트에 남는다 — 각하), ⓑ 조회+한도만
(SUSPENDED가 죽은 기능으로 남는다 — 각하). ⓒ가 부모 계획이 명시한 전 범위다.

**개인정보 노출 범위 (부모 계획 축)**: 목록·상세가 싣는 것은 **한도·정책·현재 창 사용량
횟수**뿐이다. 요청 내용·project 분해·원장 상세 이력은 싣지 않는다(회원이 `/me/quota`로
자기 상세를 보는 것과 대칭 — 관리자 표면은 운영 요약).

## 2. 결정 D2 — 한도 변경 발효: 도메인 P6 그대로 (오너 ⓐ)

> 오너 원문 선택: **"도메인 P6 그대로 (추천)"**

`set_limits`의 현행 규칙을 API도 그대로 탄다 — **유리한 변경(완화)은 즉시, 불리한 변경
(축소)은 다음 창 경계에 발효하는 `pending` 예약**(예약은 한 건, 새 예약이 앞 것을 덮는다).
창 중간에 한도를 줄이면 이미 쓴 사용량과 충돌하는데, 그 상태를 API 층에서 만들지 않는다.
긴급 차단이 필요하면 한도가 아니라 **정지**(즉시)를 쓴다 — 두 역할의 분리가 이 결정의 요점.

각하된 대안: ⓑ 관리자가 발효시점을 고르는 옵션 — "이미 쓴 사용량 > 새 한도" 상태를
만들 수 있어 각하.

## 3. 결정 D3 — 감사: 변경(한도·정지·해제)만 기록, 사유 필수 (오너 ⓑ)

> 오너 원문 선택: **"변경만 기록 (추천)"**

- **조회는 미기록** — 계정·프로젝트 목록 조회 관례(`GET /admin/users`·`GET /admin/projects`)와
  같다. 읽기가 감사를 만들면 목록 polling이 감사를 채운다.
- **한도 변경·정지·해제는 `admin_audit_events`에 기록** — 사유 필드 필수(purge·승격과 같은
  형식). 과금·서비스 영향 조작이라 이력 가치가 있다. `admin_audit_events` 확장이 "별도 명시
  결정"(`routers/admin.py` 설계 주석)이었는데 이 결정이 그 명시 결정이다. **기록은
  fail-closed**(승격 사용 감사와 같다 — 쓰기 실패가 요청을 죽인다)로 간다. 단 **정지→해제
  처벌 이력 오남용 방지**를 위해 감사 행에는 사유와 변경값만 남기고 원장·사용량 스냅샷은
  남기지 않는다.

각하된 대안: ⓐ 전부 미기록(계정 조작 관례) — 운영상 "누가 언제 왜 줄였는지"가 안 남아
각하.

## 4. 계약 세부 (구현 지침)

- **endpoint 4종 (ADMIN tier, operation 11 → 15)**:
  - `GET /admin/quota-policies` — 목록. 회원별 `username`·유효 한도·status·**현재 창 사용량
    횟수**(일·주)·보류 중 예약 유무. `/admin/users`의 회원 목록과 join하지 않고 policy
    주체로 나열하되 **정책 행이 없는 활성 회원도 기본 한도 해석으로 포함**한다(운영 목록의
    완전성 — 없는 회원이 조용히 빠지면 "무제한인 줄 알았는데 기본 20" 사고가 안 보인다).
  - `GET /admin/quota-policies/{user_id}` — 상세. **`policy.limits`를 그대로 내놓지 않는다** —
    응답의 "지금 유효한 한도"는 반드시 `effective_limits`/`limits_for` 산출값이고 진단용
    `stored_limits`·`pending`(남은 경우)을 별도 필드로 명시한다(`QuotaPolicy` docstring 경고:
    만료된 예약이 "대기 중"으로 보임 — 2026-08-03 검증 H2가 이 슬라이스를 겨눠 남긴 것).
  - `POST /admin/quota-policies/{user_id}/limits` — 한도 변경(사유 필수). 요청은
    `daily_limit`·`weekly_limit`(정수 또는 `null`), 발효는 D2.
  - `POST /admin/quota-policies/{user_id}/suspend` · `/activate` — 정지·해제(사유 필수,
    즉시). **해제는 quota 상태만 되돌린다** — 계정 비활성화(단방향, D6)와는 별개 축이다.
- **상태코드**: 401(세션 없음)·403(비관리자)·404(없는 회원)·400(잘못된 한도 값 — 음수·
  비정수·둘 다 미지정)·200(전부; 변경 응답에 유효 한도·`pending` 반영 결과를 실어 즉시
  확인 가능하게). 새 literal 없음.
- **가드(회귀)**: ADMIN tier 전수 가드 등재(11→15)·에러 선언 전수·사유 필수 단정·
  `policy.limits` 직접 노출 금지(H2 — 응답 스키마 단정)·감사 fail-closed 양방향·
  P6 발효 경계(완화 즉시/축소 예약)·정지 즉시(다음 요청 403)·정책 없는 회원 포함.
- **시행 슬라이스 (오너 "잘게" 원칙)**:
  - **8.5-a**: 조회 2종 + 가드. 감사 없음(읽기).
  - **8.5-b**: 한도 변경·정지/해제 3종 + 감사 + 가드.
  - (관리자 콘솔 UI 화면은 백엔드 확정 뒤 별도 슬라이스 — 5-d의 콘솔에 붙인다.)
- **범위 밖**: 8.6 결제 entitlement seam(우선순위: 수동 정책이 먼저)·원장 상세 이력 화면·
  프로젝트별 사용량 분해·회원별 과거 이력 그래프.
