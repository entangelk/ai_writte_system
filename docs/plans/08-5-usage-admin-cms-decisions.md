## 0. 문제 — 무엇이 유도되지 않는가

관리자가 회원별 한도·사용량을 **운영할 수 있는 표면이 없다**. 현재 정책 행을 만지는 유일한 수단은
`create_user.py`(부트스트랩 시 무제한 행)과 mongo 직접 수정이다. 특히 **정지(`SUSPENDED`)는 8.3이
시행까지 해 둔 상태(403, Q5=B)인데 켜고 끄는 관리자 수단이 없어 죽어 있는 기능**이다. 결제(8.6)를
붙이기 전에 수동 운영 경계가 먼저여야 한다(부모 계획 §6).

어디까지 만들지·변경이 언제 발효할지·무엇을 감사에 남길지는 코드에서 유도되지 않는 오너 정책
선택이다 — 그래서 이 브리프의 셋이다.

## 2. D1 — endpoint 집합

**질문**: 관리자 quota 운영 표면을 어디까지 만드는가?

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 조회만** | 전 회원 정책·사용량 목록 + 개별 상세. 한도 변경·정지는 현행대로 스크립트·mongo 직접 | 구현 가장 작음. 읽기라 감사·사유 논쟁 자체가 없음 | 한도 운영이 계속 비API 수단(mongo 직접)에 남는다 — 실수 위험이 운영의 일상이 된다. **SUSPENDED는 계속 죽은 기능** |
| **ⓑ 조회 + 한도 변경** | ⓐ + 일/주 한도 변경(무제한 포함). 정지는 계정 비활성화(D6)로 대체 | 운영의 대부분(한도 조정)을 API로. P6 발효 로직 재사용이라 도메인 추가가 없다 | 정지가 비활성화(단방향·재활성화 API 없음)와 강결합 — "잠깐 막고 싶다"가 "영구 끊기"만 남는다. 8.3이 시행해 둔 403 정지 체계와 표면이 어긋난다 |
| **ⓒ 조회 + 한도 변경 + 정지/해제** ⭐ | ⓑ + `SUSPENDED` 토글(즉시 발효, 가역) | 부모 계획이 명시한 전 범위. **죽어 있는 정지 기능에 손이 생긴다.** "긴급 차단(즉시)"과 "한도 축소(창 경계)"의 역할 분리가 자연스럽게 선다. 도메인 재사용만으로 완결 | 구현 가장 큼(그래서 8.5-a/b로 분할). 비활성화와 정지 두 개의 "막는" 수단이 공존해 운영자 교육이 필요(아래 §4 note) |

**구현자 추천: ⓒ** — 정지는 이미 도메인·시행이 다 서 있는데 관리자 수단만 없는 상태(죽은 기능)라
만들지 않을 이유가 없고, 긴급 차단 수단이 없으면 D2의 유예 정책이 실전에서 곤란해진다.

**오너 결정: ⓒ** (2026-08-23).

**개인정보 노출 범위 (부모 계획 축)**: 목록·상세가 싣는 것은 **한도·정책·현재 창 사용량 횟수**뿐.
요청 내용·project 분해·원장 상세 이력은 싣지 않는다(회원이 `/me/quota`로 자기 상세를 보는 것과
대칭 — 관리자 표면은 운영 요약).

## 3. D2 — 한도 변경의 발효 시점

**질문**: 관리자가 한도를 바꾸면 언제 유효해지는가?

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 도메인 P6 그대로** ⭐ | 현행 `set_limits` 규칙 재사용 — **유리한 변경(완화)은 즉시, 불리한 변경(축소)은 다음 창 경계에 발효하는 `pending` 예약**(예약 한 건, 새 예약이 덮음) | 이미 구현·검증된 로직이라 새 코드 0줄. **"이미 쓴 사용량 > 새 한도" 상태를 구조적으로 못 만든다.** 회원 경험 예측 가능(창이 바뀌면 새 한도) | 긴급하게 줄이고 싶어도 창 경계까지 기다려야 한다 — 그 틈은 정지(즉시)로 메워야 한다. 관리자가 "즉시 반영 안 되나?"로 오해할 수 있어 응답에 발효 시각을 명시해야 함 |
| **ⓑ 관리자가 발효 선택** | 요청에 즉시/예약(시각)을 실어 도메인 P6을 API 층에서 우회 | 긴급 축소가 가능. 예약 시각을 임의로 잡을 수 있음 | **"이미 쓴 사용량 > 새 한도"를 만들 수 있다** — 그 창의 남은 시간 동안 정상 요청이 전부 402가 되는 회원 경험 사고. P6의 존재 이유를 API 층에서 무너뜨린다. 시행·가드가 복잡해진다 |
| ⓒ 전부 즉시 강제 | 관리자 변경은 무조건 즉시 | 가장 단순 | ⓑ의 결함을 항상 발생시키는 형태라 표에서 제외(ⓑ의 극단) |

**구현자 추천: ⓐ** — 긴급 차단의 역할은 D1ⓒ의 정지(즉시)가 이미 담당하므로 한도 축소까지 즉시일
이유가 없다. 두 역할의 분리("정지=지금 막기, 한도=다음 창부터")가 운영 모델을 오히려 단순하게
만든다.

**오너 결정: ⓐ** (2026-08-23).

## 4. D3 — 변경의 감사

**질문**: 관리자의 quota 조작을 감사(`admin_audit_events`)에 남기는가?

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 전부 미기록** | 계정 관리 조작(생성·비활성화·승인) 관례를 그대로 따름 | 구현 최소. 관례 일관 | **"누가 언제 왜 한도를 줄였는지"가 아무 데도 안 남는다** — 과금·서비스 영향 조작인데 이력 부재는 운영 사고 조사를 불가능하게 한다 |
| **ⓑ 변경만 기록** ⭐ | 한도 변경·정지·해제만 `admin_audit_events`에 기록(사유 필수, fail-closed). 조회는 미기록 | 이력 가치(과금 영향 조작)와 실용(읽기가 감사를 채우지 않음)의 균형. 사유 필수 절차는 purge·승격과 같은 형태라 관례 확장이 자연스럽다 | `admin_audit_events`가 "프로젝트 내용 예외" 설계에서 "회원 정책 조작"까지 덮게 됨 — 컬렉션 지위 확장(아래 note). 구현+가드가 ⓐ보다 크다 |
| ⓒ 조회까지 전부 기록 | 읽기·쓰기 모두 감사 | 가장 완전한 이력 | 관리자 콘솔의 목록 polling 한 번에 감사 행이 계속 쌓인다 — 노이즈가 진짜 이력을 묻는다. `GET /admin/users`·`GET /admin/projects`의 기존 관례(목록 조회 미기록)와도 어긋난다 |

**구현자 추천: ⓑ** — 읽기 미기록은 이 저장소의 목록 조회 관례와 같고, 쓰기 기록은 purge·승격의
사유 필수 관례와 같다. 둘 다 기존 패턴의 연장이라 새로운 정책 발명이 아니다.

**오너 결정: ⓑ** (2026-08-23).

> **note — 감사 컬렉션 지위**: `routers/admin.py` 설계 주석은 감사 컬렉션을 "프로젝트 내용 예외
> (purge·grants)만 커버"로 못박고 확장을 "별도 명시 결정"으로 남겨 뒀다. **이 D3=ⓑ가 그 명시
> 결정이다** — 회원 정책 조작(한도·정지)이 네 번째 감시 대상으로 추가된다. 감사 행에는 사유와
> 변경값만 남기고 원장·사용량 스냅샷은 남기지 않는다(이력 오남용 방지).

## 5. 계약 세부 (구현 지침)

- **endpoint 5종 (ADMIN tier, operation 11 → 16)** —
  (초판 표기 "4종/15"는 산수 오류였다: 조회 2 + 변경·정지 3 = 5종.)
  - `GET /admin/quota-policies` — 목록. 회원별 `username`·유효 한도·status·**현재 창 사용량
    횟수**(일·주)·보류 중 예약 유무. **정책 행이 없는 활성 회원도 기본 한도 해석으로 포함**한다
    (없는 회원이 조용히 빠지면 "무제한인 줄 알았는데 기본 20" 사고가 안 보인다).
  - `GET /admin/quota-policies/{user_id}` — 상세. **`policy.limits`를 그대로 내놓지 않는다** —
    응답의 "지금 유효한 한도"는 반드시 `effective_limits`/`limits_for` 산출값이고 진단용
    `stored_limits`·`pending`(남은 경우)을 별도 필드로 명시한다(`QuotaPolicy` docstring 경고:
    만료된 예약이 "대기 중"으로 보임 — 2026-08-03 검증 H2가 이 슬라이스를 겨냎해 남긴 것).
  - `POST /admin/quota-policies/{user_id}/limits` — 한도 변경(사유 필수). 요청은
    `daily_limit`·`weekly_limit`(정수 또는 `null`), 발효는 D2=ⓐ.
  - `POST /admin/quota-policies/{user_id}/suspend` · `/activate` — 정지·해제(사유 필수,
    즉시). **해제는 quota 상태만 되돌린다** — 계정 비활성화(단방향, D6)와는 별개 축이다.
- **상태코드**: 401(세션 없음)·403(비관리자)·404(없는 회원)·400(잘못된 한도 값 — 음수·비정수·
  둘 다 미지정)·200(전부; 변경 응답에 유효 한도·`pending` 반영 결과·발효 시각을 실어 즉시
  확인 가능하게). 새 public literal 없음.
- **가드(회귀)**: ADMIN tier 전수 가드 등재(11→16)·에러 선언 전수·사유 필수 단정·
  `policy.limits` 직접 노출 금지(H2 — 응답 스키마 단정)·감사 fail-closed 양방향·
  P6 발효 경계(완화 즉시/축소 예약)·정지 즉시(다음 요청 403)·정책 없는 회원 포함.
- **시행 슬라이스 (오너 "잘게" 원칙)**:
  - **8.5-a**: 조회 2종 + 가드. 감사 없음(읽기). — **완료**(v1.8.1).
  - **8.5-b**: 한도 변경·정지/해제 3종 + 감사 + 가드. — **완료**(v1.8.2).
  - 구현이 정밀화한 것: **suspended 회원의 한도 변경은 status 를 유지한다**(`set_limits` 는 status 미지정을 ACTIVE 로 해석)·정지는 **`set_status`(신규)** 로 즉시 — P6 가 상태까지 유예하므로 `set_limits` 와 갈랐다.
  - (관리자 콘솔 UI 화면은 백엔드 확정 뒤 별도 슬라이스 — 5-d의 콘솔에 붙인다.)

## 6. 후속 고려

- **8.6 결제 entitlement seam**이 정책을 기계로 바꿀 때 수동 정책(이 API)과의 우선순위·충돌
  규칙이 새 결정이 된다(부모 계획 §4 8.6 행) — 이 슬라이스는 수동 우선(결제 없음)을 전제한다.
- 감사 행이 쌓이면 관리자 콘솔의 "정책 변경 이력" 화면으로 이어질 수 있다(감사 컬렉션 재사용).
- 프로젝트별 사용량 분해·과거 이력 그래프는 요청이 생길 때 별도 브리프.

## 7. 범위 밖 (이 슬라이스가 정하지 않는 것)

- 결제·구독·CMS 프론트(8.6 — entitlement seam 계약만 별도 브리프)
- 원장 상세 이력 화면·요청 내용 노출(개인정보 범위가 횟수 요약으로 못박았다)
- 회원 자기 서브의 quota 화면 개선(`/me/quota`는 그대로)
- 계정 비활성화 절차(D6 단방향 — 정지와 별개 축으로 유지)
