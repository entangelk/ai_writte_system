## Decision needed

**개인 페이지를 무엇으로 만들 것인가** — 오너가 *"개인 페이지잖아? 프로젝트 페이지가 아니고?
그러면 **전체 통합이어야지**. … 개인페이지 허브에서 **프로젝트 별로 뻗어나가는** 거지"* 로
방향을 못박았다(2026-08-10). **그 한 문장이 backend 새 표면을 부른다.**

**왜 스펙에서 유도할 수 없는가.** 지금 활동(operation 77)도 관측 KPI 도 **전부 project-scoped**
이고, **사용자 전역 조회는 이 저장소에 존재하지 않는다.** 관리자 전역 조회(A5=C)는 *"관리자에게
project 내용을 여는 문"* 이라 일부러 유예됐는데, **사용자 전역은 그 반대 축**(자기 것만 본다)이라
같은 이유로 막히지 않는다 — 그러나 **무엇을 합치고 어디서 자를지는 아무도 정한 적이 없다.**

## P1. ★ 통합 활동을 어떻게 얻는가 (이 슬라이스의 중심)

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 새 endpoint `GET /me/activity`** | 서버가 내 프로젝트 전체를 합쳐 최신순으로 준다 | **한 번의 요청** · 정렬·상한이 서버에서 정확하다 · 프로젝트가 늘어도 화면은 그대로 | operation **77 → 78** · `schema.d.ts`·tier 가드·경계 행렬이 함께 움직인다 · 저장소 쿼리(`project_id in [...]`) + 인덱스 확인 |
| ⓑ 프론트 fan-out | `GET /projects` 뒤 프로젝트마다 `/activity` 호출해 클라이언트에서 병합 | **backend 0줄** · 계약 무변 · **N ≤ 100 이면 top-N 이 정확하다**(아래 ★) | **N+1 요청**(프로젝트 11개면 12번) · 각 100건을 받아 버리는 대역폭 · **전역 총건수를 모른다**(화면이 "전체에서 몇 건 중"을 말할 수 없다) · **정확성이 상한 100 에 묶인다** — 통합 상한을 101 로 올리거나 F1 페이징을 열면 **조용히 틀려진다** · 프로젝트가 늘수록 요청이 는다 |
| ⓒ 링크 허브 | 통합 없이 프로젝트별로 뻗기만 | 가장 싸다 | **오너가 이미 기각했다**(*"전체 통합이어야지"*) |

### ★ 초판의 "정확성" 논거는 틀렸다 (2026-08-10 독립 검증이 반증, 구현자 재확인)

**초판은 이렇게 적었다** — *"프로젝트마다 100건으로 자른 뒤 합치면 '전체에서 최근 20건'이 실제로
최근 20건이 아닐 수 있다 … ⓑ 의 치명적인 점은 비용이 아니라 정확성이다."* **이것이 거짓이다.**

**증명**(검증 세션 제시, 구현자 재확인): 전역 top-N(N ≤ 100)의 임의 사건 `e` 가 프로젝트 `P` 에
속한다고 하자. `P` 안에서 `e` 보다 새 사건은 **전역에서 `e` 보다 새 사건의 부분집합**이므로
`≤ N−1 ≤ 99` 개다. 따라서 `e` 는 `P` 안에서 100위 안이고 **`P` 의 응답에 반드시 들어온다.**
그러므로 합집합의 top-N = 진짜 전역 top-N 이다.

**실측**([`repro_fanout_topn.py`](../verifications/2026-08-10/repro_fanout_topn.py), 무작위 20,000회 ×2):

| 조건 | 반례 |
|---|---|
| **N ≤ 상한(100)** | **0 / 20,000** — fan-out 병합이 전역 top-N 과 완전히 일치 |
| N > 상한(100) | 3,181 / 20,000 |

**즉 이 브리프가 제안한 통합 상한(P2 의 "예: 50")에서는 ⓑ 도 정확했다.** 초판이 든 예시
(*"오래된 프로젝트의 100번째가 새 프로젝트의 1번째보다 최신"*)는 **참이지만 top-N 을 깨지 않는다** —
그 사건이 최근 창에서 올바르게 빠지는 것일 뿐이다. **"병합 풀의 나이 폭이 넓다"(참)와 "top-N 이
틀린다"(거짓)를 뒤섞은 오류**다.

**★ 그러나 경계는 실재한다**: ⓑ 의 정확성은 **프로젝트별 상한 100 에 묶여 있다.** 통합 상한을
101 로 올리거나 **F1(커서 페이징)을 여는 순간 조용히 틀려진다** — 그리고 그때 아무 신호도 없다.

### 권고: 여전히 ⓐ — 다만 근거가 다르다

**"치명적 정확성"이 아니라 저울질이다**:

| ⓐ 를 고르는 이유 | ⓑ 를 고를 수 있는 이유 |
|---|---|
| 오너가 못박은 것은 **진짜 통합 표면**이지 흉내가 아니다 | **backend 0줄 · 계약 무변** |
| **전역 총건수·정직한 단일 상한**을 서버가 말할 수 있다 | **1인 · 프로젝트 소수(현재 11개, 실사용 1~3개)** 면 요청 2~4번이고 top-N 도 정확하다 |
| **F1 커서가 여기서 자연스럽게 이어진다**(ⓑ 위에서는 페이징이 정확성을 깬다) | 지금 규모에서 체감 차이가 거의 없다 |
| N+1 이 프로젝트 수에 비례해 자란다 | |

**ⓐ 의 값은 operation 77 → 78 · `schema.d.ts` 재생성 · tier 전수 가드 · 경계 행렬 · 인덱스
확인이다.** 구현자는 여전히 ⓐ 를 권고하지만, **오너는 ⓑ 가 초판이 묘사한 것보다 훨씬 실행
가능하다는 것을 알고 고르는 편이 옳다** — 특히 프로젝트가 계속 소수로 남는다면.

**ⓐ 를 고르면 함께 정해야 하는 것**(아래 P2·P8)이 생기며, 그것이 이 브리프가 존재하는 이유다.

## P2. 통합 조회의 상한과 페이징 — **F1 이 여기서 걸린다**

프로젝트별 100 은 통합에서 의미가 없다. 9.1 은 *"먼저 보고 나서"* 로 F1(커서 페이징)을 미뤘는데,
**통합 뷰는 그 미룸이 먼저 아픈 자리**다(11개 프로젝트의 활동이 한 줄로 합쳐진다).

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 통합도 고정 상한(★ per-project 100 **이상**)** | 9.1 과 같은 형태 — 화면이 수를 말한다 | 일관 · 가장 싸다 · **기존 상한 연결 가드를 그대로 확장**한다 | 통합은 훨씬 빨리 찬다 |
| ⓑ 커서 페이징(F1 을 여기서 연다) | `?before=<at>` + tie-breaker `_id` | 진짜로 다 볼 수 있다 · **관측 `?since=` 와 관례를 함께 정한다** | 인덱스(`project_id, at`) 확인 · 화면 로직 증가 · 슬라이스가 커진다 |
| ⓒ 기간 창(`?since=`) | "최근 7일" | 사람이 이해하는 단위 · 관측과 같은 축 | 활동이 적은 사용자는 빈 화면 |

**권고: ⓐ 로 열고 ⓑ 는 트리거를 붙여 유예한다**(F1 갱신). 근거는 9.1 과 같다 — **통합 화면이
실제로 얼마나 빨리 차는지 아무도 본 적이 없다.** 다만 **ⓐ 를 고르면 상한 연결 가드를 통합
쪽에도 확장**해야 한다(`ActivityCeilingClaimTest` 와 같은 형태, 이번엔 새 서비스 기본값과).

**★ 상한 역전을 피할 것**(검증 지적): 초판은 *"예: 최신 50"* 이라 적었는데 그러면 **"전체" 화면이
"단일 프로젝트" 화면(100)보다 적게 보이는 역설**이 생긴다. **통합 상한은 per-project 이상**이어야
하고, 낮추려면 per-project 도 같이 낮춰 일관시켜야 한다. 덧붙여 **100 이 경계로 의미가 하나 더
있다** — P1-ⓑ 의 정확성이 정확히 그 수에 묶이므로, ⓑ 를 고르면서 통합 상한을 100 초과로 잡는
조합은 **성립하지 않는다.**

## P3. 관측(KPI)도 통합할 것인가

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 개인 페이지엔 진입만** | 프로젝트 선택기 → 기존 `/projects/:id/observability` | backend 0줄 · **386 kB lazy 경계를 안 건드린다** | "전체 통합"의 예외가 하나 생긴다 |
| ⓑ 사용자 전역 KPI 새 endpoint | `GET /me/observability/kpi` | 진짜 통합 · **`_fold` 를 그대로 쓴다**(`aggregate_global_kpi` 가 이미 project 집합을 접는다) | operation +1 · **집계의 뜻이 흐려진다**(프로젝트마다 다른 작업을 한 평균은 해석이 어렵다) |
| ⓒ 요약 타일만 | 개인 페이지엔 성공률 등 두어 개 | 가볍다 | 또 하나의 집계 정의가 생긴다 |

**권고: ⓐ.** 활동은 *"내가 언제 무엇을 했나"* 라 합쳐야 뜻이 살지만, **KPI 는 프로젝트 성격에
종속**된다(장편 report 와 짧은 gate 를 한 평균에 넣으면 둘 다 안 보인다). 오너의 "전체 통합"은
**활동 로그 맥락에서 나온 말**이라 읽었고, KPI 까지 합치라는 뜻인지는 **확인이 필요하다** —
아니라면 ⓐ, 맞다면 ⓑ 다(그 경우 `aggregate_global_kpi` 를 소유 프로젝트 집합으로 부르는 형태라
구현은 작다).

**★ 근거 정정**(검증 지적): 초판은 "해석이 흐려진다"를 **`/me` 쪽만의 문제**인 것처럼 적었는데,
**관리자 전역 KPI(`aggregate_global_kpi`)가 이미 전 프로젝트를 그렇게 접고 있다** — 그쪽이 더
이질적이므로 **루비콘은 이미 건넜다**. `/me`(소유 프로젝트만)는 오히려 **더 일관적인 모집단**이다.
따라서 ⓐ 를 권고하는 진짜 이유는 *"불가능해서"* 가 아니라 **① 지금 얻을 게 적고 ② 386 kB lazy
경계를 건드리며 ③ 세 번째 집계 소비자가 생기면 `_fold` 규칙 변경의 파급면이 넓어진다**는 것이다.

## P4. 개인 페이지의 구성과 주소

| 선택지 | 주소 | 담는 것 |
|---|---|---|
| **ⓐ `/me`** | 짧고 API(`/me/quota`)와 대칭 | 내 정보 · **잔여 사용량**(집이 생긴다) · 통합 활동 · 프로젝트 목록(진입) · 관측 진입 |
| ⓑ `/account` | 계정 설정 뉘앙스 | 위 + 비밀번호 변경 등 설정 |
| ⓒ `/dashboard` | 대시보드 뉘앙스 | 위 + 요약 지표 |

**권고: ⓐ `/me`.** 이 페이지의 주어가 *"나"* 이고 이미 `GET /me/quota` 가 그 이름을 쓴다. **비밀번호
변경 등 계정 설정은 이 슬라이스 범위 밖**으로 두되(지금 API 가 없다) ⓐ 는 나중에 그것을 받을 수 있다.

**★ 잔여 사용량이 여기 사는 것이 이 페이지의 첫 존재 이유다** — 지금 `useMemberQuota` 가 화면 없이
떠돌고, 8.4 가 남긴 *"한 번의 생성 클릭이 유료 요청 2~3건"* 이라는 사실을 사용자가 볼 데가 없다.

## P5. 관리자 로그인 랜딩

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ `is_admin` 이면 `/admin` 으로** | 로그인 성공 직후 리다이렉트 | 오너 요청 그대로 · 로그인 응답에 `is_admin` 이 이미 있다(실측) | 관리자가 자기 원고를 쓰려면 한 번 더 이동 |
| ⓑ 선택 화면 | "관리자 콘솔 / 내 작업" | 두 역할이 명시적 | 클릭이 는다 |
| ⓒ 그대로 | 프로젝트 목록 | 무변 | 오너가 바꾸자고 한 자리다 |

**권고: ⓐ + 셸에 상시 전환 링크**(관리자에게만 보이는 "내 작업 →"). 리다이렉트는 **로그인 직후
1회**여야 하고 `/admin` 을 고정 홈으로 만들면 안 된다 — 관리자도 저자다(이 제품에서는 같은 사람이다).

**★ 딥링크를 삼키지 말 것**(검증 지적): 관리자가 `/projects/X` 로 직접 들어와 세션이 없어 로그인
화면을 만난 경우, 로그인 직후 `/admin` 으로 보내면 **의도한 도착지가 사라진다**. 원래 목적지를
보존(`?next=`)하고 **그것이 있으면 그쪽이 이긴다** — 리다이렉트는 *목적지가 없을 때의 기본값*이다.

## P6. 로그인 화면과 랜딩

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **ⓐ 로그인 제품화 + 자리만 확보** | 제품명·한 줄 설명·시각 정체성. `AuthGate` 를 **보호 구간에만** 적용해 공개 route 를 끼울 수 있게 | 체감 문제의 대부분을 해결 · 랜딩은 **필요할 때** 페이지 하나 추가 | "소개 페이지"는 아직 없다 |
| ⓑ 소개 페이지 신설 | 공개 랜딩 + 별도 `/login` | 현대적 구성 | **설득할 상대가 아직 없다**(1인 · dogfood 미착수) · 지금 쓰면 공개 시점에 대부분 다시 쓴다 |
| ⓒ 그대로 | | 무변 | 오너가 지적한 자리 |

**권고: ⓐ.** 오너가 ⓑ 를 고르면 그대로 만든다 — 다만 **내용이 공개 시점에 바뀔 것**이라는 점을
알고 고르는 것이 좋다.

## P7. 이사한 뒤 프로젝트 화면에 무엇을 남기나

지금 원고 목록에 `개요` · `검토함` · `파이프라인 관측` · `활동 타임라인` 링크가 있다.

**★ 표기 정정**(검증 지적): 2026-08-10 에 제거된 것은 **`DraftList` 의 소유자 링크뿐**이고
**route 와 페이지는 살아 있다**([`App.tsx:33`](../../frontend/src/App.tsx#L33) — 관리자가 승격으로
도달한다). "접근 이력이 제거됐다"는 표현은 부정확하다.

| 선택지 | 설명 |
|---|---|
| **ⓐ 관측·활동 링크를 뗀다** | 프로젝트 화면은 저작에 집중. 둘 다 `/me` 에서 간다 |
| ⓑ 활동만 남긴다 | 그 프로젝트의 활동은 맥락상 여기가 자연스럽다 |
| ⓒ 둘 다 남긴다 | 두 경로 모두 허용 |

**권고: ⓑ.** *"이 원고에서 무슨 일이 있었나"* 는 저작 중의 질문이라 프로젝트 화면에 있는 것이
맞고, 관측은 운영 질문이라 `/me` 로 보낸다. **오너 의도가 "프로젝트 화면을 비우는 것"이면 ⓐ 다** —
확인이 필요하다.


## P8. ★ `/me/activity` 의 범위 — 소유 기준인가 행위자 기준인가 (검증이 찾아낸 숨은 결정)

**초판은 이것을 결정으로 올리지 않고 §"구현 순서"에서 조용히 골랐다** — *"소유 프로젝트 집합에
대한 조회"*. 그런데 활동 이벤트는 `actor_user_id` 를 갖고 있어 **두 기준이 존재한다.**

| 선택지 | 뜻 | 무엇이 보이나 |
|---|---|---|
| **ⓐ 소유 기준** | 내가 **소유한 프로젝트**의 모든 활동 | 내 프로젝트에서 일어난 일 전부 — **행위자가 내가 아닐 수 있다**(승격 관리자가 한 일) |
| ⓑ 행위자 기준 | `actor_user_id == 나` 인 활동 | 내가 한 일 전부 — **남의 프로젝트에서 한 것도 포함**(승격으로 접근했을 때) |
| ⓒ 둘 다(필터) | 기본은 하나, 토글 | 완전하지만 화면·계약이 는다 |

**둘은 지금 구분되지 않는다** — 관리자 = 오너(1인)이고 승격이 실사용되지 않아 **모든 이벤트가
양쪽 조건을 동시에 만족**한다. 그래서 아무거나 골라도 오늘은 같은 결과가 나온다.

**★ 그러나 이것이 S3·F4 와 직결된다**(검증 지적): 9.1 은 *"행위자는 항상 본인"* 이라는 전제로
**행위자 열을 만들지 않았다**(S3=ⓑ). **ⓐ 를 고르면 그 전제가 이 화면에서 먼저 깨진다** — 승격
관리자가 내 프로젝트에서 한 일이 **행위자 표시 없이** 내 타임라인에 섞인다. 즉 **ⓐ 는 F4(행위자
열)를 같이 여는 트리거**가 된다.

**권고: ⓐ + 조건 명시.** 개인 페이지의 주어가 "나"지만 그 페이지가 답하는 질문은
*"**내 것들**에 무슨 일이 있었나"* 이므로 소유 기준이 맞다. **다만 계약에 이렇게 적는다** —
*"소유 기준이며, 승격 접근이 실제로 쓰이기 시작하면 **F4(행위자 열)를 함께 연다**"*. 그러면
전제가 깨지는 시점에 화면이 조용히 거짓말하지 않는다.
