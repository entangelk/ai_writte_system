## 0. 먼저 — 이 요청은 착수 시점의 정본 계약과 충돌했다 (v1.7.49로 해소)

CLAUDE.md §5는 "나중 요청이 기록된 결정과 충돌하면 어느 쪽이 canonical인지 먼저 묻는다"고 정한다.

개정됐다.** 아래는 그 질문이 필요했던 이유의 기록이다 — 현행 정본은 이미 개정돼 있다.

| 착수 시점 SoT 조항 (§"제품과 프로젝트 경계") | 이번 요청 |
|---|---|
| "MVP는 **계정/인증이 없는** 단일 사용자 시스템이다." | 로그인·인증 도입 |

**중요한 뉘앙스**: 세 번째 조항은 살아남고(v1.7.49도 그대로 유지했다 — 소유권은 `project_id` 강제를

해제한 것과 같은 성격이다.

한편 **삭제 정책은 미확정 상태로 명시돼 있었다**(§"Product Shell": "보관/삭제 정책 … 미확정").
즉 CMS의 "삭제"는 계약을 뒤집는 것이 아니라 **비어 있는 칸을 채우는 일**이다. v1.7.49가 그 칸을
"보관은 확정 / **영구 삭제만 미확정(D5)**"으로 쪼개 두었다 — 아래 D5가 그 칸을 채운다.

## 1. 착수 전 실측 — 이 변경이 실제로 건드리는 표면

추정이 아니라 현재 코드에서 센 값이다.

| 표면 | 실측 | 인증 도입 시 생기는 일 |
|---|---|---|
| 공개 operation | 전체 **62개 / 52 path**, `/health` 제외 **61개 / 51 path** | 인가 대상은 **61/51**(`/health`는 인증 없이 응답해야 하는 유일한 operation이다 — 헬스체크가 로그인을 요구하면 compose healthcheck가 죽는다). H3 계약상 **401/403을 `responses=`에 선언**해야 하고 트랙별 전수 가드가 빠뜨림을 잡는다 |
| 경계 강제 | 모든 서비스가 `project_id`를 받는다 | `project_id` **소유자 검사**가 추가돼야 한다. 지금은 "존재하면 접근 가능"이다 |
| soft delete | `DELETE /projects/{id}`·`/drafts/{id}` = **archive**(`main.py:2242`·`2254`) | CMS "삭제"가 archive인지 hard delete인지 결정 필요(D5) |
| CORS | 열지 않음. nginx가 `/api`를 프록시해 **단일 origin** | 세션 쿠키 방식이면 지금 구조가 그대로 최적(같은 origin이라 CSRF 표면도 작다) |
| Elasticsearch | `xpack.security.enabled=false` (v1.6.53 G3=A) | 그 결정의 근거가 **"인증 slice 선행 필요라 범위 밖"**이었다. 이 슬라이스가 그 선행이다 |
| Mongo | 무인증 | 같은 이유로 함께 다뤄야 한다 |
| worker · script | request 컨텍스트 없음(관측 seam이 이미 이 성질에 의존) | **서비스 계정** 개념이 필요하다. 사용자 토큰 없이 도는 정당한 주체다 |
| 관측 KPI | `GET /projects/{id}/observability/kpi` — project 단위 | 관리자 전역 뷰가 필요해진다(D6) |
| 프론트 | 로그인 화면 없음, `credentials` 미사용 | 로그인/로그아웃·세션 만료·401 리다이렉트·라우트 가드 |

**규모 감각**: 이건 "endpoint 몇 개 추가"가 아니라 **61개 operation의 전제가 한꺼번에 바뀌는 변경**이다.
아래 D7이 그 62개를 어떻게 한 번에 닫을지를 정한다.

## D1 — 별도 서버로 분리할 것인가 (오너가 직접 물은 질문)

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. Application 내부 모듈** (추천) | `services/application/app/auth/`로 인증·세션·사용자 저장을 추가. 배포 서비스 수 무변 | **소유권 검사가 도메인 서비스와 같은 프로세스**에 있다 — `project_id` 소유자 확인이 네트워크 홉 없이 이뤄진다 · 트랜잭션 경계를 공유 · 이 저장소의 "필요해질 때 분리" 관행과 정합 | application이 한 가지 책임을 더 갖는다 |
| B. 별도 인증 서비스(자체 구현) | `services/auth/`를 새 컨테이너로 | Gateway·embedding처럼 경계가 선명 | **인가는 결국 application이 해야 한다** — 분리해도 소유권 검사는 application에 남는다. 즉 분리해서 얻는 것이 토큰 발급뿐이고, 서비스 간 신뢰·키 배포·장애 결합이 새로 생긴다 |
| C. 외부 IdP (Keycloak/Authentik 등) | 인증을 통째로 위임 | OAuth/OIDC·MFA·계정 관리가 기성품 · 직접 구현하는 암호 저장/세션을 안 만든다 | 로컬 1인 개발 단계에 **운영 부담이 가장 크다**(컨테이너 1개 + 설정 + 백업) · 이 제품의 사용자 수 규모와 안 맞음 |

**추천 A의 근거**: 오너 질문("별도 서버로 해야 되나?")의 실질은 *"분리하면 뭐가 나아지나"*인데,
실측상 **분리해도 인가는 application에 남는다**. Gateway가 분리된 이유(GPU·모델 파일·독립 스케일)나
embedding이 분리된 이유(모델 로딩)에 해당하는 동기가 인증에는 없다. 나중에 사용자 수·SSO 요구가
생기면 **C로 옮기는 문은 열어 둔다**(D2에서 그 이행 비용이 결정된다).

## D2 — 인증 방식

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 서버 세션 + HttpOnly 쿠키** (추천) | 로그인 시 세션 레코드 생성, 쿠키로 식별 | **단일 origin 구조(nginx `/api` 프록시)와 정확히 맞는다** · XSS로 토큰이 새지 않는다(HttpOnly) · **즉시 무효화 가능**(관리자 강제 로그아웃 = D6 요구사항) | 세션 저장소 필요(Mongo 한 컬렉션이면 충분) · CSRF 대비 필요(SameSite=Lax + 상태변경은 POST/PUT/DELETE라 대부분 자동 방어) |
| B. JWT(무상태) | 서명 토큰을 클라이언트가 보관 | 서버 상태 없음 · 서비스 간 전달 쉬움 | **즉시 무효화가 안 된다**(관리자 정지·삭제가 만료까지 지연) · localStorage 보관 시 XSS 노출 · 짧은 만료+refresh를 만들면 결국 상태가 생긴다 |
| C. IdP 위임(OIDC) | D1-C와 짝 | 표준·SSO | D1-C의 운영 부담을 그대로 상속 |

**추천 A의 근거**: 이 제품은 **브라우저 단일 origin SPA**이고 서비스 간 토큰 전파 요구가 없다.
JWT의 장점(무상태·분산)은 지금 값을 하지 않는 반면, 단점(무효화 불가)은 **관리자 기능이 직접 요구하는
것과 충돌**한다.

## D3 — 소유권 모델

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. `Project.owner_id` 한 필드** (추천) | 프로젝트가 사용자에게 속한다. draft/version/memory는 project를 통해 상속 | **경계가 이미 `project_id` 하나**라 검사 지점이 project 조회 한 곳으로 수렴 · 마이그레이션이 단순(기존 project에 owner 부여) | 공유·협업이 안 됨(1 project = 1 owner) |
| B. workspace/팀 계층 도입 | user → workspace → project | 협업·공유가 자연스러움 | **계층이 하나 늘어 62개 endpoint의 경로·검사가 함께 늘어난다** · 지금 요구는 "아이디별 관리"이지 협업이 아니다 |
| C. project당 멤버십 목록 | `project.members[]` | 공유가 가능하면서 계층은 안 늘어남 | 권한 등급(읽기/쓰기)이 따라오고, 그건 지금 요구 밖 |

**추천 A의 근거**: 요청 문구가 "**아이디별** 제작물 관리"다 — 공유가 아니라 격리다. A는
`owner_id` 하나로 그것을 달성하고, **B/C로 가는 문을 닫지 않는다**(`owner_id`는 나중에
`members[]`의 첫 원소가 되거나 workspace 소유로 승격될 수 있다).

## D4 — 기존 데이터의 귀속 (마이그레이션)

기존 project는 소유자가 없다. `owner_id`가 required가 되는 순간 **기존 데이터가 전부 고아가 된다**.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 첫 관리자에게 일괄 귀속** (추천) | 마이그레이션 스크립트가 부트스트랩 관리자 계정을 만들고 기존 project 전부를 그 소유로 | 기존 dogfood 데이터가 그대로 살아 있다 · 선례가 있다(`scripts/migrate_ordered_units.py`) | 실제로 여러 사람이 쓰던 데이터였다면 수동 재배정 필요(지금은 단일 사용자라 해당 없음) |
| B. `owner_id` nullable 유지 | 소유자 없는 project를 허용 | 마이그레이션 불필요 | **"주인 없는 데이터"가 영구 상태로 남는다** — 인가 검사가 매번 null 분기를 갖고, 그 분기가 언젠가 우회로가 된다 |
| C. 기존 데이터 폐기 | 새로 시작 | 가장 단순 | 정본 보존 정책과 정면 충돌 |

**선행 조건**: 마이그레이션 스크립트는 `migrate_ordered_units.py` 선례를 따라 **fail-closed**
(하나라도 애매하면 project 단위로 중단)이어야 하고, 완료 뒤에만 `owner_id` 인덱스/필수화를 건다.

## D5 — CMS "삭제"의 의미 (정본 보존 정책과 부딪히는 지점)

현재 계약: **project/draft는 archive(soft delete), snapshot/version/source_ref는 보존**.
`DELETE`는 이미 있지만 archive를 한다. 오너가 말한 "삭제"가 무엇인지에 따라 갈린다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 2단계 — archive → 영구 삭제(관리자만)** (추천) | 사용자는 archive까지. 실제 데이터 파기는 관리자 전용 별도 operation | 정본 보존 정책을 지키면서 CMS 요구를 만족 · **실수로 인한 파기가 구조적으로 어렵다** · 파기 대상이 명시적(project 전체 그래프) | operation 하나 추가 · 파기 범위 정의 필요(memory·vector·ES 색인·관측 레코드까지) |
| B. hard delete 도입 | `DELETE`를 진짜 삭제로 | 직관적 | **정본 보존 정책을 뒤집는다** · snapshot/version은 다른 데이터(memory·source_ref)가 참조하므로 참조 무결성 붕괴 위험 |
| C. archive 유지, 삭제 없음 | 현행 그대로 | 무변 | 요청 미반영 |

**A를 고를 때 반드시 함께 정해야 하는 것**: 파기가 **어디까지** 지우는가.
project 하나를 파기하면 `source_snapshots`·`draft_versions`·`source_refs`·`memory`·
`memory_vectors`(Chroma)·ES 색인·`llm_call_audits`·`writing_loop_audits`·scratch가 모두 대상이다.
**부분 삭제는 조용한 고아 데이터를 만든다** — 벡터 색인에 남은 임베딩이 다른 프로젝트 검색에
뜨는 식이다. 이건 별도 증분으로 다룰 만큼 큰 표면이다.

## D7 — 인가를 어디서 시행할 것인가 (62개를 한 번에 닫는 방법)

> **결정: A** (오너가 "보안 중점으로 구현자가 골라라"고 위임, 2026-07-27).
> **보안 근거**: 여기서의 실패 모드는 *다른 사용자의 project 접근 = 데이터 유출*이다. B(미들웨어)는
> 경로 패턴이 정책이 되어 **신규 경로가 조용히 열리고**, 무엇보다 **데이터 기반 소유권 검사를 못 한다**
> (미들웨어는 요청만 보지 대상 project의 owner를 모른다). C(서비스 계층)는 우회는 막지만 모든
> 시그니처를 오염시킨다. A만이 (1) authn(세션→user)과 authz(소유권)를 경계에서 함께 강제하고,
> (2) **선언 누락을 green으로 통과시키지 않는 전수 가드**를 H3·관측 조립 가드와 같은 형태로 얹는다.
> 이 저장소가 실측한 교훈("wrapper를 벗겨도 56 passed")이 인가에서 반복되면 결과가 데이터 유출이므로,
> fail-closed 전수 가드는 보안상 선택이 아니라 필수다.

| 선택지 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 의존성(dependency)으로 강제 + 전수 가드** (추천) | FastAPI dependency가 세션→user를 해석하고, `project_id`를 받는 경로는 소유권 검사 dependency를 함께 요구. **선언을 빠뜨린 endpoint를 잡는 전수 테스트**를 H3 가드와 같은 형태로 추가 | 이 저장소가 **이미 두 번 쓴 패턴**(H3 에러 선언 전수 가드, 관측 조립 가드) · 빠뜨림이 green으로 통과하지 못한다 | dependency 선언을 62곳에 붙여야 한다 |
| B. 미들웨어 일괄 | 경로 패턴으로 전역 차단 | 한 곳만 고침 | **경로 패턴이 곧 정책**이 되어 신규 경로가 조용히 열린다 · 소유권(데이터 기반) 검사는 미들웨어에서 못 한다 |
| C. 서비스 계층 검사 | 도메인 서비스가 user를 받는다 | 우회 불가 | 모든 서비스 시그니처 변경 · 관측 seam이 피한 계층 오염을 인가가 다시 들여옴 |

**추천 A의 근거**: 이 프로젝트가 반복해서 배운 것은 **"빠뜨림이 green으로 통과하면 언젠가 빠뜨린다"**
이다(관측 조립 가드에서 실측: wrapper를 벗겨도 56 passed). 인가에서 같은 실패는 **데이터 유출**이므로
전수 가드는 선택이 아니라 필수다.

## D8 — 슬라이스 순서 (착수 시)

한 번에 하지 않는다. 각 단계가 독립적으로 green이어야 한다.

1. **사용자·세션 저장 + 로그인/로그아웃 API**(인가는 아직 없음, 표면 무변)
2. **`owner_id` + 마이그레이션**(D4) — 필드만, 검사는 아직 없음
3. **프론트 로그인/세션 만료/라우트 가드** — E4=A로 인가보다 먼저 세운다
4. **인가 시행 + 전수 가드**(D7) — 3-a 인증 dependency → 3-b 소유권+목록 필터 → 3-c 전수 가드. 여기서 `/health` 제외 operation에 401/403이 붙는다. **가장 큰 단계**
5. **관리자 API + 화면**(D6)
6. **영구 삭제**(D5) — 파기 범위가 넓어 마지막
7. **인프라 보안 정렬** — Mongo 인증·ES `xpack.security` 켜기(v1.6.53이 이 슬라이스를 선행으로 지목했다)

## Follow-up considerations

- **관측 KPI가 사용자 축을 갖게 될 수 있다**(누가 얼마나 LLM을 쓰는가). `llm_call_audits`에
  `owner_id`를 넣을지는 이 슬라이스가 아니라 그 요구가 생길 때 결정한다 — 지금 넣으면 계측 계약을
  근거 없이 넓힌다.
- **비밀번호 저장**은 직접 구현하게 된다(D1=A·D2=A 선택 시). `argon2` 또는 `bcrypt` 중 택1이
  별도 의존성 결정이며, 직접 만들지 않는다(해시 함수를 손으로 짜는 것은 금기).
- **CORS는 계속 닫아 둔다.** 단일 origin 구조가 유지되는 한 열 이유가 없고, 쿠키 인증에서
  `Access-Control-Allow-Credentials`를 여는 것은 **다른 origin이 사용자의 인증 상태로 API 응답을
  읽게** 만드는 일이다. CSRF는 그와 다른 축이며 `SameSite`가 막는다(D2=A) — CORS는 CSRF를 막지 않는다.
- **`project_id` 강제 조항은 살아남는다.** 소유권은 그 위에 얹히는 두 번째 경계이지 대체가 아니다.

## Deferred / out of scope

- **협업·공유·권한 등급**(읽기/쓰기/댓글) — D3=A가 문을 열어 두되 이번 범위 아님.
- **SSO·OAuth 소셜 로그인·MFA** — D1/D2가 A면 나중에 C로 이행하는 문제.
- **요금제·사용량 과금** — 관측 KPI가 원자료를 이미 갖고 있지만 요구가 없다.
- **감사 로그 UI**(누가 무엇을 삭제했나) — D5 영구 삭제가 들어올 때 함께 볼 사안.
- **다중 테넌트 격리**(DB 분리 수준) — 로컬 1인 단계 범위 밖.
