### 2. 표 산술 정합성 — 전 행 정확 ✅

알파 표(work_log 564-573줄)의 모든 행을 직접 재계산. `입력 = system 465 + 컨텍스트 + 후보 4,159 +
래퍼 94`, `입력+출력 = 입력 + 6,144`, `창 여유 = 32,768 − (입력+출력)`.

| 예산 | 보고 입력 | 재계산 입력(465+ctx+4159+94) | 보고 합 | 재계산 합 | 보고 여유 | 재계산 여유 |
|---:|---:|---|---:|---:|---:|---:|
| 2048 | 6,769 | 465+2,051+4,159+94=6,769 ✓ | 12,913 | 6,769+6,144=12,913 ✓ | +19,855 | 32,768−12,913=19,855 ✓ |
| 8192 | 13,077 | 465+8,359+4,159+94=13,077 ✓ | 19,221 | 13,077+6,144=19,221 ✓ | +13,547 | 32,768−19,221=13,547 ✓ |
| 16384 | 20,473 | 465+15,755+4,159+94=20,473 ✓ | 26,617 | 20,473+6,144=26,617 ✓ | +6,151 | 32,768−26,617=6,151 ✓ |

전 행 일치. 베타 표(work_log 66-73줄)도 동일 방식으로 정합(8192 행: 465+8,358+4,159+94=13,076,
13,076+6,144=19,220, 16,384−19,220=−2,836). **작업자가 표 숫자를 정확히 맞췄다.**

핵심 관측: 여유 차이 `+13,547(알파) − (−2,836)(베타) = 16,383 ≈ 창 차이 16,384`(1 토큰 차이는 §4
참조). "창을 키우면 같은 패키지가 REJECT→PASS로 갈린다"는 R-c의 본질이 산술으로 성립한다.

### 3. "리그 PASS = 가드 통과" — 코드 수준에서 참 ✅

이것은 work_log 619-621이 "리그가 가드와 같은 식·같은 토크나이저를 쓰므로 cross-parity 테스트로
검증됨, 리그 PASS = 가드 통과"라고 단정한 **가장 강한 주장**이다. 세 갈래로 검증:

- **(a) 가드 식**(`client.py:158`): `if input_tokens + max_output <= window: return None`(PASS),
  아니면 `ProviderError`(REJECT). **inclusive(`<=`)**.
- **(b) 리그 식**(`report_budget_measure.py:133`): `"PASS" if self.total <= self.window else "REJECT"`,
  `total = input + output_cap`. 가드와 **정확히 동일한 식**. 주석(132줄)도 `client._window_decision`과
  같다고 명시.
- **(c) cross-parity 테스트**(`test_report_budget_measure_script.py::GuardParityTest:88-128`): 경계 3점
  `window−cap−1`(PASS)·`window−cap`(정확히 창, PASS)·`window−cap+1`(REJECT)에서 `BudgetRow.verdict`와
  프로덕션 `LlamaCppProvider._window_decision`의 결정이 같은지 `assertEqual(row.verdict == "REJECT",
  guard_rejects)`로 양방향 단언. 가드 식이 `<=`→`<`로 드리프트하면 이 셀이 문다.

추가로 리그는 창을 상수로 박지 않고 `counter.window()` → `/props`에서 읽는다(`report_budget_measure.py:271,177-178`). 그러므로 "같은 스크립트 한 줄로 알파(32768)·베타(16384)가 그려진다"는
전제가 코드로 성립한다. 계수도 가드와 같은 경로(`provider._count_prompt_tokens`, 181줄).

**한계(독자가 알아야 할 것)**: cross-parity는 가드의 **판정 로직 동등성**을 FakeJsonTransport로
검증한다. 즉 "두 식이 같다"이지, "배포된 창 32768에서 엔드포인트를 실제로 쳤을 때 가드가 PASS다"를
end-to-end로 검증한 것은 아니다. 다만 R-c의 본질은 창 **값**만 바뀌는 것이므로 산식 동등성으로
충분하고, 엔드포인트→가드 배선 자체는 베타 관통 실측(R-a v1.7.65, work_log 257-266 "유도 5307 →
report 호출 통과")에서 이미 검증됐다. 합리적 범위.

### 4. "동일 시드로 대조" — **서술 정확성 결함(차단 아님)** ⚠

오너 요약·SoT v1.7.68 행은 "동일 시드"/"같은 패키지"로 표현했다. 그러나 관측 사실은 **별개 시드**다.

- 알파 시드 project `6a6c7f914d586daaeef1cf22`(work_log 618·HANDOFF 63줄).
- 베타 시드 project `6a6be9c0dbb39de0a51ed8ba`(work_log 145·HANDOFF 64줄).
- **ID가 다르다** — 알파 시드는 알파 DB에서 새로 만들었고, 베타 시드는 베타 DB의 것이다.
- work_log 560-562는 정직하게 "시드는 알파에서 새로 만들었다 — 베타 시드와 **같은 생성기**라
  패키지 구조가 같다"고 적는다(같은 `build_manuscript` 결정론적 생성기). SoT v1.7.68 행도
  `input 13,076/13,077`로 **둘 다** 적어 다르다는 것을 숨기지 않는다.

**완전 동일 시드가 아닌 증거**: 입력 토큰이 1 차이(알파 13,077 vs 베타 13,076). 컨텍스트도 1 차이
(8,359 vs 8,358). `build_manuscript`(`report_budget_measure.py:83-108`)는 PRNG 없이 `_SENTENCES`를
회전시키는 **완전 결정론적** 함수이므로, 같은 `target_chars`·같은 `_grow_candidate` 수렴이면 산문은
바이트 단위로 동일해야 하고 토큰 수도 정확히 같아야 한다. **1 토큰 차이 = 산문이 미세하게 다르다 =
완전 동일 시드가 아니다.** 가능한 원인: 두 모델 서버(알파 `-m` 직접 로드 vs 베타 외부 서버)의
`/tokenize` 응답 미세 차이가 `_grow_candidate`의 글자 수 수렴을 1단계 어긋나게 한 것. "같은
모델·토크나이저"라는 전제가 토큰 단위로는 완벽히 들어맞지 않은 것이다.

**결론에 영향**: 없다. 패키지 구조(항목 62·회계 8,185)는 동일하므로 핵심 관측(8192가 창 32768에서
PASS)은 1 토큰 차이로 절대 뒤집히지 않는다(여유 +13,547). 하지만 **"동일 시드로 대조했다"는
표현은 엄밀하지 않다** — 정확히는 "같은 결정론적 생성기로 만든 **별개** 시드, 패키지 구조 동일,
입력 1 토큰 차이"다. 오너가 이 간극을 인지한 상태에서 "트랙 종료" 판단을 했는지 확인이 필요하다.

### 5. R-a 권장치 도출 — 보고값 범위 내 (미세 비재현) ✅

- 산식: `32,768 − 6,144 − 4,718 = 21,906`(재계산 정확 ✓).
- 환산: 보고 "만재 비율 0.981 → 약 21,487". 재계산 `21,906 × 0.981 = 21,489`(보고 21,487과 2 토큰
  차이 — 비율 반올림 범위).
- **미세 불일치**: 알파 표에서 실제 만재(포화) 행은 16,384, 비율 `15,444 / 15,755 = 0.9803`(반올림
  0.980). work_log가 "0.981"이라 한 것과 셋째 자리가 다르다. `21,906 × 0.9803 = 21,473`이면 보고
  21,487과 14 토큰 차이. 어느 비율을 쓰느냐(0.980 vs 0.981)로 권장치가 ±10 토큰 흔들린다.
- **추가 비대칭**: 베타 권장 5,407은 8192 행(비-진만재, 비율 0.979)에서, 알파 권장 21,487은 16,384
  포화 행(비율 0.981)에서 뽑았다 — 환산 비율이 0.979 vs 0.981로 달라 "창 증분에 **정확히**
  비례"는 엄밀히 아니다(보고 +16,080 vs 창 증분 16,384). 다만 차이가 미세하고 "R-c가 R-a에
  흡수됐다"는 정성적 결론은 흔들리지 않는다.

이것은 스크립트가 "가장 큰 포화 예산에서 비율을 뽑는다"(`report_budget_measure.py:405-411`,
독립검증 하드닝 #1로 고친 것)는 규칙의 정밀도 한계이지 결함이 아니다.

### 6. 회귀 기준선 "무변" — 논리적으로 타당 ✅ (한 맥락 누락)

코드 변경이 0이므로 기준선 변화의 원천이 없다 → "무변"은 타당. 당일 기준선 추이도 일관:
1772(R-a) → 1773(보강) → 1777(루프) → 1779(K-4) → **1779 무변**(이 슬라이스). 증가만, 회귀 0.

**누락된 맥락(메모 수준)**: "1779 무변"은 **베타 K-4 기준선의 인용**이다. 이 관측은 알파 머신에서
했는데, 알파 application 이미지는 argon2-cffi가 빠져 "auth 관련 26개 모듈이 수집 단계에서 실패"
한다(HANDOFF 61·149줄). 즉 **알파에서는 1779 기준선을 재실측할 수 없었고**, 이 슬라이스에서
회귀를 아예 재실행하지 않았다(코드 변경 0이므로 합리적이지만 명시는 안 됨). HANDOFF가 기준선
출처("K-4 후 실측")를 명시하므로 심각한 문제는 아니다.
